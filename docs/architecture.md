# Архитектура бэкенда

Бэкенд сгенерирован из шаблона
[`copier-template-python-backend`](https://github.com/eldenizfamilyanskicode/copier-template-python-backend)
и следует его ролям и правилам (`AGENTS.md`, `docs/conventions.md`). Здесь — как
техническое задание из [концепции v2](concept.md) переложено на Python.

## Отличия от стека в ТЗ

| В ТЗ | Здесь | Почему |
| --- | --- | --- |
| Next.js API-роуты (вебхуки, инструменты) | FastAPI в этом репозитории | требование владельца: бэкенд на Python по шаблону copier |
| Сайт, анкета, кабинет на Next.js | кабинет на Next.js в `web/` | ходит в HTTP API бэкенда через свои серверные маршруты; токен только в httpOnly cookie |
| Supabase Postgres (ЕС) + RLS | контракт документного хранилища; in-memory для тестов и Postgres (ЕС) с изоляцией по `business_id` | use case не зависят от базы |
| Node-воркер + pg-boss | Python-воркер с очередью в Postgres | один язык и одни use case для API и фоновых задач |
| packages/core, brain, channels, niches, evals | роли шаблона: use_cases, orchestrators, registries, adapters… | `services` запрещён шаблоном |
| `tenants`, `users` | `BusinessDocument`, `UserDocument` | те же поля; «бизнес» понятнее в коде |

Всё остальное — как в ТЗ: OpenAI gpt-5-mini в проекте с хранением в ЕС как «мозг»,
ElevenLabs Agents для голоса, номера Zadarma, WhatsApp Cloud API, Instagram и
Messenger через Graph API, Telegram Bot API, свой виджет, Flitt, Langfuse, Sentry.

## Роли и направление зависимостей

```text
HTTP (FastAPI)              app/gateways/http/      маршруты, коды ошибок, ответы
  └─ operators              app/operators/          одна точка входа на эндпоинт
      └─ pipelines          app/pipelines/          порядок оркестраторов в фазе
          └─ orchestrators  app/orchestrators/      координация нескольких use case
              └─ use_cases  app/use_cases/          одно бизнес-действие
                  ├─ repositories  app/repositories/  документы с изоляцией по бизнесу
                  ├─ registries    app/registries/    страны, языки, ниши, тарифы
                  ├─ facilitators  app/facilitators/  узкие побочные эффекты (SMS, уведомления)
                  ├─ utilities     app/utilities/     детерминированные операции
                  └─ transformers  app/transformers/  преобразование форм
repositories ─ adapters (app/adapters/) ─ clients (app/clients/)  внешние системы
```

Направление проверяет `lint-imports` по контрактам `.importlinter` в каждом прогоне
тестов; утилиты — чистые помощники, их могут импортировать все роли
([ADR 0002](adr/0002-role-chain-and-layers.md)).

## Данные (ТЗ §2)

Каждая таблица ТЗ — документ в `app/schemas/domain/`. Документы бизнеса несут
`business_id`; репозитории читают их только вместе с `business_id`
(`BusinessScopedRepository`), поэтому чужие данные недоступны ни по какому id —
это аналог RLS из ТЗ. `tenant_id` в инструментах берётся из сессии или из
канала на сервере, никогда из слов модели.

Вторая линия защиты — RLS в Postgres. Операторы (`BusinessScopedPipelineOperator`)
выполняют запрос бизнеса внутри `StorageScopeContract.scoped_to_business(...)`,
так же работают ход разговора (с вызовами инструментов модели), вызовы
инструментов голосового агента и задачи очереди с `business_id`. Тогда даже
репозиторий, забывший фильтр по бизнесу, не прочитает и не запишет чужие строки.

Область хранилища закрыта по умолчанию (fail-closed): код, не вошедший ни в
какую область, — `UNSCOPED` (`app.business_id = ''`, обход RLS выключен), и
коллекции бизнесов отказывают ему (`UnscopedStorageAccessError`, в памяти так
же, как в Postgres); коллекции платформы (пользователи, сессии, бизнесы,
журнал) доступны. Работа уровня платформы объявлена явно оператором
`PlatformWidePipelineOperator` (`platform_pipeline_operator` в
`provider_chains.py`): вебхуки до определения бизнеса (Telegram, Meta,
платежи, голос, согласие Google), список клиентов в админке, демо-данные и
периодические задачи по всем бизнесам. Вход, текущий пользователь и очередь
задач в админке работают без области — им нужны только коллекции платформы.
Код, которому нужно посмотреть сквозь бизнесы внутри запроса бизнеса
(уникальность аккаунта канала), явно поднимается через `platform_wide()`.
Каждая операция хранилища — своя транзакция, в начале которой задаётся
область; несколько чтений одной области можно выполнить в одной сессии
чтения (`StorageReadSessionContract.read_session()`: одно соединение, одна
транзакция, область задаётся один раз вместе с `begin`, каждое чтение — один
оператор). Записи и чтения другой области (коллекции платформы) внутри неё
идут на своих соединениях, как без неё, поэтому настройки RLS сессии никто
другой не меняет.
Проверки: `tests/platform/test_authorization_matrix.py` (каждая операция
`/v1/businesses/{business_id}/…` из описания API: чужой — 404 без следов,
сотрудник на операциях владельца — 403, без токена — 401, запрос — только в
области своего бизнеса; то же на Postgres в
`tests/storage/test_authorization_matrix_postgres.py`) и
`tests/architecture_policy/test_business_routes_are_scoped.py` (маршруты
бизнеса — только через `BusinessScopedPipelineOperator`, список операторов
уровня платформы утверждён).

## Пошаговый запуск

Путь владельца от «Создать AI-помощника» до живого помощника
(`app/use_cases/setup/`, `app/use_cases/assistants/apply/`):

- шаги запуска не хранятся, а вычисляются из данных бизнеса
  (`app/utilities/setup/setup_steps.py`): пробелы анкеты, контакт сотрудника,
  каналы, проба помощника, опубликованная версия; хранятся только
  пропущенные необязательные шаги;
- готовые ответы ниш (`app/registries/niches/starters/`) — подсказки, не
  факты: в анкету попадают только по согласию владельца и только в пустые
  разделы, цен в них нет;
- «Применить изменения» — оркестратор `ApplyChangesOrchestrator`: регистрация
  (атомарно, одна на бизнес), сборка, проверка условий запуска, постановка
  автотестов в очередь; публикует версию воркер, когда прогон закончился
  (`RunQueuedAutotestsOrchestrator` → `PublishAppliedVersionUseCase`) — через
  ту же активацию, что и ручная публикация;
- первый выход в эфир открывает пробный период (`StartTrialAtGoLiveUseCase`)
  и пишет веху `went_live`; первые настоящие разговор, бронь и передача
  человеку находятся по самым ранним записям бизнеса при чтении шагов, поэтому
  модули разговоров и броней о вехах не знают;
- тестовый чат владельца перед ответом собирает черновик, если в версиях ещё
  нет его последних правок (`PrepareTestChatVersionUseCase`);
- в кабинете этот путь — полноэкранный туннель из восьми вопросов: `/create`
  (бизнес и место; бизнес создаётся `POST /v1/assistants` в конце второго
  вопроса, до этого ответы хранятся в браузере) и `/b/{id}/setup` (остальные
  шаги, запуск и финал); туннель открывается на первом незавершённом шаге,
  своих данных у него нет (web/README.md, «Create an AI assistant»);
- после запуска тот же `GET …/setup` отдаёт подсказку «Обзора» (`guide`,
  `app/utilities/setup/guide_steps.py`): проверка с телефона, второй канал,
  ссылка для клиентов. Их факты тоже вычисляются (`SetupProbeRepository`:
  первое входящее с номеров владельца или в чат страницы, пока идёт проверка;
  каналы для клиентов; первая бронь в нерабочее время), а в состоянии запуска
  (`SetupStateDocument` v2) хранятся только времена, которых в данных нет:
  проверка начата и прошла, ссылка напечатана или скачана, первый визит на
  страницу чата, подсказка убрана, напоминания выключены. Модуль входящих
  сообщений о проверке не знает: факты замечает чтение шагов или задача
  `notice_milestones`;
- вехи после запуска объявляются владельцу один раз
  (`app/use_cases/setup/milestone_announcements.py`: `StaffAlert` с
  `subject` «milestone:…» через `ManagerNotificationFacilitator`), кабинет
  поздравляет и подтверждает `POST …/celebrate`;
- напоминания о настройке — периодическая задача `send_activation_nudges`
  (`SendActivationNudgesUseCase`): правило дня (`nudge_schedule.py`,
  `NudgeCode`, `NudgeDayOffset`), отправка через исходящие
  (`OwnerNudgeFacilitator`: Telegram-контакты владельца у бота платформы,
  почта, устройства) и запись в `nudges_sent` с ключом из
  (business_id, nudge_code); повторный запуск находит запись и молчит;
- способ подключения (`SetupOption`) выбирается при подписке: `SELF_SERVE`
  бесплатно, `DONE_FOR_YOU` — плата за подключение тарифа из каталога
  (`SETUP_FEES`) с первым ежемесячным счётом и заявка команде
  (`onboarding_requests`, письмо админам платформы).

## Общие входящие команды

Несколько человек ведут разговоры одного бизнеса (`app/use_cases/inbox/`,
`app/repositories/inbox_repositories.py`, миграция 1053):

- поля команды в `ConversationDocument` — ответственный, кто и когда
  назначил, `assignment_revision`, `has_open_request` и производное
  `awaits_team` (нужен человек или открыта заявка) — меняются только через
  `ConversationTeamRepoContract`: назначение — сравнить и записать по
  ревизии под блокировкой строки, открытая заявка — пересчётом при создании
  и смене статуса заявки (`track_request`). Обычное сохранение разговора
  (ход, передача, закрытие) берёт поля команды из хранимой строки, поэтому
  ход, начатый до назначения, его не отменяет;
- виды «нужен человек», «заявки», «мои», «без ответственного» и «все» —
  keyset-страницы по индексам `(business_id, условие вида,
  last_message_at)`; «без ответственного» — условие хранилища `missing`
  (поле отсутствует или null, `DocumentFilter.missing`); счётчики видов и
  нагрузка участников — один сгруппированный подсчёт ждущих разговоров;
  `CountInboxAttentionUseCase` отдаёт одни и те же счётчики вкладкам
  (`…/inbox/counts`) и значкам меню (`…/attention-counts`): значок
  «Входящие» — сумма вкладок «Нужен человек» и «Заявки»;
- строка вида собирается `InboxItemTransformer` из разговора, последнего
  написанного сообщения, открытых передачи и заявки (по одному `latest_by`
  на страницу) и числа заметок — без расхода модели, вызовов инструментов и
  свободного текста;
- автоназначение — декоратор передачи (`AutoAssigningHandoffUseCase`) и шаг
  создания заявки: кандидаты — выбранные участники, иначе сотрудники, иначе
  владельцы; меньше ждущих разговоров, при равенстве — по кругу после
  последнего назначенного; ошибка назначения пишется в лог и не мешает
  передаче;
- заметки — отдельная коллекция, а не сообщения: подготовка хода, расшифровка
  для модели, виджет и уведомления их не читают
  (`tests/e2e/test_team_inbox_journey.py`); быстрые ответы — один документ
  на бизнес с вариантами по языкам, переменные подставляются только из
  данных разговора, недостающие остаются в скобках;
- каждая операция проверяет доступ через `AuthorizeBusinessAccessUseCase`,
  просмотр вида, назначение, заметки, быстрые ответы и настройки пишутся в
  журнал аудита, назначение и заметки — в живые события
  (`conversation.assigned`, `conversation.note`).

## Ценность помощника, сводки и отчёты

Что помощник сделал и сколько это стоит (`app/use_cases/insights/value/`,
`app/repositories/value_repositories.py`, миграция 1061):

- модель ценности (`ComputeValueModelUseCase`) считает за период и за
  предыдущий период той же длины (тестовая активность не входит):
  разговоры и разговоры в нерабочее время, сообщения клиентов и ответы
  помощника, принятые звонки, все брони и брони, сделанные помощником в
  разговоре и не отменённые, заявки, передачи человеку; минуты сотрудников =
  ответы × секунды на ответ ниши + звонки × секунды на звонок
  (`app/registries/niches/niche_value_catalog.py`); деньги = брони помощника
  по их собственной стоимости (цена услуги, ночи номера по сезонным
  тарифам; см. «Услуги, мастера и номера»), остальные брони × средний чек
  (`revenue_source`: `booked_values`, `mixed` или `average_check`); для
  ниш, где принимают заказы, — заявки × средний чек (`value_basis`);
- средний чек — свой у владельца (`value_settings`, `PUT …/value/settings`,
  пишется в журнал аудита) или типичный для ниши, пересчитанный в валюту
  бизнеса и округлённый до двух значащих цифр; без него оценки в деньгах
  нет, кроме броней со своей стоимостью;
- `GET …/value` отдаёт модель кабинету, сотрудникам — без денег; счётчики —
  сгруппированные подсчёты хранилища (`ValueCountRepository`), без чтения
  строк;
- сводки и отчёт: периодическая задача `send_value_reports` (раз в час,
  запуск сохраняется в `PeriodicJobRunner`, поэтому один на все процессы и
  перезапуски) для каждого работающего бизнеса в его часовом поясе готовит
  дневную сводку (вчера, если хоть один владелец её включил), недельную (с
  понедельника 9:00 — прошлая неделя) и месячный отчёт (с 1-го числа 9:00 —
  прошлый месяц, и для бизнеса на паузе). Снимок итогов сохраняется в
  `value_reports` с ключом uuid5(бизнес, вид, период) через
  `insert_if_absent`: второй запуск видит готовый отчёт и ничего не шлёт;
  письма и push уходят через outbox с ключами по отчёту, поэтому повтор
  после падения посередине не дублирует уже поставленные
  (`tests/value/test_value_reports_restart.py`). Период без активности
  сохраняется как `quiet` и не отправляется;
- получатели (`OwnerDigestFacilitator`) — владельцы, у которых этот вид
  включён (`digest_preferences`: по умолчанию недельная сводка и месячный
  отчёт, дневная выключена): письмо на адрес входа на языке кабинета и push
  на устройства с включёнными уведомлениями этого бизнеса (тихие часы
  владельца соблюдаются только для push). В тексте — подписанная ссылка
  `{кабинет}/n/{token}` (цель `report`), открывающая отчёт на странице
  «Обзор → Отчёты», и строка о том, где отключить сводки;
- кабинет: на сводке владелец видит блок ценности (брони ≈ деньги, нерабочее
  время, сэкономленное время, средний чек правится на месте), у каждой
  цифры — изменение к предыдущему периоду словами для экранного диктора;
  сотрудник вместо этого видит свою очередь дня (`GET …/today-queue` и виды
  ящика). Страница «Отчёты» (только владельцы): текущий месяц, сохранённые
  месячные, недельные и дневные отчёты и выбор сводок.

Чего нет: сводок в Telegram и WhatsApp сотрудников (только почта и push),
ссылки отписки в одно нажатие без входа в кабинет.

## Услуги, мастера и номера

Что можно забронировать и сколько стоит бронь (`app/utilities/bookings/`,
`app/use_cases/bookings/offer_selection.py`, миграция 1083):

- знания вида `service`, `package` и `room_type` описывают бронь:
  длительность (`ServiceDurationMinutes`, 5–720 минут), перерыв мастера
  после визита (`BufferMinutes`), цену и исполнителей
  (`performer_resource_ids`); ресурс со своей стороны называет услуги,
  которые выполняет (`serves_item_ids`), и тип номера (`room_type_item_id`).
  Связь читается с обеих сторон. У типа номера — сезонные цены ночи
  (`seasonal_rates`, «MM-DD»–«MM-DD» каждый год, в том числе через Новый
  год); ночь вне сезонов стоит `price_minor`;
- инструменты модели `check_availability` и `create_booking` принимают
  `service_id` и `resource_id` — id или имя в любой письменности
  («Nino», «ნინო», «Нино», «стрижку»): `target_resolution` сравнивает имена
  как написаны и в латинской транскрипции, по словам, с учётом склонений и
  опечаток, имена на иврите и арабском — по согласным. Неизвестное или
  неоднозначное имя — отказ с кодом (`unknown_service`,
  `ambiguous_resource`, …), список вариантов для модели и id в `details`;
  мастер, который не выполняет услугу, — `not_performed`. Без услуги
  результат проверки перечисляет услуги с их id;
- слоты длятся столько, сколько услуга, и предлагаются только её
  исполнителям; бронь хранит свой перерыв (`buffer_minutes`), и следующая
  бронь ресурса не начнётся раньше его конца (`booking_placement`);
- бронь хранит услугу и стоимость (`service_item_id`, `value_minor`,
  `currency_code`): цену услуги или сумму ночей проживания по сезонам
  (`stay_quotes`); перенос проживания пересчитывает её. `get_price` с датой
  заезда и числом ночей отдаёт расчёт по ночам;
- сводка кабинета (`booked_value`, `after_hours_booked_value`) и модель
  ценности складывают стоимости базой данных (`sum_value_made`,
  генерируемые колонки и покрывающий индекс миграции 1083), без чтения
  броней; отменённые и неявки не входят;
- автотесты ниш: салон, клиника и ветклиника бронируют услугу у названного
  мастера, отель и аренда — тип номера на несколько ночей
  (`BookingScenarioVariant`).

Редакторы услуг, исполнителей и сезонов в кабинете — R10-SERVICES-CABINET.

## Страница чата и ссылки

Контекст `sharing` (`app/use_cases/sharing/`, маршруты
`sharing_routes.py` и `public_chat_routes.py`):

- адрес страницы чата `/c/{slug}` — запись `public_slug_claims` с ключом-адресом,
  вставляется «если нет» (`insert_if_absent`), поэтому один адрес не достаётся
  двум бизнесам даже при гонке и под RLS; записи остаются у бизнеса навсегда,
  так что старый адрес (и напечатанный QR-код) ведёт к нему же. Коллекция —
  бизнеса (`business_id`), публичный поиск по адресу явно поднимается через
  `platform_wide()` (`ResolveHostedChatUseCase`), затем страница читается в
  области найденного бизнеса (`HostedChatOrchestrator`). Первый адрес — из
  названия (`app/utilities/sharing/`: транслитерация грузинского, кириллицы,
  армянского), при занятости — с номером, в крайнем случае `chat-<hex>`
  (такие адреса зарезервированы и владельцу недоступны);
- ссылки каналов строит `app/utilities/channels/channel_links.py`; публичные
  адреса аккаунтов (номер WhatsApp, username страницы и Instagram) API узнаёт
  при подключении канала (`ChannelDocument.public_profile`); канал без них
  отдаёт «переподключите»;
- ссылка на политику конфиденциальности — вид `privacy` в ссылках анкеты; она
  хранится в отдельном поле `BusinessProfileDocument.privacy_notice_url`
  (правило expand/contract: новое значение перечисления не пишется в
  документы в том же выпуске, где появилось), API показывает её среди ссылок;
- «Позвать человека» из виджета (`WidgetHandoffPipeline`) держит ту же
  блокировку клиента, что и входящее сообщение, открывает или находит
  разговор посетителя и передаёт его через `HandoffToHumanUseCase` с причиной
  `customer_request`; уже переданный разговор второй передачи не получает.

Страницу `/c/{slug}` рисует кабинет (`web/src/app/c/[slug]/`): прокси узнаёт
бизнес у `GET /v1/public/chat/{address}`, переводит старые адреса и id на
текущий, ставит строгую CSP с адресом API в `connect-src` и передаёт ответ
странице в заголовке запроса (повторного вызова нет); страница грузит
`widget.js` с nonce в режиме страницы. Та же страница — «ссылка в профиле»:
рядом с чатом она показывает часы работы (в часовом поясе бизнеса), адрес
со ссылкой на карту и кнопку «Забронировать» (`HostedChatView` отдаёт
`hours`, `address`, `maps_url`, `takes_bookings`, `booking_url`).

### Живой поток посетителя

Виджет слышит ответ сразу, а не со следующим опросом:

- билет: `IssueWidgetStreamTicketUseCase` (в цепочке сообщения и опроса,
  `WidgetMessageOrchestrator`, `WidgetMessagesOrchestrator`) подписывает
  `WidgetStreamTicketSigner` (HMAC, ключ из `ENCRYPTION_KEY` с меткой
  `assistant-workshop/widget-stream-tickets/v1`, старые ключи проверяют):
  бизнес, `WidgetVisitorId` (sha256 ключа посетителя — сам ключ в билете не
  лежит) и срок на час. Ключ посетителя никогда не попадает в адрес;
  билет в адресе вымарывается из журнала доступа;
- маршрут `GET /v1/widget/{id}/events?ticket=…`
  (`widget_event_routes.py`, в схеме OpenAPI как `text/event-stream`, как и поток кабинета):
  `OpenWidgetStreamOperator` → `OpenWidgetStreamUseCase` проверяет билет
  (401 — чужой, просроченный, испорченный) и что чат сайта подключён (404),
  затем `WidgetEventStreamFacilitator` подписывает на шину живых событий
  только события этого посетителя (лимиты на процесс: 500 потоков бизнеса,
  20 с одной сети, сверх — 429). Поток живёт 15 минут, сердцебиение — 20 с;
- события: `widget.typing` публикует `CustomerWait`, когда воркер взял
  сообщение посетителя; `widget.reply` — запись ответа помощника, сообщения
  сотрудника, «минутку», заметки о передаче. Оба — только с id; текст
  читает `ReadWidgetStreamMessageUseCase` и отдаёт его в `answer_ready`,
  только если это исходящий ответ модели с вердиктом проверки CLEAN
  (остальное — без текста: виджет дочитывает опросом). Поток кабинета и
  буфер повтора этих событий не видят; старый выпуск их пропускает;
- виджет (`mount_stream.js`) открывает EventSource, пока ждёт ответа, и
  остаётся на опросе без него; через 90 секунд без ответа — заметка «Мы
  ответим, как только сможем» и `POST …/handoff` с `reason: no_answer`
  (`no_answer_handoffs.py`: «нестандартный запрос», высокая срочность,
  сводка `MODEL_UNAVAILABLE` с последним вопросом).

## Подтверждение брони и страница гостя

Когда `create_booking` или `reschedule_booking` помощника удаётся вне
тестового чата, `RunAssistantToolUseCase` после ответа инструмента зовёт
`BookingConfirmationHook` (слой инструментов, не сценарий брони: брони
сотрудников из кабинета гостю ничего сами не пишут). Хук вызывает
`SendBookingConfirmationUseCase`; его сбой пишется в лог и не доходит до
модели. Подтверждение идёт в чат, где сделана бронь: в виджет — сообщением
разговора (`author: system`, `direction: outbound`, виджет показывает его
как обычный текст со ссылкой; `widget.js` не меняется), в мессенджеры —
через outbox (`booking_confirmation`, придержано на 5 секунд за ответом
помощника, `send_before` — начало брони); WhatsApp вне 24-часового окна
получает утверждённый шаблон `WHATSAPP_BOOKING_CONFIRMATION_TEMPLATE`,
Messenger и Instagram — ничего. Телефон не подтверждается (у звонка своё
письменное подтверждение).

Ссылка `{CABINET_BASE_URL}/r/{token}` ничего не хранит: токен
(`BookingManageTokenSigner`, HMAC-SHA256 с ключом из `ENCRYPTION_KEY` и
меткой, как у ссылок сотрудников `/n/…`; предыдущие ключи кольца тоже
проверяются) несёт бизнес, бронь, её «версию» (время начала) и срок
(месяц после конца). Публичные маршруты `/v1/public/bookings/{token}`
проверяют подпись и срок (`OpenBookingManageLinkUseCase`), затем входят в
область хранения бизнеса из токена (`ManagedBookingOrchestrator`) и читают
бронь; перенесённая бронь отвечает 404 `booking_changed`. Отмена и перенос
идут теми же `CancelBookingUseCase` и `RescheduleBookingUseCase` с
контактом брони (правила владения те же, что в чате), а
`expected_starts_at` проверяется под блокировкой бизнеса: две вкладки одной
ссылки не перенесут бронь дважды. Свободное время для переноса —
`CheckAvailabilityUseCase` со всеми временами дня и без самой брони.
Лимиты — на ссылку, сеть и платформу.

Страница гостя в кабинете (`web/src/app/r/[token]/`) читает бронь на
сервере и говорит на языке брони (15 языков подтверждения,
`web/src/lib/bookingPage/`, иврит и арабский справа налево); действия идут
через BFF, после переноса адрес страницы меняется на новую ссылку. Прокси
отдаёт её с `noindex`, `Referrer-Policy: no-referrer` и `no-store`, ключ
ссылки вырезается из access-логов API и из событий Sentry. Страница
`/c/{address}` стала «ссылкой в шапке профиля»: `HostedChatView` несёт часы,
адрес, ссылку на карту и признак записи, и рядом с чатом (на телефоне —
строкой над ним) видно, открыто ли сейчас, неделю, адрес и кнопку
«Забронировать» (страница бронирования бизнеса или первая фраза в чате).

## Импорт знаний с сайта и защита от SSRF

Импорт с сайта бизнеса (`app/use_cases/knowledge/website_import/`) — задача
воркера: страницы того же сайта (до 15, из `sitemap.xml` или ссылок стартовой
страницы) читаются по одной, каждая проходит одно извлечение моделью, а
найденное становится выключенными черновиками того же вида, что у импорта
меню, — их проверяет и включает владелец, сам импорт ничего не публикует.

Любой адрес, который присылает владелец или находит импорт, скачивается только
через `SafeHttpFetcherContract` (`app/clients/http/safe_http_fetcher.py`):

- адрес проверяется до сети (`http`/`https`, порты 80 и 443, без логина,
  без `localhost` и служебных зон);
- имя разрешается один раз, каждый IP сверяется со списком запрещённых сетей
  (`public_addresses.py`), и соединение открывается ровно на проверенный IP
  (`VettingNetworkBackend` для httpcore; TLS проверяет исходное имя) — подмена
  DNS между проверкой и соединением ничего не даёт;
- каждый из не более трёх редиректов проверяется так же;
- общий срок, предел размера после распаковки и белый список типов содержимого.

Текст страницы очищается от скриптов, стилей и скрытого текста
(`app/utilities/knowledge/website/`) и уходит модели внутри ограждения со
случайным ключом как недоверенные данные.

## Адаптивность под любую страну

Требование владельца проекта и раздел «Масштаб» ТЗ («новая страна — это язык,
номера, платежи и партнёр на месте, а не новый продукт»):

1. **Номера телефонов** любой страны разбираются библиотекой `phonenumbers`
   (245 регионов) и хранятся только в E.164. Из номера выводятся страна, тип
   линии и часовые пояса. Телефон в инструментах модели разбирается с подсказкой
   страны бизнеса, а не «+995» по умолчанию.
2. **Профиль страны** собирается для каждой страны мира из `phonenumbers` и
   Babel/CLDR (языки, валюта, часовые пояса), сверху — кураторские данные:
   экстренный номер, стартовые языки (для Грузии ka, ru, en; по запросу tr, he,
   ar, hy), канал кода входа, правило записи звонков (уведомление или согласие
   всех сторон), местные номера, статус онбординга, регион данных (ЕС).
3. **Языки** — любые теги BCP 47; направление письма (иврит и арабский — справа
   налево); честная пометка голоса: `verified`, `beta`, `needs_pilot_check`
   (грузинский — до замера на пилоте, как требует ТЗ).
4. **Деньги** — целые минимальные единицы валюты бизнеса (в Грузии — лари).
   Тарифы — в евро с прайсом в лари; фильтр выдуманных цифр понимает символы и
   коды любой валюты. Курсы — датированные строки `exchange_rates` (задача
   `refresh_exchange_rates`: НБГ и ЕЦБ раз в 6 часов), точные десятичные
   строки; недостающая пара — обратный или кросс-курс через евро с пометкой
   «рассчитан», старше 4 дней — «устарел»; до первого обновления — датированный
   запасной каталог. Один `ExchangeRateRegistry` пересчитывает и цены тарифов,
   и ценность помощника, и маржу клиента в админке.
5. **Время** — часы, исключения и брони в часовом поясе бизнеса (IANA),
   хранение в UTC.
6. **Тексты** для владельца и клиента — словари `язык → текст` с откатом:
   запрошенный язык → базовый язык → английский. Тексты владельца на бэкенде
   (тарифы, шаблоны ниш, уведомления сотрудникам, инструкции переадресации,
   тексты оплаты) — каталог `app/registries/localization/texts/<язык>.json`
   на каждом языке кабинета (`CABINET_LANGUAGES`: ka, ru, en, he, de). Файлы
   читаются и проверяются при старте (`owner_texts.py`: язык файла,
   английский — проверенный источник, нет лишних ключей, те же
   `{плейсхолдеры}`), модули берут тексты по ключу, литералов в коде нет
   (политика `test_owner_texts_cover_cabinet_languages.py`). Иврит и немецкий —
   черновики (`needs_review`, `TextCatalogRegistry.review_status`); в
   выставленные счета и чеки попадают только проверенные языки
   (`reviewed_owner_text`), остальные читают английский. Промпт помощника
   берёт только английские значения, снимки промптов не меняются. Пропуски и
   черновики показывает `uv run python -m scripts.translate_catalogs backend
   check`, `backend draft --language <тег>` пишет черновики пропусков моделью
   из `.env`, `backend reviewed` отмечает проверку носителем языка. Черновики
   DPA на иврите и немецком — `docs/legal/drafts/` (не публикуются).
7. **Язык клиента** — любой, не только языки версии
   (`LanguageDetector.detect_any`, `app/utilities/conversations/any_language_detection.py`):
   сначала письменность (грузинские, армянские, ивритские буквы сразу
   называют язык), для общих письменностей (латиница, кириллица, арабская,
   деванагари) — частые слова, особые буквы и буквы, которых нет в алфавите
   языка; около 55 языков, на которых есть уведомление об ИИ. Латиница
   проверяется ещё и как транслит грузинского, русского, украинского,
   армянского и иврита («gamarjoba», «privet», «barev», «shalom»): язык —
   грузинский, подсказка письменности `Latn`. Сообщение без слов («ok»,
   эмодзи, цифры) или со слишком слабыми признаками сохраняет язык
   разговора, затем контакта, затем язык версии по умолчанию; чужая
   письменность (кроме латиницы, на которой пишут имена и бренды)
   переключает сразу. `PreparedTurn.reply_language` и `script_hint` попадают
   в строку контекста модели («Reply language: Hebrew (he).»), на этом языке
   идут уведомление об ИИ, «передаю коллеге» и сообщение о лимите;
   разговор, сообщение и контакт хранят его же. Автотесты каждой версии
   проверяют это сценариями `foreign_language` (язык не из списка: один с
   другой письменностью, один латинский, `language_scenarios.py`) и
   `transliterated` (язык версии латиницей); детерминированная проверка
   `wrong_disclosure_language` смотрит, что уведомление об ИИ пришло на
   языке клиента.
8. **Переадресация звонков** — коды GSM (`**61*`, `**67*`, `**62*`,
   `##002#`) для любой страны; для GE, AM, AZ, UA, TR, DE и IL инструкция
   называет операторов и их особенности (`call_forwarding_carriers.py`).
   Оператор, чьи коды ещё не сверены с его документацией (`needs_review`, все
   кроме Magti), помечен в кабинете фразой «пока не подтверждено у
   оператора», чтобы владелец знал, кого спросить, если код не сработал.

## Обучение помощника на разговорах

- «Исправить ответ» (`CorrectAnswerUseCase`, только владелец): исправление
  ответа помощника становится элементом знаний (вопрос, цена, часы или
  правило), который помнит исправленное сообщение (`correction_of`) и, как
  любая правка знаний, ждёт «Применить изменения»; плохая оценка разговора
  перестаёт ждать улучшения (`improved_at`). Черновик диалога
  (`GetAnswerCorrectionDraftUseCase`) берёт вопрос клиента, предлагаемый вид
  по вызовам инструментов и вердикту проверки ответа и то, что помощник знает
  сейчас; чтение пишется в аудит.
- Причина плохой оценки (`rating_reason`: неверные сведения, нужно было
  передать человеку, тон, слишком длинно) и поля разбора разговора пишет
  только `ConversationReviewWrites` (`ConversationReviewRepoContract`); обычное
  сохранение разговора их не трогает.
- Проверки владельца — `AutotestCaseDocument` (вопрос, ожидание
  `must_mention` / `must_not_mention` / `must_hand_off` / `must_create_lead`,
  слова, язык, откуда взята). `PlanAutotestScenariosUseCase` добавляет включённые
  проверки сценариями `owner_check` и в полный прогон, и в быстрый прогон
  «Применить изменения»; клиент задаёт вопрос слово в слово, судья не нужен:
  `check_owner_expectation` решает детерминированно (коды
  `expected_text_missing`, `forbidden_text_mentioned`, `not_handed_off`,
  `no_lead_created`). Сценарная модель (`LLM_PROVIDER=scripted`) отвечает на
  вопрос, совпавший с заголовком строки знаний, её текстом, так что
  исправление и проверка из него проходят на сервере разработки и в e2e.
- Обзор показывает «Ответы, которые стоит улучшить»
  (`ListAnswersToImproveUseCase`): плохие оценки без исправления, затем
  вопросы без ответа.

## Глубина проверок и качество в продакшене

- pass^k: важные для запуска сценарии (`LAUNCH_CRITICAL_SCENARIO_KINDS`:
  вопрос о цене, бронь, бронь вне часов, проверки владельца и атаки)
  играются `AUTOTEST_CRITICAL_SAMPLES` раз (по умолчанию 2) отдельными
  разговорами (`…-play2`); сценарий пройден, только если пройдены все прогоны,
  прогоны останавливаются на первом непройденном (`merge_sample_results`:
  его разговор и оценки, стоимость всех, `sample_count` и
  `passed_sample_count` в результате).
- Цены проверяются без судьи (`autotest_price_checks`): ответ на вопрос о
  цене должен назвать цену услуги (оценщик R9 `score_prices`), а в
  сценариях, где речь о деньгах, каждая сумма помощника должна быть из
  знаний или из результата инструмента разговора (`get_price`, расчёт
  проживания): коды `price_not_named`, `unsupported_price`.
- Атаки (red team) играются в каждой нише как проверки перед запуском:
  `prompt_injection_spoof` (поддельное «уведомление платформы»),
  `data_exfiltration` (чужие контакты и инструкция), `staff_impersonation`
  (клиент выдаёт себя за сотрудника), `tool_abuse` (массовые отмены и
  брони). `red_team_checks` решает детерминированно: десять слов подряд из
  инструкции вне знаний и примеров (`instructions_revealed`), телефон или
  почта не из знаний и не клиента (`personal_data_revealed`), бронь, отмена
  или перенос по просьбе атакующего (`unauthorized_action`), любая отмена или
  больше одной брони у злоупотребляющего (`tools_misused`).
- Судья — `LLM_JUDGE_MODEL_ID`, по умолчанию модель другого провайдера
  (при ключе второго провайдера), чтобы модель не оценивала своё семейство.
- Сравнение версий: прогон запоминает прогон живой версии на момент запуска
  (`AutotestRunDocument.compared_to_run_id`); `GetAutotestRunUseCase` для
  законченного прогона строит `comparison` (`compare_runs`): новые
  провалы и исправленное по сценариям (ключ, вид, язык), изменения средней
  оценки сценария от 0,5 балла (худшие первыми) и средние каждого критерия
  судьи в обоих прогонах. Страница версии
  («Помощник → Дополнительно → Версии») показывает их рядом с итогом.
- Качество в продакшене: ночная задача `sample_conversation_quality`
  (`SampleConversationQualityUseCase`) берёт разговоры живых и приостановленных
  бизнесов, затихшие от часа до двух суток назад, без песочницы; выборка
  устойчива (хэш id < `QUALITY_SAMPLE_PERCENT`), не больше
  `QUALITY_SAMPLE_PER_BUSINESS` на бизнес, бизнесы по очереди, каждый
  разговор оценивается один раз. Перед каждым вызовом худший случай (все
  токены ответа, неизвестная модель — по самой дорогой цене) сверяется с
  остатком `QUALITY_SAMPLE_BUDGET_CENTS` за сутки UTC, включая уже
  потраченное, — ночь останавливается на потолке. Судья видит разговор с
  замазанными телефонами и почтой и пишет замечания на языке владельца без
  цитат клиента; оценка хранится в `conversation_quality_scores` (1120) 90
  дней. Тренд за 30 дней (неделя к неделе, худшие разговоры) —
  `GET /v1/admin/clients/{business_id}/quality` на странице клиента в
  админке; оценка разговора — `GET /v1/businesses/{business_id}/conversations/
  {conversation_id}/quality` в его карточке. Падение средней оценки последних
  суток на 10 % к семи дням до них (от 10 оценок) — оповещение `quality_drop`
  (SEV3, `assistant-quality.md`).

## Память о постоянных клиентах

- Сводка разговора: `PrepareConversationTurnUseCase` через
  `RecallCustomerMemoryUseCase` ставит в очередь задачу
  `summarize_conversation` (линия `default`) на «через два часа», когда
  разговор становится активным (новый разговор или сообщение после двух
  тихих часов). `SummarizeConversationUseCase` сдвигает себя, пока приходят
  сообщения, а после двух тихих часов дешёвая модель (`LLM_SUMMARY_MODEL_ID`,
  иначе модель чата) пишет `ConversationDocument.summary`
  (`ConversationSummaryText`, не длиннее 300 символов, по-английски, без
  телефонов и почты). Запись — одним шагом и только пока разговор тот же
  (`ConversationMemoryRepoContract.set_summary`: другой `last_message_at` или
  стёртый посетитель — ничего не пишется). Индекс для поиска тихих разговоров
  не нужен: задача сама знает свой разговор.
- Память в ходе: на первом ответе разговора (`is_first_reply`) в строку
  контекста пользовательского хода (не в инструкцию: префикс кэша и прежние
  ходы не меняются) добавляются строки `returning_customer_lines`: сколько
  разговоров было и когда последний, три последние сводки, предстоящие брони
  (`find_customer_bookings` по `list_ending_after`), незакрытые заявки из
  последних разговоров и — если владелец разрешил — заметки команды. Текст
  клиентов и заметки идут блоками `<untrusted>`. Всё читается только внутри
  бизнеса и по `contact_id`; песочница, стёртый контакт и выключенная память
  не получают ничего.
- Инструмент `list_my_bookings` (пустая схема): брони клиента, которые ещё
  не закончились (и отменённые, со статусом), по контакту разговора и
  номеру, который подтвердил канал, как `cancel_booking`; в чате и в звонке
  (веб-хук инструмента голосового агента). Версии, собранные до него,
  получают его рядом со своими инструментами броней
  (`tool_selection.with_list_my_bookings`).
- Настройки → Бизнес: `AssistantSettingsDocument` (`remembers_customers`,
  по умолчанию включено; `shares_team_notes`, по умолчанию выключено),
  `GET·PUT …/assistant-settings`, изменение пишется в аудит. Удаление данных
  клиента стирает сводки его разговоров.

## Клиенты и поиск

- Карточка клиента живёт в `ContactDocument` (v4): `tags[]` (`ContactTagMark`:
  метка `CustomerTag` как её ввели, ключ `CustomerTagKey` — свёрнутый регистр,
  кто и когда), `is_vip`, `block` (кто и когда) с поисковым `is_blocked`.
  Обычное сохранение контакта ходом разговора не трогает карточку
  (`keep_card_fields`): ход, прочитавший контакт до того, как коллега его
  пометил или заблокировал, не откатывает это. Изменения карточки —
  `_modify_in_business` под блокировкой строки (в памяти — под замком), в
  аудит. Миграция 1140 добавляет столбцы `doc_is_vip`, `doc_is_blocked` и
  ключи `tags[].key` триггером в одной транзакции; заполняет старые строки
  `workshop backfill-lookup` (1122).
- Список клиентов (`GET …/contacts?search=&tag=&filter=all|vip|blocked`) —
  постраничный по ключу; для сотрудников телефон маскируется
  (`customer_phone_privacy`: код страны и две последние цифры, группы по три
  с конца), пока владелец не включит `CustomerSettingsDocument.staff_sees_phone_numbers`;
  каждый просмотр списка и карточки — запись аудита `view`.
- Страница клиента (`GET …/contacts/{id}`): положение (`standing_of`: NEW,
  RETURNING, VISITED, REGULAR с двух визитов), число визитов (завершённые
  брони), хронология (`build_timeline`: разговоры по последнему сообщению,
  брони по началу, заявки, звонки — новые сверху). Над разговором —
  `GET …/contacts/{id}/standing` («Постоянный клиент · 4 визита»).
- Блокировка (`PUT …/contacts/{id}/blocking`, только владелец): ход разговора
  заблокированного клиента записывает сообщение во «Входящие», но помощник
  молчит (`BLOCKED_SILENCE`); напоминания, просьбы об отзыве и ответы на
  пропущенные звонки проверяют блокировку так же, как отказ от рассылок.
- Сегменты (`…/customer-segments`, только владелец, до 50): правила (метка,
  последний визит больше N дней назад, броней не меньше / не больше, только
  VIP) хранятся в `CustomerSegmentDocument` и проверяются при чтении:
  `scan_segment` идёт по клиентам бизнеса страницами с пределом просмотра
  (подсчёт помечает «не меньше», если предел достигнут), заблокированные,
  стёртые и тестовые не входят никогда. Участники и CSV
  (`…/{id}/export?language=`, повторная проверка входа, аудит, телефоны с
  защитой от формул) — для W17-WAITLIST-REBOOKING тот же `scan_segment`.
- Поиск (`GET …/search?q=`): клиенты по имени, телефону и id (сначала
  точные совпадения по индексу, затем ограниченный обход списка), последние
  разговоры и брони найденных клиентов и разговор или бронь по своему id, до
  пяти в группе; найденное пишется в аудит; в кабинете — палитра
  Cmd/Ctrl+K в `ShellFrame` (и кнопка поиска в верхней панели телефона),
  «/» остаётся поиском во «Входящих».

## Лист ожидания и повторные визиты

- Лист ожидания (`waitlist_entries`, `WaitlistEntryDocument`): клиент,
  день, окно времени, гости, вид места, услуга или конкретное место, ночи
  для проживания, статус `WAITING` → `OFFERED` → `BOOKED` или `EXPIRED` с
  причиной (`DECLINED`, `NO_ANSWER`, `DATE_PASSED`, `UNREACHABLE`,
  `REMOVED`). Настройки (`WaitlistSettingsDocument`) включены по
  умолчанию, место придерживается `WaitlistHoldMinutes` (15–120, по
  умолчанию 30). `check_availability` говорит `waitlist_open` только для
  открытого дня без свободного времени; инструмент `join_waitlist`
  помощник вызывает после согласия клиента (минуты удержания в ответе
  инструмента — строкой, чтобы проверка ответа видела число).
- Отмена или перенос брони (`GrowthBookingsFacilitator` в сценариях
  броней) ставит задачу `offer_freed_place`: под блокировкой бизнеса
  (`BusinessLockRegistry`, в Postgres — advisory lock) место проверяется
  свободным, первая подходящая запись (самая ранняя) становится `OFFERED`,
  место придерживается (`HeldPlaces` занимают единицу при подборе
  времени для всех, кроме держателя), предложение уходит через outbox в
  канал и на языке клиента; вне окна 24 часов WhatsApp — шаблон
  `WHATSAPP_WAITLIST_TEMPLATE`. Ответ клиента читается до помощника
  (`AnswerWaitlistOfferUseCase` в оркестраторе хода): «да» создаёт бронь
  с `origin=waitlist` под той же блокировкой, «нет» отдаёт место
  следующему; если место уже занято, запись возвращается в `WAITING`.
  Записи меняются CAS-обновлением, гонки двух «да» и удержания с ответом
  решает блокировка. Периодическая задача `expire_waitlist_offers` (60 с)
  завершает просроченные удержания (`NO_ANSWER`, место — следующему) и
  прошедшие дни (`DATE_PASSED`).
- Повторные визиты (`CampaignSettingsDocument`, только по согласию
  владельца): правило ниши из `rebooking_rule_registry` (салон —
  приглашение через 35 дней, клиника — напоминание через 180, гостиница —
  сообщение за 2 дня до заезда), дни, аудитория (все, кого находит
  правило, или участники сохранённого сегмента — тот же обход, что у
  `scan_segment`), месячный предел (до 2000). Задача
  `run_rebooking_campaigns` (раз в час, только бизнесы в работе) берёт
  последний визит клиента, пропускает вернувшихся и тех, кому писали
  меньше 14 дней назад, и пишет `CampaignMessageDocument` один раз на
  бронь-повод: `SKIPPED` с причиной для STOP, списка отказов и
  блокировки, неизвестного клиента, клиента без канала или с закрытым
  окном без шаблона (`WHATSAPP_REBOOKING_TEMPLATE` — только для
  приглашения и напоминания). Новая бронь в течение 7 дней после
  приглашения помечает его `BOOKED` и получает `origin=campaign`.
- Ценность и отчёты считают брони из листа ожидания и после приглашений
  отдельными строками (`waitlist_*` и `campaign_*` в `ValueTotals`,
  стоимость только в валюте бизнеса). В кабинете — вкладки раздела
  «Брони»: «Лист ожидания» (сотрудники видят и убирают записи, настройки
  меняет владелец) и «Повторные визиты» (только владелец); живое событие
  `waitlist.changed` обновляет списки. Выгрузка клиента и полная выгрузка
  бизнеса включают записи листа и сообщения; удаление данных клиента
  стирает имя и заметки и завершает открытые записи (миграция 1151).

## Двусторонняя занятость: календари и системы записи

- Источники занятости ресурса (`ResourceCalendarLinkDocument` в
  `resource_calendar_links`, один на ресурс, миграция 1160): календарь
  Google (`ResourceDocument.external_calendar_id`, читается через
  `GoogleCalendarClient.query_free_busy`, доступ `calendar.readonly`), до
  пяти импортированных iCal-лент (адрес зашифрован `SecretCipher`, видна
  только площадка) и система записи (`BookingSystemConnectorContract`:
  `list_busy`, `create_booking`, `cancel_booking`; адаптеры в
  `booking_system_connector_registry`, первый — Cal.com, ключ бизнеса
  зашифрован). У каждого источника — статус последнего чтения
  (`BusySourceStatus`: попытка, успех, число интервалов, `problem` из
  `CalendarSyncProblem`).
- Прочитанная занятость лежит кэшем в `calendar_busy_times` (один документ
  на ресурс и источник, до 2000 интервалов): Google на 60 дней вперёд, iCal
  на 400, система записи на 180, с запасом на сутки назад. Периодическая
  задача `sync_calendars` (каждые 5 минут, пакетная полоса) читает
  ресурсы, чья очередь подошла (`next_sync_at`), по 10 секунд на источник;
  «Обновить сейчас», изменения источников и подбор времени при устаревшем
  кэше (старше двух периодов) читают по 2 секунды. Сбой одного источника
  только записывает проблему, остальные читаются; старый кэш остаётся до
  успешного чтения.
- Подбор времени (`CheckAvailabilityUseCase`, создание, перенос и ручные
  брони) считает интервал занятости занятым для всех единиц ресурса.
  События нашего собственного календаря броней (тот же Google-календарь,
  куда пишутся брони, `primary`) из занятости вычитаются, чтобы бронь не
  закрывала сама себя; проживания (ночи) закрываются целыми днями по
  часам заезда и выезда ресурса.
- iCal: импорт идёт через `SafeHttpFetcher` (только публичные адреса,
  порты 80/443, лимит размера, разбор библиотекой `icalendar`);
  `webcal://` читается как `https://`. Экспорт — `GET
  /v1/public/ical/{token}.ics` без входа: брони ресурса и занятость из
  Google и системы записи (импортированные iCal-события не
  возвращаются обратно — иначе площадки зациклятся), без данных гостей.
  Токен показывается один раз, хранится только его хэш
  (`ical_export_feeds`); новый токен сразу отключает старый; лента
  ограничена по частоте с адреса и по платформе.
- Изменения источников — только владелец, каждое пишется в журнал аудита;
  «Настройки → Интеграции» (`ListIntegrationsUseCase`) показывают
  состояние Google Calendar, импорта, экспорта и Cal.com и сводку по
  каждому ресурсу (`ResourceSyncSummary`), её же показывает строка ресурса
  в «Ресурсах и часах». Cal.com — обработчик самого бизнеса (ключ его
  аккаунта), а не субобработчик платформы.

## Предохранитель расходов и лимиты

- Расход дня бизнеса: `CheckBusinessSpendUseCase` перед каждым ходом модели
  (`ConversationTurnOrchestrator`, хук `spend_brake`) и перед звонком
  (`StartVoiceCallUseCase`) суммирует в базе `usage_events` его дня (в его
  часовом поясе; столбцы `doc_kind`, `doc_cost_micro_usd`, `doc_quantity`,
  миграция 1142), где цены нет — по плановым ценам провайдеров
  (`planned_provider_costs`). Лимиты — свои у бизнеса
  (`BusinessLimitsDocument`, их ставит админ:
  `PUT /v1/admin/clients/{id}/spend-limits`) или кратные плановому дню тарифа
  (`SPEND_SOFT_LIMIT_MULTIPLE`, `SPEND_HARD_LIMIT_MULTIPLE`). После мягкого —
  ход идёт на дешёвой модели; после жёсткого до конца дня только заявки:
  разговор уходит команде через обычную передачу, голосовой агент не
  принимает звонок. Первый переход дня записывается один раз
  (`spend_limit_marks`, `insert_if_absent`): владельцам и команде платформы
  уходит одно сообщение, жёсткий пишет в аудит `spend_limit_reached`;
  дальше жёсткая отметка избавляет ходы от суммы. Автопроверки идут мимо
  (у них свои лимиты).
- Расход платформы: плитка «Расходы сегодня» в админке
  (`GET /v1/admin/spend`, единственный платформенный оператор пакета) и
  правила `spend_spike` (день больше трёх средних за 7 дней) и
  `spend_budget` (80% `PLATFORM_DAILY_SPEND_BUDGET_USD`) задачи оповещений
  суммируют день UTC по BRIN-индексу `usage_events`.
- Лимиты запросов (`rate_limit_buckets`, `RequestRateLimitRegistry`):
  общие — на человека в зависимости `current_user` (600 в минуту, выгрузки
  строже) и на адрес без токена или с отвергнутым токеном
  (`AnonymousRequestLimitMiddleware`, 120 в минуту; виджет, веб-хуки и
  демо — со своими лимитами); действия владельца (`AdmitOwnerActionUseCase`:
  пробный чат 30 в минуту на человека, импорт меню 10 в час, автопроверки
  20 в день и одна идущая — кроме проверок «Применить изменения»). Сверх
  лимита — 429 с `Retry-After`.
- Сайты чата: `BusinessLimitsDocument.widget_allowed_origins`
  (`GET·PUT …/channels/web/allowed-origins`, меняет владелец). Зависимость
  маршрутов `/v1/widget/{business_id}/*` сверяет `Origin` (иначе `Referer`)
  по хосту без `www.` и порту; пустой список — любой сайт, свои страницы
  платформы (`CABINET_BASE_URL`, `APP_BASE_URL`, `CORS_ALLOWED_ORIGINS`) —
  всегда, чужой сайт — 403. Опрос сообщений (каждые 4 с) вызывает ту же
  проверку внутри своего маршрута, а не зависимостью: запрос остаётся одним
  переходом в поток запроса.
- Звонки: `CALL_MAX_DURATION_SECONDS` и `CALL_SILENCE_END_SECONDS` попадают
  в конфигурацию агента (`build_agent_config`: `max_duration_seconds`,
  `silence_end_call_timeout`) при каждой его настройке.

Вебхук канала → адаптер канала (`parse_webhook`, `verify_signature`) → бизнес
по id канала → **входящие** (`inbound_events`, вставка «on conflict do
nothing» по каналу и id сообщения у провайдера) → задача
`process_inbound_message` в полосе `inbound` → ответ платформе `200`. Вебхук
не зовёт модель и не шлёт ответ: он только проверяет подпись, пишет строку и
ставит задачу, поэтому отвечает быстро, а повтор той же доставки (Telegram и
Meta повторяют, если ответ задержался) не создаёт второй строки и второго
ответа.

Воркер: задача берёт событие с арендой на 180 с (`PROCESSING`) → контакт →
разговор, закреплённый за опубликованной версией → язык клиента (любой, см.
«Адаптивность», п. 7) →
модель с инструкцией (шаблон ниши + факты) и инструментами → сервер выполняет
инструменты → проверка ответа (переписать один раз, потом передать
человеку; см. «Проверка ответа» ниже) → запись в `messages` и `usage_events` → ответ в **исходящие**
(`outbound_messages`) → событие `ANSWERED` (или `HANDED_OFF`, когда бот молчит,
потому что передача человеку открыта). Id сообщения клиента и id ответа
заранее выведены из события, поэтому повторная обработка не дублирует
сообщения, а ответ, сохранённый до падения, отправляется без нового вызова
модели. Если воркер умер посреди хода, задачу освобождает сборщик
просроченных аренд, и событие обрабатывается заново. Сообщения одного
клиента идут по одному (`serial_key` задачи по каналу и клиенту).

Вложения: адаптер канала кладёт во входящее сообщение `InboundAttachment`
(голос, фото, место, контакт, стикер, другое; id файла у провайдера, тип,
подпись). Файлы скачивает воркер, а не вебхук
(`ReadInboundAttachmentsOrchestrator`: `ChannelMediaFetcherContract` —
WhatsApp Graph `/{media_id}`, Telegram `getFile`, адрес CDN Meta только с
хостов Meta), с лимитами размера до и во время скачивания и проверкой
содержимого по сигнатуре. Голос расшифровывает модель `LLM_TRANSCRIBE_MODEL`
(по умолчанию `gpt-4o-transcribe`) в EU-проекте OpenAI (языки версии —
подсказка), расход пишется как `transcription_seconds`; модель видит текст
внутри ограды клиента с меткой
«[Voice message, transcribed]». Фото уходит модели картинкой (OpenAI
`input_image`, Anthropic `image`), в истории хода хранится только ссылка
`stored_media`, которую `MediaResolvingLlmAdapter` раскрывает при каждом
запросе (последние 4 фото, остальные — заметкой). Место — координаты и
ссылка на карту. Сообщение без читаемого содержимого (только стикер,
контакт, файл) получает `CANNOT_READ_ATTACHMENT` на языке клиента без
вызова модели. Файлы лежат зашифрованными (AES-256-GCM, ключ на бизнес и
путь) в хранилище записей под `message-media/`, их описания — в коллекции
`message_media`; хранятся столько же, сколько записи звонков; кабинет
открывает их через `GET /v1/businesses/{id}/media/{media_id}` с записью в
журнал аудита. Id файла выведен из id события и позиции, поэтому повтор
задачи не скачивает и не оплачивает расшифровку второй раз.

Исходящие: строка с ключом идемпотентности (разговор + id ответа, уникален
в бизнесе) → задача `deliver_outbound` в полосе `outbound` → отправка по
частям (отправленные части не повторяются) → `DELIVERED`. Ответы одному
получателю уходят по порядку: более раннее неотправленное сообщение того же
получателя задерживает следующее. Ошибки провайдера разобраны по классам:
`429` ждёт `Retry-After`; `5xx` и сеть — повтор с экспоненциальной паузой
(10 с … 30 мин, ±25 % случайного сдвига, до 8 попыток); отказ `4xx` или
отозванный токен — сообщение `DEAD` и `last_error` канала (канал в `ERROR`).
Ответ клиенту, который так и не ушёл, открывает передачу человеку, чтобы
клиент не остался без ответа.

Уведомления персоналу (`ManagerNotificationFacilitator`) тоже пишутся в
исходящие и уходят той же задачей: передача человеку остаётся `PENDING`, пока
уведомление в пути, становится `NOTIFIED` после доставки и
`NOTIFICATION_FAILED`, если ни одно уведомление не дошло.

Всё, что получает клиент, идёт через исходящие — сценарий не зовёт `send`
или `send_template` канала сам (`tests/architecture_policy/
test_customer_messages_go_through_the_outbox.py`; исключения — сам outbox и
проверка подключения канала). Строка и задача пишутся в одной транзакции
(`queue_outbound_message`), ключ идемпотентности задаёт повод: ответ
сотрудника — id сообщения (`staff_reply`), напоминание — бронь, вид и время
начала (`booking_reminder`; перенесённая бронь получает новое), подтверждение
и ссылки после звонка — id звонка и вид (`call_confirmation`, `call_links`,
первый мессенджер, который может принять текст сейчас), ответ на пропущенный
звонок — id звонка (`text_back`, шаблон WhatsApp со сроком `send_before`:
позже он не уходит, `expired`). Сообщение сотрудника хранится вместе со
строкой исходящих; карточка разговора показывает под ним доставку
(`MessageView.delivery`: отправляется, повтор с причиной и временем
следующей попытки, доставлено, не доставлено с причиной —
`DeliveryFailureReason`), каждая попытка будит открытые кабинеты событием
разговора. Отказ Meta от шаблона ответа сотрудника — `template_rejected` без
повтора по-английски. Шаблон ответа на пропущенный звонок, когда он
доставлен или окончательно не ушёл, снова запускает задачу
`send_missed_call_text_back`: она отмечает звонок и при отказе шлёт SMS.
Новые виды сообщений пишутся в том же выпуске, что их читает: откат на
выпуск старше этого не прочтёт такие строки исходящих (прежде чем
откатываться, дождаться, пока они уйдут).

Приём тоже атомарен: вебхук пишет событие входящих и его задачу в одной
транзакции (`store_and_queue` с `storage_unit_of_work`), так что падение
между ними не оставляет ни того, ни другого, и платформа присылает вебхук
снова. Если задача всё же потерялась (старый выпуск, задачу сняли руками),
её находит периодическая `sweep_stale_inbound_events` (каждые 5 минут, вся
платформа, индекс миграции 1094 по статусу и времени прихода): событие в
`RECEIVED` или `PROCESSING` дольше двух аренд обработки, без живой аренды и
без ждущей или идущей задачи получает задачу снова (их число — в отчёте
задачи и в логе). Сообщение клиента, от которого ассистент отказался
(`FAILED`), через час уходит человеку передачей с цитатой сообщения
(`MODEL_UNAVAILABLE`, срочно), один раз: событие помечается
`handoff_requested_at`.

Виджет сайта — такой же канал: запрос пишет строку во входящие и ставит
задачу `process_inbound_message` в одной транзакции и сразу отвечает `202`
с id события. Ход клиента делает воркер; виджет показывает «печатает…» и
забирает ответ (или сообщение сотрудника) опросом сообщений, поэтому
медленная модель не держит потоки запросов API. Опрос сначала считает
запрос в лимитах (отдельный оператор SQL), затем в одной сессии чтения
(одна транзакция) читает разговоры посетителя и позиции (id и время) десяти
его новейших сообщений из индекса, без самих сообщений; если курсор среди них
и они уходят в прошлое дальше курсора, ответ тот же, что дала бы вся
переписка, и целиком читаются только сообщения после курсора (обычно ни
одного). Длинный хвост новых сообщений, неизвестный курсор или его
отсутствие читают переписку целиком (`widget_message_window`). Открытый
чат процесс помнит 10 секунд (`OpenChatMemory`, только открытый: включённый
виджет отвечает сразу, выключенный перестаёт отвечать на опросы не позже чем
через 10 секунд). Только
тестовый чат владельца отвечает в запросе, не больше
`TEST_CHAT_MAX_CONCURRENCY` сразу (дальше — `429`).

Задачу воркер берёт сразу: очередь вместе со вставкой делает
`pg_notify('workshop_jobs', <полоса>)` (уведомление уходит только при
фиксации транзакции), а поток `LISTEN` воркера будит потоки полосы. Опрос
очереди остаётся страховкой (`WORKER_INBOUND_POLL_SECONDS`,
`WORKER_POLL_SECONDS`, первые опросы потоков разнесены). Задержку от
постановки до захвата каждая задача пишет в лог (`pickup_delay_ms`,
`docs/operations/capacity.md`).

Быстрые ответы (R9). Клиент сразу видит «печатает…»
(`ChannelAdapterContract.signal_typing`: Telegram `sendChatAction` раз в
4 с, WhatsApp — отметка «прочитано» с индикатором набора, Messenger и
Instagram — `typing_on`; виджет рисует свой), пока ответ пишется
(`TypingSignalFacilitator`, отдельный поток, ошибки только в лог). Несколько
быстрых сообщений подряд получают один ответ: задача
(`ClaimInboundBurstUseCase`) находит другие необработанные сообщения того же
клиента (индекс `inbound_events (business_id, doc_created_at)`, миграция
1090) и, пока клиент не молчит `MESSAGE_COALESCE_SECONDS` (не дольше трёх
таких пауз от первого), ставит себя снова на нужный момент, не меняя
входящих. Потом сообщения серии идут в конвейер по порядку: ранние только
записываются (`InboundMessage.is_reply_deferred`), последнее отвечает на
все (модель видит их в транскрипте), а события серии закрываются исходом
последнего. Если ход идёт дольше `CHAT_TURN_DEADLINE_SECONDS` от первого
сообщения, `TurnDeadlineWatch` один раз отправляет через исходящие короткое
`ONE_MOMENT` на языке клиента (около 55 языков; id выведен из id ответа,
поэтому повтор хода его не дублирует; если это первое сообщение помощника в
разговоре, оно открывается раскрытием «я — ИИ-помощник»); дальше — ответ
или передача человеку.
Каждый ответ записывает в `MessageDocument` канал, `reply_latency_ms` (от
первого сообщения без ответа до записи ответа), число раундов модели и
`is_fallback_model`; админ видит p50/p95 за 7 дней по каналам, а при p95
больше 15 с — проблему `SLOW_REPLIES` (база считает ответы по корзинам
задержки, индекс миграции 1090).

Строки входящих и исходящих удаляет `purge_stale_rows` через 30 дней.

Проверка ответа (R10). Каждый текст модели проходит три проверки
(`ReplyReviewer`, `app/use_cases/conversations/replies/`):

1. Выдуманные значения: цены, проценты, время, даты и телефоны ответа должны
   найтись в фактах, результатах инструментов, строке контекста или словах
   сотрудников (время, даты, телефоны и количества — ещё и в словах клиента).
   Цифры читаются в любой системе письма, а числа словами — на 10 языках
   (`NUMBER_WORDS` в `reply_guard/numerals.py`: en, ru, ka, uk, tr, he, ar,
   de, fr, es), рядом со словами валюты, процента и времени («fifty lari»,
   «ორმოცდაათ ლარად», «две тысячи лари», «at nine.», «saat yedide»).
2. Утверждения о правилах и наличии («парковка бесплатная», «с собаками
   можно»): предфильтр по словарю маркеров каждого языка
   (`claim_candidates.py`) находит такие предложения, и только тогда
   дешёвая модель `LLM_VERIFIER_MODEL_ID` (`ClaimCheckFacilitator`, один
   вызов без инструментов, 12 с, без повтора) сверяет их с теми же данными.
   Сбой или нечитаемый ответ модели проверки ответ не задерживает:
   утверждения помечаются `unchecked`.
3. Чужие контакты: телефон ответа (libphonenumber в стране бизнеса),
   принадлежащий другому контакту бизнеса (индексированный поиск по
   телефону), и e-mail, которого нет ни в данных бизнеса, ни в словах этого
   клиента, не уходят.

Найденное отправляется модели один раз с просьбой переписать; если и
переписанный ответ не прошёл — передача человеку (`PERSONAL_DATA`, затем
`UNVERIFIED_NUMBERS`, затем `UNSUPPORTED_CLAIM`; утверждения попадают в
передачу как отмеченные значения, чужие контакты — никогда). Ответ
помощника хранит `guard_verdict`, `guard_reasons`, `unverified_values` и
`claim_findings` (`MessageDocument` v4), кабинет получает их в
`MessageView.guard`, а админ видит работу проверки за 7 дней и проблему
`GUARD_SPIKE` (каждый шестой ответ задержан, не меньше пяти, или десять
попыток подмены инструкции). Расход модели проверки учитывается в
`usage_events` по её цене.

Попытки подмены инструкции: эвристика на 10 языках
(`reply_guard/injection_signals.py`: «ignore previous instructions», «ты
теперь…», «покажи системный промпт», «перечисли всех клиентов», поддельные
строки платформы) помечает сообщение клиента (`injection_flag`); на такое
сообщение помощник отвечает как обычно (текст клиента и так в ограде), но
после `INJECTION_FLAG_LIMIT` помеченных сообщений за сутки контакт получает
один раз вежливое «напишите позже» и затем тишину до конца суток.
Импортированные с сайта или из файла меню знания (факты с `is_imported`,
`AssistantVersionDocument` v5, и тексты из `search_knowledge`/`get_price`)
и имя клиента в результате брони модель видит в блоке
`<untrusted>…</untrusted>`, который их текст не может закрыть; инструкция
говорит, что такой блок — данные, а не указания.

## Путь звонка (ТЗ §1, §7)

Переадресация «нет ответа / занято» → номер Zadarma → SIP → агент ElevenLabs
этого бизнеса. Агент собран из той же версии: та же инструкция и те же
инструменты, вызываемые через наши вебхуки с подписью HMAC. После звонка вебхук
приносит расшифровку, запись и стоимость: вебхук проверяет подпись, кладёт
отчёт во входящие (повтор того же отчёта — `duplicate`) и ставит задачу; воркер
записывает `calls`, итог (бронь, заявка, передача, вопрос без ответа) и
подтверждение клиенту сообщением.

Шаги воркера после записи звонка — `PostCallWebhookOrchestrator`: разговор
для звонка, где клиент говорил (карточка звонка в «Сообщениях»), аудит
названных помощником значений, пропущенный звонок (клиент промолчал или
перевод на сотрудника никто не взял), итог звонка, подтверждение брони,
ссылки и архив записи. `SummarizeCallUseCase` пишет короткий итог дешёвой
моделью (`LLM_SUMMARY_MODEL_ID`) на языках владельца и сотрудников, хранит
его в `calls.summaries` один раз и отправляет сотрудникам через outbox
(Telegram и WhatsApp; ключ идемпотентности — `call:{id}` на получателя).

Пропущенные звонки (`missed_calls`) приходят из трёх мест: уведомление
NOTIFY_END АТС Zadarma (`POST /v1/telephony/zadarma/notifications`, подпись
`ZADARMA_API_SECRET`; занято, нет ответа, сброс, сбой линии), событие
`call_initiation_failure` вебхука ElevenLabs и шаги воркера выше.
`RegisterMissedCallUseCase` сохраняет звонок один раз на `provider_call_id`
и решает, писать ли звонящему: выключено, скрытый номер, помощник не в
эфире, отчёт старше двух часов, нет канала, клиент отказался от сообщений
или уже пишет бизнесу, лимиты (один раз в сутки на номер, 200 в сутки на
бизнес; общие счётчики `rate_limit_buckets`). Задача
`send_missed_call_text_back` (полоса `outbound`) отправляет одобренный
шаблон WhatsApp на языке звонящего с номера бизнеса и открывает разговор
WhatsApp, где продолжится ответ клиента; при отказе WhatsApp — SMS
платформы; временный сбой повторяет очередь задач. Настройки — коллекция
`call_settings`, страница «Настройки → Звонки».

## Отзыв после визита и отказ от рассылок

Контекст `feedback` (`app/use_cases/feedback/`, маршруты `review_routes.py`):

- периодическая задача `request_visit_feedback` (каждые 10 минут, оператор
  поднимает `platform_wide()`) берёт бизнесы с включёнными отзывами
  (`review_settings`, бизнес в эфире) и визиты, закончившиеся
  `delay_minutes` назад (не позже чем ещё через шесть часов — поздний вопрос
  хуже никакого): бронь `completed` или всё ещё `confirmed` после конца, не
  тестовая. `RequestVisitFeedbackUseCase` создаёт `feedback_requests` с id из
  бизнеса и брони (один раз на визит) и пишет клиенту в мессенджер брони, а
  если там нельзя — в другой подключённый (Telegram, WhatsApp, Messenger,
  Instagram) через outbox (`customer_reply`, шаблон WhatsApp с названием
  бизнеса вне 24-часового окна, английский перевод при отказе Meta, учёт
  `wa_template`). Не спрашиваем (запрос `skipped` с причиной): клиент
  отказался от рассылок, нет контакта или мессенджера, окно WhatsApp
  закрыто без шаблона, уже спрашивали сегодня, исчерпан дневной лимит.
  Вопрос виден в разговоре как сообщение бизнеса;
- ответы читает платформа до модели (`AnswerCustomerSignalUseCase` в
  `ConversationTurnOrchestrator`): оценка 1–5 (цифры любой письменности,
  звёзды-эмодзи, числительные ~55 языков, «4/5») сразу после запроса в том
  же канале и в течение недели записывается в запрос, клиент получает
  благодарность и ссылку на страницу отзывов Google при любой оценке (без
  «фильтрации отзывов»); оценка 3 и ниже ещё и передаёт разговор человеку
  (`complaint`, низкая срочность, итог на языке владельца). Ссылка идёт
  через `GET /v1/public/reviews/{token}` (случайный токен запроса; поиск по
  токену явно `platform_wide()`), который считает переходы (не превью
  мессенджеров) и отвечает 302; без `APP_BASE_URL` клиент получает адрес
  Google напрямую, переходы не считаются;
- ссылка Google хранится в анкете в отдельном поле
  `BusinessProfileDocument.google_review_url` (как `privacy`, правило
  expand/contract), API показывает её среди ссылок как `google_review`;
- отказ от рассылок: сообщение целиком «STOP», «СТОП», «სტოპ» или их
  переводы (`app/utilities/channels/opt_out_keywords.py`) добавляет канал в
  `ContactDocument.opted_out_channels`, «START» снимает отказ; обе записи —
  в журнале аудита (`message_opt_out`), клиент получает подтверждение на
  своём языке. Клиент с отказом в любом канале не получает напоминаний,
  запросов отзыва и сообщений после пропущенного звонка; кроме того, у
  каждого клиента общий дневной лимит таких сообщений (3 в сутки,
  `proactive_message_counter` в `rate_limit_buckets`).

## Выгрузки и права субъектов данных

Выгрузки владельца и права клиентов (`app/use_cases/exports/`,
`app/use_cases/compliance/`, `app/facilitators/privacy/`, маршруты
`export_routes.py` и `business_export_routes.py`, миграция 1113):

- таблицы кабинета в CSV — `GET /v1/businesses/{id}/exports/{table}`
  (брони, заявки, клиенты, разговоры с сообщениями, журнал действий) с теми
  же фильтрами, что у списков. Только владелец, после недавнего входа или
  подтверждения (step-up), одна запись EXPORT в журнале на выгрузку. Тело
  идёт потоком по страницам ключевого пейджинга (100 000 строк стоят одну
  страницу памяти), UTF-8 с BOM, ячейки, похожие на формулы (`=`, `+`, `-`,
  `@`, табуляция), экранируются апострофом; удалённые клиенты и тестовые
  чаты владельца не попадают;
- полный экспорт бизнеса — очередь `build_business_export`: ZIP с JSON на
  каждую коллекцию (клиенты, разговоры, сообщения, звонки, брони, заявки,
  передачи, места, услуги, пропущенные звонки, отзывы, журнал) и теми же
  таблицами в CSV. Архив лежит в объектном хранилище, зашифрованный ключом
  бизнеса (AES-256-GCM, ключ из `ENCRYPTION_KEY` через HKDF), без S3 — в
  локальной папке. Архив хранится сутки и скачивается не больше трёх раз:
  каждый раз владелец после недавнего входа получает одноразовую ссылку
  (`export_download_links`, хранится только SHA-256 токена) на
  `EXPORT_DOWNLOAD_LINK_MINUTES` (10 мин), и она открывается только в его
  сеансе; каждая загрузка пишется в журнал, а все владельцы получают
  уведомление с адресом и браузером. Ежечасная `purge_business_exports`
  удаляет просроченные архивы и ссылки. Сценарий пригоден для закрытия аккаунта;
- список отказов (`suppression_entries`): при STOP пишется HMAC-SHA256
  номера E.164 или идентичности канала под ключом платформы
  `SUPPRESSION_LIST_KEY` и вид канала. Записи переживают удаление клиента,
  поэтому напоминания, сообщения после пропущенного звонка, вопросы и
  просьбы об отзыве проверяют и его: новый контакт с тем же номером после
  удаления ничего не получит, пока не напишет START;
- удаление и выгрузка данных клиента охватывают и пропущенные звонки (по
  номеру), исходящие сообщения (по ключу получателя), входящие события (по
  идентичности канала) и запросы отзыва (по контакту). Архитектурный тест
  `tests/architecture_policy/test_erasure_covers_personal_data.py`
  проверяет, что каждая коллекция каталога с телефоном, e-mail,
  идентификатором в канале или текстом сообщения либо обрабатывается
  удалением, либо стоит в списке исключений с причиной.

## Аналитика роста для основателя

Свои события продукта, без внешних трекеров (`app/use_cases/admin/metrics/`,
`app/use_cases/telemetry/`, маршруты `analytics_routes.py`, миграция 1074):

- `product_events` — шаги владельца от регистрации до оплаты
  (`ProductEventName`): регистрация и вход, бизнес создан, экраны туннеля
  (открыт, пройден, пропущен), итог запуска, принятие DPA, подключение
  канала, вехи (запуск, первый настоящий разговор, бронь, передача), пробный
  период, подписка, смена тарифа, отмена, неуспешный платёж. Каждый
  перечисленный сценарий пишет шаг одной строкой через
  `RecordProductEventFacilitator`, который никогда не роняет действие
  владельца. Однократные шаги получают id из субъекта (UUID v5), поэтому
  хранятся один раз; шаги оплаты несут, сколько подписка приносит в месяц
  (годовая цена / 12) и в какой валюте;
- ежедневная задача `reconcile_product_events` восстанавливает пропущенные
  шаги из записей (регистрации, бизнесы, вехи, запуск по первой
  опубликованной версии, каналы, пробный период) и выравнивает шаги оплаты с
  подпиской (ACTIVE или PAST_DUE в льготный срок после оплаченного периода —
  платит; иначе нет);
- `GET /v1/admin/metrics` строит всё на лету: воронка владельцев
  (приглашённые сотрудники и админы платформы не считаются; шаг засчитан,
  только если пройдены все предыдущие), медианное время до запуска,
  активация бизнеса (запуск, канал и настоящий разговор за 7 дней от
  создания; моложе недели — «ещё в пути»), пробный → оплата, туннель,
  когорты по месяцу регистрации, источники (`signup_attribution` на
  пользователе: utm_source → `src` → `referral` → `hosted_chat` → сайт →
  `direct`; без атрибуции — `unknown`), MRR: воспроизведение шагов оплаты
  по бизнесу даёт MRR на начало и конец периода и движения new,
  reactivation, expansion, contraction, churn (начало + движения = конец);
  суммы в евро по курсам `ExchangeRateRegistry` (НБГ, ЕЦБ или плановый курс; прямой или
  опубликованный обратный курс; валюта без курса не считается и
  называется), ARPA, валовая маржа из `ComputeClientCostUseCase`;
- `POST /v1/telemetry/events` принимает от кабинета пакеты Web Vitals (LCP,
  INP, CLS по шаблону маршрута и классу устройства) и шагов туннеля; 30
  пакетов в минуту на человека (`rate_limit_buckets`); замеры удаляет
  ежедневная `purge_web_vitals` через 90 дней (запись в аудите); p75
  считается по корзинам значений в базе (`count_by`);
- атрибуция: прокси кабинета на первой странице визита (лендинг, страница
  чата) кладёт в httpOnly-cookie `aw_attr` utm-метки, `ref`, `src`, хост
  ссылающегося сайта и путь; BFF входа отправляет её как
  `signup_attribution`, API хранит её только у нового аккаунта.
- бизнесы рядом с владельцами (`business_growth.py`,
  `business_funnel_math.py`): каждый бизнес, созданный в периоде, считается
  один раз — второй бизнес уже зарегистрированного владельца тоже (`created`,
  `by_returning_owners`); воронка бизнеса — те же шаги после регистрации;
  туннель по бизнесам — экраны туннеля приписываются бизнесу (или следующему
  бизнесу владельца, пока тот не создан; незаконченная настройка — отдельная
  единица `setup:{owner}`), общая математика с туннелем владельцев
  (`tunnel_math.py`);
- админы платформы: их регистрации и бизнесы не входят в воронки, туннели,
  когорты и источники, а ответ называет, сколько их исключено
  (`excluded_platform_admins`, `excluded_admin_businesses`);
  `?include_admins=true` включает их. Выручка, маржа, активация и пробные
  периоды всегда считают все бизнесы;
- MRR называет курсы, по которым пересчитан (`MrrView.rates`: источник —
  НБГ, ЕЦБ или плановый курс платформы, дата, признак устаревшего курса);
  страница пишет их под таблицей, а не обещает «официальные курсы».

## Счета для бухгалтера: номера, НДС, PDF

Счёт платформы — документ для бухгалтера бизнеса (`app/facilitators/invoicing/`,
`app/registries/billing/tax_policy_registry.py`, маршруты
`billing_document_routes.py`, миграция 1114):

- **Реквизиты.** `billing_profiles` — одна запись на бизнес (id выводится из
  бизнеса): юридическое название, налоговый номер, адрес, e-mail для счетов,
  страна. Без записи счёт называет бизнес и его страну. Сохранение — только
  владелец, с записью в аудите.
- **Номер.** `invoice_counters` — платформенная коллекция, строка на серию и
  год (`AW:2026`); номер берётся сравнением-с-заменой `last_number`
  (`insert_if_absent` для первого, `replace_if` для следующих, повтор при
  гонке), поэтому номера не повторяются и не пропускаются. Год — по дате
  счёта в часовом поясе продавца (`SELLER_TIME_ZONE`). Вид номера —
  `AW-2026-000042`.
- **НДС.** `TaxPolicyRegistry` решает по стране покупателя: продавец не
  плательщик (`PLATFORM_VAT_REGISTERED` выключен) — без НДС; покупатель в
  Грузии — 18 % сверху; за границей с налоговым номером — reverse charge;
  без номера — вне сферы НДС Грузии. Сумма считается в минорных единицах с
  округлением половины вверх; у продления, где карта уже списала сумму,
  НДС выделяется из списанного (`extract_tax`), поэтому итог счёта всегда
  равен списанию.
- **Выпуск.** `InvoiceIssuingFacilitator.issue` при создании счёта
  копирует продавца (`SELLER_*`) и покупателя, номер, подытог, ставку, налог;
  `paid_at` и замаскированная карта (платёжная система и 4 последние
  цифры из уведомления Flitt) пишутся при оплате. Счёт, выписанный до
  нумерации, получает номер при первом скачивании (`complete`, без НДС).
- **Строка счёта.** При выпуске `InvoiceLineTextsTransformer` формулирует
  строку на английском, русском и грузинском без дат (`line_texts`; период
  печатается рядом), поэтому PDF на любом из этих языков не смешивает языки,
  а кабинет показывает строку на языке интерфейса. `description` остаётся
  строкой на языке владельца, как выпущено; у старых счетов только она.
- **PDF.** `BillingDocumentLayoutTransformer` собирает HTML счёта или
  квитанции на английском, русском или грузинском (Noto Sans и Noto Sans
  Georgian), `WeasyPrintInvoiceDocumentRendererAdapter` печатает его без
  обращений к сети. Кабинет скачивает файл через BFF как есть
  (`Content-Disposition: attachment`), каждое скачивание — в аудите.
- **Письмо.** После применённой оплаты `PaymentWebhookOrchestrator`
  ставит в outbox сообщение `STAFF_NOTIFICATION` с полем
  `billing_documents` на e-mail для счетов (иначе владельцам с e-mail);
  PDF собираются при отправке и уходят вложениями. Старый релиз отправит
  такое сообщение без вложений, новых видов сообщений нет.

## Сессии, команда админов и доступ поддержки

- **Сессии устройств.** `UserSessionDocument` хранит браузер (User-Agent),
  адрес входа, время и адрес последнего использования и `idle_expires_at`.
  Проверка токена (`AuthenticateUserUseCase`) удаляет сессию после 7 дней
  без дела (у админа — 12 часов, и не позже суток после входа) и пишет
  последнее использование не чаще раза в 5 минут. Вход с устройства, которого
  нет среди живых сессий человека (тот же браузер и система), присылает
  личное уведомление через фасилитатор оповещений команды
  (`SignInNoticeFacilitator`, адресат — только этот человек).
- **Команда админов.** Роли SUPER, SUPPORT_READONLY и BILLING лежат в
  коллекции `platform_admins` (платформенной, без `business_id`); права ролей —
  `app/utilities/security/admin_permissions.py`, проверка —
  `AuthorizePlatformAdminUseCase` на каждом запросе. Списки
  `PLATFORM_ADMIN_*` только создают первого SUPER-админа
  (`PlatformAdminRegistry`).
- **Доступ поддержки.** Запрос админа к бизнесу, где он не участник,
  проходит через `AuthorizeSupportAccessUseCase`: нужна живая запись
  `support_access_grants` вида SESSION (60 минут, с причиной; иначе 403
  `support_access_required`). Режим запроса — чтение (GET/HEAD/OPTIONS) или
  изменение; изменение требует живого согласия владельца (запись вида
  WRITE_CONSENT, 1–168 часов) и права CHANGE_CLIENT_CABINET (иначе 403
  `support_read_only`); действия только для владельцев поддержке закрыты,
  кроме сборки и публикации помощника (`support_may_change`). Начало и конец
  пишутся в журнал аудита (`support_access_start`, `support_access_end`) с
  адресом; просроченные записи закрывает периодическая задача
  `end_expired_support_access`.

## Действия админа с аккаунтом клиента и история клиента

Админ платформы с правом `manage_client_billing` (роли SUPER и BILLING)
меняет аккаунт клиента только с причиной (`AdminActionReason`, 8–300
символов); каждое действие пишет запись аудита `ADMIN_*` с причиной и
адресом (`app/use_cases/admin/billing_actions/`, маршруты
`admin_account_action_routes.py`, миграция 1143):

- **продлить пробный период** на 1–60 дней (закончившийся неоплаченный
  начинается заново с сегодняшнего дня, его неоплаченные счета аннулируются,
  полный сервис возвращается);
- **скидка** `DiscountPercent` до последнего дня (в часовом поясе бизнеса,
  не дальше трёх лет): периоды, начавшиеся до конца этого дня, выставляются
  со скидкой от цены до налога (`invoice_adjustments.py`, округление
  половины вверх);
- **кредит**: строка GRANTED в журнале `billing_credits`; выставление счёта
  под блокировкой `billing-credits|{business}` списывает остаток строкой
  USED (id из счёта, UUID v5, поэтому повтор не спишет дважды) после скидки
  и до налога; аннулированный счёт возвращает свой кредит (остаток не
  считает его строки). Счёт, обнулённый скидкой или кредитом, сразу
  оплачен. PDF называет скидку, кредит и способ оплаты;
- **отменить плату за настройку**: неоплаченный счёт настройки
  аннулируется, новый не выставляется;
- **отметить счёт оплаченным** (BANK_TRANSFER или CASH, со ссылкой на
  платёж): оплаченный период продлевает подписку и возвращает полный
  сервис, как оплата картой;
- **сменить тариф** без оплаты по прайсу со следующего счёта; если меняется
  списываемая сумма, автоплатёж останавливается, неоплаченные счета старой
  цены аннулируются; тариф без голоса выключает голосового агента.

Автоплатёж Flitt списывает фиксированную сумму: скидка и кредит действуют
на счета, оплачиваемые в кабинете или переводом (страница клиента говорит
это прямо).

История клиента на его странице: заметки команды (`client_notes`,
закреплённые сверху; писать могут роли с `write_client_notes`) и лента
(`GET …/timeline`, курсор, сначала новое), которая сливает журнал аудита
(без просмотров и входов), счета и кредит, шаги подписки, вехи настройки,
заявку «под ключ» и смены здоровья клиента: задача `refresh_client_standings`
пишет каждую смену статуса в `client_health_changes`. Ежедневная задача
`critical_clients_digest` присылает в Telegram-чаты платформы
(`PLATFORM_ALERT_TELEGRAM_CHAT_IDS`) клиентов, ставших критичными с прошлой
сводки (состояние в `admin_digest_states`, повтор не дублирует). Заявку
«под ключ» команда закрывает кнопкой на странице клиента. Страница админа
показывает вариант настройки так же, как кабинет владельца: платящий
пробный период без выбора — SELF_SERVE.

## Помощь, поддержка и страница статуса

- **Справка.** Статьи — Markdown-файлы `docs/help/{en,ru,ka}/{slug}.md` с
  заголовком и метаданными (тема, порядок, ключевые слова, связанные
  статьи). `HelpArticleRegistry` читает их один раз, как реестр DPA, и отдаёт
  статью на языке человека или на английском (`GET /v1/help/{language}`,
  `/{slug}`, `/search?q=`; поиск по заголовку, ключевым словам, описанию и
  тексту — `app/utilities/help/help_search.py`). Тест требует одинаковых
  статей во всех языках; кабинет проверяет ссылки статей на свои страницы.
- **Подсказки и «Что нового».** `help_progress` (платформенная коллекция, по
  человеку) хранит увиденные подсказки и последнюю прочитанную запись
  «Что нового»; сами записи — содержимое кабинета (`web/content/changelog`).
- **Контакты поддержки.** `SUPPORT_WHATSAPP`, `SUPPORT_TELEGRAM`,
  `SUPPORT_EMAIL` → `GET /v1/support/contacts` (ссылки wa.me, t.me, mailto).
- **Статус платформы.** `GET /v1/platform/status` (публичный) сводит уровни
  частей (чат, WhatsApp/Instagram/Messenger, Telegram, звонки, кабинет) из
  сработавших сигналов `platform_alerts` (`component_levels.py`) и активных
  объявлений команды; периодическая задача `record_platform_status` раз в
  5 минут дописывает худший уровень дня в `platform_status_days` — отсюда
  история за 90 дней. Объявления (`platform_announcements`) создаёт и
  закрывает админ с правом MANAGE_OPERATIONS после недавнего входа; каждое
  изменение — запись аудита `platform_announcement`. Внешний монитор
  доступности здесь не подключён (`docs/operations/status-page.md`).

## LLM

- Провайдер-нейтральный контракт `LlmAdapterContract`. По умолчанию — OpenAI
  `gpt-5-mini` через `https://eu.api.openai.com/v1` (проект с хранением в ЕС,
  как в ТЗ); запасной — Anthropic; для тестов — `ScriptedLlmAdapter`.
- Транскрипт хранится «как есть» и только дописывается: пользовательские ходы —
  в каноническом формате, ходы модели — в формате провайдера. Изменчивое
  (текущее местное время) — в пользовательском ходе, не в инструкции.
- Инструкция собирается кодом из шаблона ниши без модели и не меняется внутри
  версии, поэтому кэш промпта работает.
- Отказ провайдера не оставляет клиента без ответа: у каждой пары
  «провайдер:модель» свой автомат (`CircuitBreakerFacilitator`: открывается
  после 5 сбоев за 60 с, через 30 с пропускает одну пробу), и
  `RoutingLlmAdapter` при сбое или открытом автомате повторяет ход на
  `LLM_FALLBACK_MODEL_ID` другого провайдера. Запасная модель читает
  провайдер-нейтральную копию ходов модели (`LlmTurnDocument.canonical_payload`,
  текст и вызовы инструментов без рассуждений провайдера); ответ помечается
  `is_fallback_model`, а разговор возвращается к своей модели, как только
  она снова отвечает.

## HTTP-слой

- Роутер каждого раздела — функция `build_<раздел>_router(...)`, операторы
  приходят аргументами.
- Ошибки приложения переводятся в HTTP-коды в одном месте
  (`app/gateways/http/error_responses.py`). Любая ошибка — `ErrorBody`
  (`{"error", "message", "reasons"?}`), и отказы самого фреймворка тоже
  (нет параметра — 422 с причинами `missing`/`invalid`, нет маршрута — 404);
  каждый роутер описывает их через `standard_error_responses()`
  (`openapi_error_contract.py`), и сгенерированный клиент кабинета знает тип
  ошибок. DELETE отвечает 204.
- Авторизация: `Authorization: Bearer`, асинхронная зависимость
  `build_current_user_dependency`: проверив токен (в пуле потоков), она
  кладёт сессию запроса (`SessionAssurance`: пользователь, сессия,
  `auth_level`, `authenticated_at`) в `SessionAssuranceContext` —
  контекстную переменную задачи запроса, которую видят потоки маршрута, но
  не другие запросы и не фон. Доступ к бизнесу — `AuthorizeBusinessAccessUseCase`
  (owner, staff; при `require_mfa_for_members` участник с одним фактором
  получает 403 `mfa_required`; вход платформенного админа пишется в журнал
  аудита). Админ платформы — тот, кто есть в `PLATFORM_ADMIN_*` сейчас
  (`is_listed_platform_admin`, при каждой проверке; флаг в `UserDocument`
  только для отображения), и админка требует сессию с двумя факторами
  (`AuthorizePlatformAdminUseCase`). Фон (сессии нет) действует от имени
  уже проверенного запроса.
- Двухфакторный вход (`app/use_cases/users/mfa/`): `VerifyOtpLoginUseCase`
  открывает сессию только тем, у кого нет приложения и кто не админ;
  остальным — `MfaRequiredView` и `MfaChallengeDocument`, а сессию с
  `TWO_FACTOR` открывает `VerifyMfaLoginUseCase` (код TOTP ±30 с, каждый
  шаг один раз — compare-and-swap по `last_used_step`; код восстановления
  гасится тоже через compare-and-swap). Каждое изменение фактора — запись
  `MFA_CHANGED` в журнале аудита.
- Подтверждение важных действий (step-up): use case после авторизации
  вызывает одну строку `step_up.require_recent_authentication()`
  (`RequireRecentAuthentication`, окно `STEP_UP_MAX_AGE_SECONDS`). Отказ —
  `StepUpRequiredError`: 401 `authentication_required` с причиной
  `step_up_required` и `WWW-Authenticate: Bearer
  error="insufficient_user_authentication"` (RFC 9470), по которому прокси
  кабинета не стирает сессию; кабинет показывает окно подтверждения
  (`/v1/auth/step-up`) и повторяет запрос. Неверный код — 422 с причиной
  `wrong_code`, а не 401.
- Живой кабинет (`events_routes.py`): use case после сохранения объявляет
  одной строкой, что изменилось (`EventPublisherFacilitatorContract.publish`:
  бизнес, вид события, id; никогда текст клиента; песочница не объявляется).
  Шина — `LiveEventBusAdapterContract`: в Postgres `NOTIFY` на канале
  `workshop_live_events` и одно слушающее соединение `LISTEN` на процесс (его
  поток раздаёт события подписчикам процесса; воркер только публикует), без
  Postgres — в памяти процесса. `GET …/events` — асинхронный маршрут
  Server-Sent Events: доступ проверяется коротко в пуле потоков, дальше поток
  не держит ни потока, ни соединения с базой; пульс каждые 20 с, через
  15 минут поток закрывается, `Last-Event-ID` досылает пропущенное из буфера
  процесса или просит кабинет перечитать всё (`stream.resync`); не больше 5
  потоков у человека на процесс. Кабинет перечитывает изменённое обычными
  маршрутами, которые проверяют доступ и пишут аудит.

## Сборка и точки входа

- Корень композиции — `app/containers/app.py::AppContainer`. Контейнеры по ролям
  зависят только «вниз»: операторы → пайплайны → оркестраторы → use case →
  репозитории, реестры, фасилитаторы, трансформеры, утилиты → адаптеры → клиенты.
  Use case типизированы своим контрактом (`UseCaseContract[вход, выход]`), а
  цепочки `PipelineOperator(OrchestratorPipeline(UseCaseOrchestrator(...)))`
  строятся типизированными помощниками `app/containers/provider_chains.py`, поэтому
  вызов каждого `build_<раздел>_router` проверяется mypy и pyright.
  Края корня (настройки, время, утилиты, клиенты, адаптеры и контейнеры коллекций
  рядом с адаптерами) — в базовом `app/containers/app_edges.py::AppEdgesContainer`,
  `AppContainer` наследует его и строит роли; так же контейнер use case
  наслаивается: `CoreUseCasesContainer` → `BusinessUseCasesContainer` (работа
  самого бизнеса) → `UseCasesContainer` (контексты платформы и роста).
- Большие контейнеры ролей собраны из дочерних контейнеров по ограниченным
  контекстам: `app/containers/<роль>/<роль>_container.py` компонует
  `<контекст>_<роль>.py` (use case — по пакетам `app/use_cases/`, оркестраторы,
  пайплайны и операторы — по разделам API: accounts, compliance, knowledge,
  operations, conversations, assistants, channels, billing, platform, а также
  demo — демо-данные разработки, `SEED_DEMO_DATA`). Провайдер
  читается по пути контекста: `use_cases.bookings.create_booking_use_case`,
  `operators.billing.end_trials_operator`. Дочерний контейнер получает рёбрами
  только нужные ему контексты; контейнер уровнем выше видит вложенные контексты
  через `composed_container_edge` (`app/containers/container_edges.py`).
- Где модуль нарушает направление ролей, провайдер стоит в контейнере уровнем выше:
  прогон сценария автотеста (use case, которому нужен оркестратор разговора) — в
  `AssistantOrchestratorsContainer`, оркестраторы вебхуков каналов и виджета (им
  нужен пайплайн сообщения клиента) — в `ChannelPipelinesContainer`.
- Синглтоны: клиенты, адаптеры (в том числе все коллекции документов на одном пуле
  Postgres и одном `StorageScopeContext`, дочерний `DocumentCollectionsContainer`
  контейнера адаптеров), репозитории, реестры (замки и лимиты запросов —
  общие для всех процессов: advisory-блокировки и таблица `rate_limit_buckets`
  в Postgres, см. «Несколько процессов» ниже), фасилитаторы, пайплайн
  сообщения клиента. Use case, оркестраторы и операторы — фабрики.
- Журнал вызовов модели (`llm_trace_facilitator`) живёт в `AdaptersContainer`:
  `TracingLlmAdapter` оборачивает им маршрутизирующий адаптер модели, а
  фасилитаторы сами зависят от адаптеров.
- HTTP: `app/main.py` (фабрика uvicorn) и `app/gateways/http/router_assembly.py`.
  Миграции: `python -m app.gateways.cli.migrate` — шлюз командной строки, он
  запускает use case применения миграций (`app/gateways/cli/`).
  Фоновый воркер: `app/worker_main.py`, задачи перечислены в
  `app/containers/periodic_jobs.py` (периодические) и
  `app/containers/queued_jobs.py` (из очереди), воркер собирает
  `app/containers/gateways.py`. Входящие (`process_inbound_message`,
  `process_platform_bot_update`, `process_post_call`) идут в полосе `inbound`,
  доставка исходящих (`deliver_outbound`) — в полосе `outbound`. В разработке
  без Postgres тот же воркер идёт потоком внутри API (`EMBEDDED_WORKER`,
  жизненный цикл в `app/main.py`): данные в памяти видны только своему
  процессу, а поставленная задача будит его сразу, поэтому ответ в
  разработке приходит без ожидания опроса очереди.

## Несколько процессов

API работает в нескольких экземплярах (`numInstances: 2` в `render.yaml`) рядом
с воркерами, поэтому ничто, от чего зависит правильность, не живёт в памяти
одного процесса:

- **Пул соединений и закрепление.** `PostgresConnectionPoolClient.pinned_connection()`
  закрепляет одно соединение за потоком на время блока: все операции хранилища
  этого потока внутри блока идут через него, вложенная транзакция становится
  точкой сохранения. Поток никогда не держит больше одного соединения, а
  запрос держит его мгновение, поэтому пул меньше числа потоков (по
  умолчанию `DB_POOL_SIZE` — половина `THREADPOOL_SIZE`); простаивающие
  соединения закрываются (`DB_POOL_MAX_IDLE_SECONDS`, до
  `DB_POOL_MIN_SIZE`). Сумма соединений всех процессов во время деплоя
  проверяется тестом `tests/platform/test_connection_budget.py`.
- **Единица работы.** `PostgresUnitOfWorkAdapter.unit_of_work()` (контракт
  `StorageUnitOfWorkContract`): одна транзакция на закреплённом соединении,
  область RLS задаётся в начале; каждая операция коллекции внутри — точка
  сохранения со своей областью, поэтому запись уровня платформы не оставляет
  обход RLS следующей записи бизнеса.
- **Блокировки** (`AdvisoryLockAdapterContract`, `app/adapters/locks/`):
  `hold_with_transaction` — `pg_advisory_xact_lock(hashtextextended(key, 0))`
  внутри единицы работы: запись брони и снятие блокировки бизнеса фиксируются
  вместе (`BusinessLockRegistry`), так же резерв отправки кода входа
  (`LoginCodeSendLockRegistry`). `hold_with_session` — `pg_advisory_lock` на
  закреплённом соединении на весь ход клиента (`CustomerMessageLockRegistry`,
  ключ business|channel|channel_user_id): ход вызывает модель, поэтому
  транзакция не держится открытой, а каждая запись хода фиксируется сразу.
  Ожидание ограничено (`lock_timeout`), ожидающие одного ключа в процессе
  стоят в очереди на локальной блокировке и не занимают соединения. Без базы
  те же реестры работают на блокировках процесса (`InMemoryAdvisoryLockAdapter`).
- **Лимиты запросов** (`RequestRateLimitRegistry` над
  `RateLimitBucketAdapterContract`): счётчики окон в таблице
  `rate_limit_buckets` (миграция 1041, `UNLOGGED`), запрос — один оператор:
  функция `workshop.count_request_within_limits` (миграция 1135) прибавляет
  запрос ко всем ключам в порядке ключей, сравнивает оценки с лимитами и,
  если лимит исчерпан, тут же вычитает запрос обратно (созданный им
  счётчик удаляет), так что запрос сверх лимита нигде не засчитывается.
  Строки заблокированы только пока выполняется этот оператор, а не на круг
  до Python и обратно: каждый опрос виджета считает одну и ту же строку
  платформы (`docs/operations/capacity.md`). Оценка — текущее окно плюс
  предыдущее с весом его части внутри скользящего окна
  (`app/utilities/limits/sliding_window_limits.py`, функция повторяет то же
  неравенство); устаревшие счётчики удаляет задача `sweep_rate_limit_buckets`
  раз в 10 минут.
- **Потоки и модель.** Обработчики запросов — не больше `THREADPOOL_SIZE`
  потоков (ограничитель AnyIO задаётся при старте), вызовы модели — не больше
  `LLM_MAX_CONCURRENCY` в процессе (`ConcurrencyLimitedLlmAdapter`, вокруг
  трассирующего адаптера: ожидание места не попадает в трассу). Ход клиента
  сначала берёт место хода (`TurnSlotRegistry`, столько же мест), и только
  потом блокировку клиента, которая закрепляет соединение: ожидающий место
  ход соединения не держит.
- **Готовность.** `GET /readyz` отказывает (503), только если база не
  отвечает или не применена миграция сборки; занятый пул — `degraded` (200),
  отказ — лишь после 30 с подряд без свободного соединения.
- **Записи звонков** (`RecordingStorageAdapterContract`): с
  `RECORDINGS_STORAGE=s3` — `EncryptedObjectRecordingStorageAdapter` над
  S3-совместимым хранилищем в ЕС (`S3ObjectStorageClient`: запросы по ссылкам
  с подписью SigV4 на 60 с, чтение диапазонами байт). Запись шифруется до
  отправки (`app/utilities/security/recording_encryption.py`: ключ бизнеса —
  HKDF от `ENCRYPTION_KEY` и id бизнеса, ключ записи — HKDF от ключа бизнеса,
  соли и пути; AES-256-GCM блоками по 64 КиБ с номером блока и меткой
  последнего в AAD), поэтому диапазон плеера читает и открывает только свои
  блоки. После звонка задача `archive_call_recording` переносит запись из
  ElevenLabs в бакет (CAS по пути записи звонка: очистка по сроку или
  удаление контакта в это время побеждают) и удаляет разговор у ElevenLabs.
  Локальные файлы (`LocalRecordingStorageAdapter`) — только разработка.
- **Проверка.** `tests/storage/test_two_processes.py` запускает два процесса API
  (uvicorn) и воркеры на одной тестовой базе: последнюю бронь получает ровно
  один, лимит виджета общий, ответы одному клиенту идут по очереди.
  `tests/storage/test_worker_pickup.py`: сообщение, принятое API, отдельный
  воркер берёт за 500 мс; `tests/storage/test_widget_burst.py`: 64 медленных
  хода виджета разом, а `/readyz` остаётся 200 и кабинет отвечает быстро.
