# Архитектура бэкенда

Бэкенд сгенерирован из шаблона
[`copier-template-python-backend`](https://github.com/eldenizfamilyanskicode/copier-template-python-backend)
и следует его ролям и правилам (`AGENTS.md`, `docs/conventions.md`). Здесь — как
техническое задание из [концепции v2](concept.md) переложено на Python.

## Отличия от стека в ТЗ

| В ТЗ | Здесь | Почему |
| --- | --- | --- |
| Next.js API-роуты (вебхуки, инструменты) | FastAPI в этом репозитории | требование владельца: бэкенд на Python по шаблону copier |
| Сайт, анкета, кабинет на Next.js | кабинет на Next.js в `web/` | ходит в HTTP API бэкенда через свои серверные маршруты; токен только в httpOnly cookie |
| Supabase Postgres (ЕС) + RLS | контракт документного хранилища; in-memory для тестов и Postgres (ЕС) с изоляцией по `business_id` | use case не зависят от базы |
| Node-воркер + pg-boss | Python-воркер с очередью в Postgres | один язык и одни use case для API и фоновых задач |
| packages/core, brain, channels, niches, evals | роли шаблона: use_cases, orchestrators, registries, adapters… | `services` запрещён шаблоном |
| `tenants`, `users` | `BusinessDocument`, `UserDocument` | те же поля; «бизнес» понятнее в коде |

Всё остальное — как в ТЗ: OpenAI gpt-5-mini в проекте с хранением в ЕС как «мозг»,
ElevenLabs Agents для голоса, номера Zadarma, WhatsApp Cloud API, Instagram и
Messenger через Graph API, Telegram Bot API, свой виджет, Flitt, Langfuse, Sentry.

## Роли и направление зависимостей

```text
HTTP (FastAPI)              app/gateways/http/      маршруты, коды ошибок, ответы
  └─ operators              app/operators/          одна точка входа на эндпоинт
      └─ pipelines          app/pipelines/          порядок оркестраторов в фазе
          └─ orchestrators  app/orchestrators/      координация нескольких use case
              └─ use_cases  app/use_cases/          одно бизнес-действие
                  ├─ repositories  app/repositories/  документы с изоляцией по бизнесу
                  ├─ registries    app/registries/    страны, языки, ниши, тарифы
                  ├─ facilitators  app/facilitators/  узкие побочные эффекты (SMS, уведомления)
                  ├─ utilities     app/utilities/     детерминированные операции
                  └─ transformers  app/transformers/  преобразование форм
repositories ─ adapters (app/adapters/) ─ clients (app/clients/)  внешние системы
```

Направление проверяет `lint-imports` по контрактам `.importlinter` в каждом прогоне
тестов; утилиты — чистые помощники, их могут импортировать все роли
([ADR 0002](adr/0002-role-chain-and-layers.md)).

## Данные (ТЗ §2)

Каждая таблица ТЗ — документ в `app/schemas/domain/`. Документы бизнеса несут
`business_id`; репозитории читают их только вместе с `business_id`
(`BusinessScopedRepository`), поэтому чужие данные недоступны ни по какому id —
это аналог RLS из ТЗ. `tenant_id` в инструментах берётся из сессии или из
канала на сервере, никогда из слов модели.

Вторая линия защиты — RLS в Postgres. Операторы (`BusinessScopedPipelineOperator`)
выполняют запрос бизнеса внутри `StorageScopeContract.scoped_to_business(...)`,
так же работают ход разговора (с вызовами инструментов модели), вызовы
инструментов голосового агента и задачи очереди с `business_id`. Тогда даже
репозиторий, забывший фильтр по бизнесу, не прочитает и не запишет чужие строки.

Область хранилища закрыта по умолчанию (fail-closed): код, не вошедший ни в
какую область, — `UNSCOPED` (`app.business_id = ''`, обход RLS выключен), и
коллекции бизнесов отказывают ему (`UnscopedStorageAccessError`, в памяти так
же, как в Postgres); коллекции платформы (пользователи, сессии, бизнесы,
журнал) доступны. Работа уровня платформы объявлена явно оператором
`PlatformWidePipelineOperator` (`platform_pipeline_operator` в
`provider_chains.py`): вебхуки до определения бизнеса (Telegram, Meta,
платежи, голос, согласие Google), список клиентов в админке, демо-данные и
периодические задачи по всем бизнесам. Вход, текущий пользователь и очередь
задач в админке работают без области — им нужны только коллекции платформы.
Код, которому нужно посмотреть сквозь бизнесы внутри запроса бизнеса
(уникальность аккаунта канала), явно поднимается через `platform_wide()`.
Проверки: `tests/platform/test_authorization_matrix.py` (каждая операция
`/v1/businesses/{business_id}/…` из описания API: чужой — 404 без следов,
сотрудник на операциях владельца — 403, без токена — 401, запрос — только в
области своего бизнеса; то же на Postgres в
`tests/storage/test_authorization_matrix_postgres.py`) и
`tests/architecture_policy/test_business_routes_are_scoped.py` (маршруты
бизнеса — только через `BusinessScopedPipelineOperator`, список операторов
уровня платформы утверждён).

## Пошаговый запуск

Путь владельца от «Создать AI-помощника» до живого помощника
(`app/use_cases/setup/`, `app/use_cases/assistants/apply/`):

- шаги запуска не хранятся, а вычисляются из данных бизнеса
  (`app/utilities/setup/setup_steps.py`): пробелы анкеты, контакт сотрудника,
  каналы, проба помощника, опубликованная версия; хранятся только
  пропущенные необязательные шаги;
- готовые ответы ниш (`app/registries/niches/starters/`) — подсказки, не
  факты: в анкету попадают только по согласию владельца и только в пустые
  разделы, цен в них нет;
- «Применить изменения» — оркестратор `ApplyChangesOrchestrator`: регистрация
  (атомарно, одна на бизнес), сборка, проверка условий запуска, постановка
  автотестов в очередь; публикует версию воркер, когда прогон закончился
  (`RunQueuedAutotestsOrchestrator` → `PublishAppliedVersionUseCase`) — через
  ту же активацию, что и ручная публикация;
- первый выход в эфир открывает пробный период (`StartTrialAtGoLiveUseCase`)
  и пишет веху `went_live`; первые настоящие разговор, бронь и передача
  человеку находятся по самым ранним записям бизнеса при чтении шагов, поэтому
  модули разговоров и броней о вехах не знают;
- тестовый чат владельца перед ответом собирает черновик, если в версиях ещё
  нет его последних правок (`PrepareTestChatVersionUseCase`);
- в кабинете этот путь — полноэкранный туннель из восьми вопросов: `/create`
  (бизнес и место; бизнес создаётся `POST /v1/assistants` в конце второго
  вопроса, до этого ответы хранятся в браузере) и `/b/{id}/setup` (остальные
  шаги, запуск и финал); туннель открывается на первом незавершённом шаге,
  своих данных у него нет (web/README.md, «Create an AI assistant»);
- после запуска тот же `GET …/setup` отдаёт подсказку «Обзора» (`guide`,
  `app/utilities/setup/guide_steps.py`): проверка с телефона, второй канал,
  ссылка для клиентов. Их факты тоже вычисляются (`SetupProbeRepository`:
  первое входящее с номеров владельца или в чат страницы, пока идёт проверка;
  каналы для клиентов; первая бронь в нерабочее время), а в состоянии запуска
  (`SetupStateDocument` v2) хранятся только времена, которых в данных нет:
  проверка начата и прошла, ссылка напечатана или скачана, первый визит на
  страницу чата, подсказка убрана, напоминания выключены. Модуль входящих
  сообщений о проверке не знает: факты замечает чтение шагов или задача
  `notice_milestones`;
- вехи после запуска объявляются владельцу один раз
  (`app/use_cases/setup/milestone_announcements.py`: `StaffAlert` с
  `subject` «milestone:…» через `ManagerNotificationFacilitator`), кабинет
  поздравляет и подтверждает `POST …/celebrate`;
- напоминания о настройке — периодическая задача `send_activation_nudges`
  (`SendActivationNudgesUseCase`): правило дня (`nudge_schedule.py`,
  `NudgeCode`, `NudgeDayOffset`), отправка через исходящие
  (`OwnerNudgeFacilitator`: Telegram-контакты владельца у бота платформы,
  почта, устройства) и запись в `nudges_sent` с ключом из
  (business_id, nudge_code); повторный запуск находит запись и молчит;
- способ подключения (`SetupOption`) выбирается при подписке: `SELF_SERVE`
  бесплатно, `DONE_FOR_YOU` — плата за подключение тарифа из каталога
  (`SETUP_FEES`) с первым ежемесячным счётом и заявка команде
  (`onboarding_requests`, письмо админам платформы).

## Общие входящие команды

Несколько человек ведут разговоры одного бизнеса (`app/use_cases/inbox/`,
`app/repositories/inbox_repositories.py`, миграция 1053):

- поля команды в `ConversationDocument` — ответственный, кто и когда
  назначил, `assignment_revision`, `has_open_request` и производное
  `awaits_team` (нужен человек или открыта заявка) — меняются только через
  `ConversationTeamRepoContract`: назначение — сравнить и записать по
  ревизии под блокировкой строки, открытая заявка — пересчётом при создании
  и смене статуса заявки (`track_request`). Обычное сохранение разговора
  (ход, передача, закрытие) берёт поля команды из хранимой строки, поэтому
  ход, начатый до назначения, его не отменяет;
- виды «нужен человек», «заявки», «мои», «без ответственного» и «все» —
  keyset-страницы по индексам `(business_id, условие вида,
  last_message_at)`; «без ответственного» — условие хранилища `missing`
  (поле отсутствует или null, `DocumentFilter.missing`); счётчики видов и
  нагрузка участников — один сгруппированный подсчёт ждущих разговоров;
  `CountInboxAttentionUseCase` отдаёт одни и те же счётчики вкладкам
  (`…/inbox/counts`) и значкам меню (`…/attention-counts`): значок
  «Входящие» — сумма вкладок «Нужен человек» и «Заявки»;
- строка вида собирается `InboxItemTransformer` из разговора, последнего
  написанного сообщения, открытых передачи и заявки (по одному `latest_by`
  на страницу) и числа заметок — без расхода модели, вызовов инструментов и
  свободного текста;
- автоназначение — декоратор передачи (`AutoAssigningHandoffUseCase`) и шаг
  создания заявки: кандидаты — выбранные участники, иначе сотрудники, иначе
  владельцы; меньше ждущих разговоров, при равенстве — по кругу после
  последнего назначенного; ошибка назначения пишется в лог и не мешает
  передаче;
- заметки — отдельная коллекция, а не сообщения: подготовка хода, расшифровка
  для модели, виджет и уведомления их не читают
  (`tests/e2e/test_team_inbox_journey.py`); быстрые ответы — один документ
  на бизнес с вариантами по языкам, переменные подставляются только из
  данных разговора, недостающие остаются в скобках;
- каждая операция проверяет доступ через `AuthorizeBusinessAccessUseCase`,
  просмотр вида, назначение, заметки, быстрые ответы и настройки пишутся в
  журнал аудита, назначение и заметки — в живые события
  (`conversation.assigned`, `conversation.note`).

## Ценность помощника, сводки и отчёты

Что помощник сделал и сколько это стоит (`app/use_cases/insights/value/`,
`app/repositories/value_repositories.py`, миграция 1061):

- модель ценности (`ComputeValueModelUseCase`) считает за период и за
  предыдущий период той же длины (тестовая активность не входит):
  разговоры и разговоры в нерабочее время, сообщения клиентов и ответы
  помощника, принятые звонки, все брони и брони, сделанные помощником в
  разговоре и не отменённые, заявки, передачи человеку; минуты сотрудников =
  ответы × секунды на ответ ниши + звонки × секунды на звонок
  (`app/registries/niches/niche_value_catalog.py`); деньги = брони помощника
  по их собственной стоимости (цена услуги, ночи номера по сезонным
  тарифам; см. «Услуги, мастера и номера»), остальные брони × средний чек
  (`revenue_source`: `booked_values`, `mixed` или `average_check`); для
  ниш, где принимают заказы, — заявки × средний чек (`value_basis`);
- средний чек — свой у владельца (`value_settings`, `PUT …/value/settings`,
  пишется в журнал аудита) или типичный для ниши, пересчитанный в валюту
  бизнеса и округлённый до двух значащих цифр; без него оценки в деньгах
  нет, кроме броней со своей стоимостью;
- `GET …/value` отдаёт модель кабинету, сотрудникам — без денег; счётчики —
  сгруппированные подсчёты хранилища (`ValueCountRepository`), без чтения
  строк;
- сводки и отчёт: периодическая задача `send_value_reports` (раз в час,
  запуск сохраняется в `PeriodicJobRunner`, поэтому один на все процессы и
  перезапуски) для каждого работающего бизнеса в его часовом поясе готовит
  дневную сводку (вчера, если хоть один владелец её включил), недельную (с
  понедельника 9:00 — прошлая неделя) и месячный отчёт (с 1-го числа 9:00 —
  прошлый месяц, и для бизнеса на паузе). Снимок итогов сохраняется в
  `value_reports` с ключом uuid5(бизнес, вид, период) через
  `insert_if_absent`: второй запуск видит готовый отчёт и ничего не шлёт;
  письма и push уходят через outbox с ключами по отчёту, поэтому повтор
  после падения посередине не дублирует уже поставленные
  (`tests/value/test_value_reports_restart.py`). Период без активности
  сохраняется как `quiet` и не отправляется;
- получатели (`OwnerDigestFacilitator`) — владельцы, у которых этот вид
  включён (`digest_preferences`: по умолчанию недельная сводка и месячный
  отчёт, дневная выключена): письмо на адрес входа на языке кабинета и push
  на устройства с включёнными уведомлениями этого бизнеса (тихие часы
  владельца соблюдаются только для push). В тексте — подписанная ссылка
  `{кабинет}/n/{token}` (цель `report`), открывающая отчёт на странице
  «Обзор → Отчёты», и строка о том, где отключить сводки;
- кабинет: на сводке владелец видит блок ценности (брони ≈ деньги, нерабочее
  время, сэкономленное время, средний чек правится на месте), у каждой
  цифры — изменение к предыдущему периоду словами для экранного диктора;
  сотрудник вместо этого видит свою очередь дня (`GET …/today-queue` и виды
  ящика). Страница «Отчёты» (только владельцы): текущий месяц, сохранённые
  месячные, недельные и дневные отчёты и выбор сводок.

Чего нет: сводок в Telegram и WhatsApp сотрудников (только почта и push),
ссылки отписки в одно нажатие без входа в кабинет.

## Услуги, мастера и номера

Что можно забронировать и сколько стоит бронь (`app/utilities/bookings/`,
`app/use_cases/bookings/offer_selection.py`, миграция 1083):

- знания вида `service`, `package` и `room_type` описывают бронь:
  длительность (`ServiceDurationMinutes`, 5–720 минут), перерыв мастера
  после визита (`BufferMinutes`), цену и исполнителей
  (`performer_resource_ids`); ресурс со своей стороны называет услуги,
  которые выполняет (`serves_item_ids`), и тип номера (`room_type_item_id`).
  Связь читается с обеих сторон. У типа номера — сезонные цены ночи
  (`seasonal_rates`, «MM-DD»–«MM-DD» каждый год, в том числе через Новый
  год); ночь вне сезонов стоит `price_minor`;
- инструменты модели `check_availability` и `create_booking` принимают
  `service_id` и `resource_id` — id или имя в любой письменности
  («Nino», «ნინო», «Нино», «стрижку»): `target_resolution` сравнивает имена
  как написаны и в латинской транскрипции, по словам, с учётом склонений и
  опечаток, имена на иврите и арабском — по согласным. Неизвестное или
  неоднозначное имя — отказ с кодом (`unknown_service`,
  `ambiguous_resource`, …), список вариантов для модели и id в `details`;
  мастер, который не выполняет услугу, — `not_performed`. Без услуги
  результат проверки перечисляет услуги с их id;
- слоты длятся столько, сколько услуга, и предлагаются только её
  исполнителям; бронь хранит свой перерыв (`buffer_minutes`), и следующая
  бронь ресурса не начнётся раньше его конца (`booking_placement`);
- бронь хранит услугу и стоимость (`service_item_id`, `value_minor`,
  `currency_code`): цену услуги или сумму ночей проживания по сезонам
  (`stay_quotes`); перенос проживания пересчитывает её. `get_price` с датой
  заезда и числом ночей отдаёт расчёт по ночам;
- сводка кабинета (`booked_value`, `after_hours_booked_value`) и модель
  ценности складывают стоимости базой данных (`sum_value_made`,
  генерируемые колонки и покрывающий индекс миграции 1083), без чтения
  броней; отменённые и неявки не входят;
- автотесты ниш: салон, клиника и ветклиника бронируют услугу у названного
  мастера, отель и аренда — тип номера на несколько ночей
  (`BookingScenarioVariant`).

Редакторы услуг, исполнителей и сезонов в кабинете — R10-SERVICES-CABINET.

## Страница чата и ссылки

Контекст `sharing` (`app/use_cases/sharing/`, маршруты
`sharing_routes.py` и `public_chat_routes.py`):

- адрес страницы чата `/c/{slug}` — запись `public_slug_claims` с ключом-адресом,
  вставляется «если нет» (`insert_if_absent`), поэтому один адрес не достаётся
  двум бизнесам даже при гонке и под RLS; записи остаются у бизнеса навсегда,
  так что старый адрес (и напечатанный QR-код) ведёт к нему же. Коллекция —
  бизнеса (`business_id`), публичный поиск по адресу явно поднимается через
  `platform_wide()` (`ResolveHostedChatUseCase`), затем страница читается в
  области найденного бизнеса (`HostedChatOrchestrator`). Первый адрес — из
  названия (`app/utilities/sharing/`: транслитерация грузинского, кириллицы,
  армянского), при занятости — с номером, в крайнем случае `chat-<hex>`
  (такие адреса зарезервированы и владельцу недоступны);
- ссылки каналов строит `app/utilities/channels/channel_links.py`; публичные
  адреса аккаунтов (номер WhatsApp, username страницы и Instagram) API узнаёт
  при подключении канала (`ChannelDocument.public_profile`); канал без них
  отдаёт «переподключите»;
- ссылка на политику конфиденциальности — вид `privacy` в ссылках анкеты; она
  хранится в отдельном поле `BusinessProfileDocument.privacy_notice_url`
  (правило expand/contract: новое значение перечисления не пишется в
  документы в том же выпуске, где появилось), API показывает её среди ссылок;
- «Позвать человека» из виджета (`WidgetHandoffPipeline`) держит ту же
  блокировку клиента, что и входящее сообщение, открывает или находит
  разговор посетителя и передаёт его через `HandoffToHumanUseCase` с причиной
  `customer_request`; уже переданный разговор второй передачи не получает.

Страницу `/c/{slug}` рисует кабинет (`web/src/app/c/[slug]/`): прокси узнаёт
бизнес у `GET /v1/public/chat/{address}`, переводит старые адреса и id на
текущий, ставит строгую CSP с адресом API в `connect-src` и передаёт ответ
странице в заголовке запроса (повторного вызова нет); страница грузит
`widget.js` с nonce в режиме страницы.

## Импорт знаний с сайта и защита от SSRF

Импорт с сайта бизнеса (`app/use_cases/knowledge/website_import/`) — задача
воркера: страницы того же сайта (до 15, из `sitemap.xml` или ссылок стартовой
страницы) читаются по одной, каждая проходит одно извлечение моделью, а
найденное становится выключенными черновиками того же вида, что у импорта
меню, — их проверяет и включает владелец, сам импорт ничего не публикует.

Любой адрес, который присылает владелец или находит импорт, скачивается только
через `SafeHttpFetcherContract` (`app/clients/http/safe_http_fetcher.py`):

- адрес проверяется до сети (`http`/`https`, порты 80 и 443, без логина,
  без `localhost` и служебных зон);
- имя разрешается один раз, каждый IP сверяется со списком запрещённых сетей
  (`public_addresses.py`), и соединение открывается ровно на проверенный IP
  (`VettingNetworkBackend` для httpcore; TLS проверяет исходное имя) — подмена
  DNS между проверкой и соединением ничего не даёт;
- каждый из не более трёх редиректов проверяется так же;
- общий срок, предел размера после распаковки и белый список типов содержимого.

Текст страницы очищается от скриптов, стилей и скрытого текста
(`app/utilities/knowledge/website/`) и уходит модели внутри ограждения со
случайным ключом как недоверенные данные.

## Адаптивность под любую страну

Требование владельца проекта и раздел «Масштаб» ТЗ («новая страна — это язык,
номера, платежи и партнёр на месте, а не новый продукт»):

1. **Номера телефонов** любой страны разбираются библиотекой `phonenumbers`
   (245 регионов) и хранятся только в E.164. Из номера выводятся страна, тип
   линии и часовые пояса. Телефон в инструментах модели разбирается с подсказкой
   страны бизнеса, а не «+995» по умолчанию.
2. **Профиль страны** собирается для каждой страны мира из `phonenumbers` и
   Babel/CLDR (языки, валюта, часовые пояса), сверху — кураторские данные:
   экстренный номер, стартовые языки (для Грузии ka, ru, en; по запросу tr, he,
   ar, hy), канал кода входа, правило записи звонков (уведомление или согласие
   всех сторон), местные номера, статус онбординга, регион данных (ЕС).
3. **Языки** — любые теги BCP 47; направление письма (иврит и арабский — справа
   налево); честная пометка голоса: `verified`, `beta`, `needs_pilot_check`
   (грузинский — до замера на пилоте, как требует ТЗ).
4. **Деньги** — целые минимальные единицы валюты бизнеса (в Грузии — лари).
   Тарифы — в евро с прайсом в лари; фильтр выдуманных цифр понимает символы и
   коды любой валюты. Курсы — датированные строки `exchange_rates` (задача
   `refresh_exchange_rates`: НБГ и ЕЦБ раз в 6 часов), точные десятичные
   строки; недостающая пара — обратный или кросс-курс через евро с пометкой
   «рассчитан», старше 4 дней — «устарел»; до первого обновления — датированный
   запасной каталог. Один `ExchangeRateRegistry` пересчитывает и цены тарифов,
   и ценность помощника, и маржу клиента в админке.
5. **Время** — часы, исключения и брони в часовом поясе бизнеса (IANA),
   хранение в UTC.
6. **Тексты** для владельца и клиента — словари `язык → текст` с откатом:
   запрошенный язык → базовый язык → английский.

## Путь сообщения (ТЗ §1)

Вебхук канала → адаптер канала (`parse_webhook`, `verify_signature`) → бизнес
по id канала → **входящие** (`inbound_events`, вставка «on conflict do
nothing» по каналу и id сообщения у провайдера) → задача
`process_inbound_message` в полосе `inbound` → ответ платформе `200`. Вебхук
не зовёт модель и не шлёт ответ: он только проверяет подпись, пишет строку и
ставит задачу, поэтому отвечает быстро, а повтор той же доставки (Telegram и
Meta повторяют, если ответ задержался) не создаёт второй строки и второго
ответа.

Воркер: задача берёт событие с арендой на 180 с (`PROCESSING`) → контакт →
разговор, закреплённый за опубликованной версией → язык по первой фразе →
модель с инструкцией (шаблон ниши + факты) и инструментами → сервер выполняет
инструменты → фильтр выдуманных цифр (переписать один раз, потом передать
человеку) → запись в `messages` и `usage_events` → ответ в **исходящие**
(`outbound_messages`) → событие `ANSWERED` (или `HANDED_OFF`, когда бот молчит,
потому что передача человеку открыта). Id сообщения клиента и id ответа
заранее выведены из события, поэтому повторная обработка не дублирует
сообщения, а ответ, сохранённый до падения, отправляется без нового вызова
модели. Если воркер умер посреди хода, задачу освобождает сборщик
просроченных аренд, и событие обрабатывается заново. Сообщения одного
клиента идут по одному (`serial_key` задачи по каналу и клиенту).

Вложения: адаптер канала кладёт во входящее сообщение `InboundAttachment`
(голос, фото, место, контакт, стикер, другое; id файла у провайдера, тип,
подпись). Файлы скачивает воркер, а не вебхук
(`ReadInboundAttachmentsOrchestrator`: `ChannelMediaFetcherContract` —
WhatsApp Graph `/{media_id}`, Telegram `getFile`, адрес CDN Meta только с
хостов Meta), с лимитами размера до и во время скачивания и проверкой
содержимого по сигнатуре. Голос расшифровывает модель `LLM_TRANSCRIBE_MODEL`
(по умолчанию `gpt-4o-transcribe`) в EU-проекте OpenAI (языки версии —
подсказка), расход пишется как `transcription_seconds`; модель видит текст
внутри ограды клиента с меткой
«[Voice message, transcribed]». Фото уходит модели картинкой (OpenAI
`input_image`, Anthropic `image`), в истории хода хранится только ссылка
`stored_media`, которую `MediaResolvingLlmAdapter` раскрывает при каждом
запросе (последние 4 фото, остальные — заметкой). Место — координаты и
ссылка на карту. Сообщение без читаемого содержимого (только стикер,
контакт, файл) получает `CANNOT_READ_ATTACHMENT` на языке клиента без
вызова модели. Файлы лежат зашифрованными (AES-256-GCM, ключ на бизнес и
путь) в хранилище записей под `message-media/`, их описания — в коллекции
`message_media`; хранятся столько же, сколько записи звонков; кабинет
открывает их через `GET /v1/businesses/{id}/media/{media_id}` с записью в
журнал аудита. Id файла выведен из id события и позиции, поэтому повтор
задачи не скачивает и не оплачивает расшифровку второй раз.

Исходящие: строка с ключом идемпотентности (разговор + id ответа, уникален
в бизнесе) → задача `deliver_outbound` в полосе `outbound` → отправка по
частям (отправленные части не повторяются) → `DELIVERED`. Ответы одному
получателю уходят по порядку: более раннее неотправленное сообщение того же
получателя задерживает следующее. Ошибки провайдера разобраны по классам:
`429` ждёт `Retry-After`; `5xx` и сеть — повтор с экспоненциальной паузой
(10 с … 30 мин, ±25 % случайного сдвига, до 8 попыток); отказ `4xx` или
отозванный токен — сообщение `DEAD` и `last_error` канала (канал в `ERROR`).
Ответ клиенту, который так и не ушёл, открывает передачу человеку, чтобы
клиент не остался без ответа.

Уведомления персоналу (`ManagerNotificationFacilitator`) тоже пишутся в
исходящие и уходят той же задачей: передача человеку остаётся `PENDING`, пока
уведомление в пути, становится `NOTIFIED` после доставки и
`NOTIFICATION_FAILED`, если ни одно уведомление не дошло.

Всё, что получает клиент, идёт через исходящие — сценарий не зовёт `send`
или `send_template` канала сам (`tests/architecture_policy/
test_customer_messages_go_through_the_outbox.py`; исключения — сам outbox и
проверка подключения канала). Строка и задача пишутся в одной транзакции
(`queue_outbound_message`), ключ идемпотентности задаёт повод: ответ
сотрудника — id сообщения (`staff_reply`), напоминание — бронь, вид и время
начала (`booking_reminder`; перенесённая бронь получает новое), подтверждение
и ссылки после звонка — id звонка и вид (`call_confirmation`, `call_links`,
первый мессенджер, который может принять текст сейчас), ответ на пропущенный
звонок — id звонка (`text_back`, шаблон WhatsApp со сроком `send_before`:
позже он не уходит, `expired`). Сообщение сотрудника хранится вместе со
строкой исходящих; карточка разговора показывает под ним доставку
(`MessageView.delivery`: отправляется, повтор с причиной и временем
следующей попытки, доставлено, не доставлено с причиной —
`DeliveryFailureReason`), каждая попытка будит открытые кабинеты событием
разговора. Отказ Meta от шаблона ответа сотрудника — `template_rejected` без
повтора по-английски. Шаблон ответа на пропущенный звонок, когда он
доставлен или окончательно не ушёл, снова запускает задачу
`send_missed_call_text_back`: она отмечает звонок и при отказе шлёт SMS.
Новые виды сообщений пишутся в том же выпуске, что их читает: откат на
выпуск старше этого не прочтёт такие строки исходящих (прежде чем
откатываться, дождаться, пока они уйдут).

Приём тоже атомарен: вебхук пишет событие входящих и его задачу в одной
транзакции (`store_and_queue` с `storage_unit_of_work`), так что падение
между ними не оставляет ни того, ни другого, и платформа присылает вебхук
снова. Если задача всё же потерялась (старый выпуск, задачу сняли руками),
её находит периодическая `sweep_stale_inbound_events` (каждые 5 минут, вся
платформа, индекс миграции 1094 по статусу и времени прихода): событие в
`RECEIVED` или `PROCESSING` дольше двух аренд обработки, без живой аренды и
без ждущей или идущей задачи получает задачу снова (их число — в отчёте
задачи и в логе). Сообщение клиента, от которого ассистент отказался
(`FAILED`), через час уходит человеку передачей с цитатой сообщения
(`MODEL_UNAVAILABLE`, срочно), один раз: событие помечается
`handoff_requested_at`.

Виджет сайта — такой же канал: запрос пишет строку во входящие и ставит
задачу `process_inbound_message` в одной транзакции и сразу отвечает `202`
с id события. Ход клиента делает воркер; виджет показывает «печатает…» и
забирает ответ (или сообщение сотрудника) опросом сообщений, поэтому
медленная модель не держит потоки запросов API. Только тестовый чат
владельца отвечает в запросе, не больше `TEST_CHAT_MAX_CONCURRENCY` сразу
(дальше — `429`).

Задачу воркер берёт сразу: очередь вместе со вставкой делает
`pg_notify('workshop_jobs', <полоса>)` (уведомление уходит только при
фиксации транзакции), а поток `LISTEN` воркера будит потоки полосы. Опрос
очереди остаётся страховкой (`WORKER_INBOUND_POLL_SECONDS`,
`WORKER_POLL_SECONDS`, первые опросы потоков разнесены). Задержку от
постановки до захвата каждая задача пишет в лог (`pickup_delay_ms`,
`docs/operations/capacity.md`).

Строки входящих и исходящих удаляет `purge_stale_rows` через 30 дней.

## Путь звонка (ТЗ §1, §7)

Переадресация «нет ответа / занято» → номер Zadarma → SIP → агент ElevenLabs
этого бизнеса. Агент собран из той же версии: та же инструкция и те же
инструменты, вызываемые через наши вебхуки с подписью HMAC. После звонка вебхук
приносит расшифровку, запись и стоимость: вебхук проверяет подпись, кладёт
отчёт во входящие (повтор того же отчёта — `duplicate`) и ставит задачу; воркер
записывает `calls`, итог (бронь, заявка, передача, вопрос без ответа) и
подтверждение клиенту сообщением.

Шаги воркера после записи звонка — `PostCallWebhookOrchestrator`: разговор
для звонка, где клиент говорил (карточка звонка в «Сообщениях»), аудит
названных помощником значений, пропущенный звонок (клиент промолчал или
перевод на сотрудника никто не взял), итог звонка, подтверждение брони,
ссылки и архив записи. `SummarizeCallUseCase` пишет короткий итог дешёвой
моделью (`LLM_SUMMARY_MODEL_ID`) на языках владельца и сотрудников, хранит
его в `calls.summaries` один раз и отправляет сотрудникам через outbox
(Telegram и WhatsApp; ключ идемпотентности — `call:{id}` на получателя).

Пропущенные звонки (`missed_calls`) приходят из трёх мест: уведомление
NOTIFY_END АТС Zadarma (`POST /v1/telephony/zadarma/notifications`, подпись
`ZADARMA_API_SECRET`; занято, нет ответа, сброс, сбой линии), событие
`call_initiation_failure` вебхука ElevenLabs и шаги воркера выше.
`RegisterMissedCallUseCase` сохраняет звонок один раз на `provider_call_id`
и решает, писать ли звонящему: выключено, скрытый номер, помощник не в
эфире, отчёт старше двух часов, нет канала, клиент отказался от сообщений
или уже пишет бизнесу, лимиты (один раз в сутки на номер, 200 в сутки на
бизнес; общие счётчики `rate_limit_buckets`). Задача
`send_missed_call_text_back` (полоса `outbound`) отправляет одобренный
шаблон WhatsApp на языке звонящего с номера бизнеса и открывает разговор
WhatsApp, где продолжится ответ клиента; при отказе WhatsApp — SMS
платформы; временный сбой повторяет очередь задач. Настройки — коллекция
`call_settings`, страница «Настройки → Звонки».

## Отзыв после визита и отказ от рассылок

Контекст `feedback` (`app/use_cases/feedback/`, маршруты `review_routes.py`):

- периодическая задача `request_visit_feedback` (каждые 10 минут, оператор
  поднимает `platform_wide()`) берёт бизнесы с включёнными отзывами
  (`review_settings`, бизнес в эфире) и визиты, закончившиеся
  `delay_minutes` назад (не позже чем ещё через шесть часов — поздний вопрос
  хуже никакого): бронь `completed` или всё ещё `confirmed` после конца, не
  тестовая. `RequestVisitFeedbackUseCase` создаёт `feedback_requests` с id из
  бизнеса и брони (один раз на визит) и пишет клиенту в мессенджер брони, а
  если там нельзя — в другой подключённый (Telegram, WhatsApp, Messenger,
  Instagram) через outbox (`customer_reply`, шаблон WhatsApp с названием
  бизнеса вне 24-часового окна, английский перевод при отказе Meta, учёт
  `wa_template`). Не спрашиваем (запрос `skipped` с причиной): клиент
  отказался от рассылок, нет контакта или мессенджера, окно WhatsApp
  закрыто без шаблона, уже спрашивали сегодня, исчерпан дневной лимит.
  Вопрос виден в разговоре как сообщение бизнеса;
- ответы читает платформа до модели (`AnswerCustomerSignalUseCase` в
  `ConversationTurnOrchestrator`): оценка 1–5 (цифры любой письменности,
  звёзды-эмодзи, числительные ~55 языков, «4/5») сразу после запроса в том
  же канале и в течение недели записывается в запрос, клиент получает
  благодарность и ссылку на страницу отзывов Google при любой оценке (без
  «фильтрации отзывов»); оценка 3 и ниже ещё и передаёт разговор человеку
  (`complaint`, низкая срочность, итог на языке владельца). Ссылка идёт
  через `GET /v1/public/reviews/{token}` (случайный токен запроса; поиск по
  токену явно `platform_wide()`), который считает переходы (не превью
  мессенджеров) и отвечает 302; без `APP_BASE_URL` клиент получает адрес
  Google напрямую, переходы не считаются;
- ссылка Google хранится в анкете в отдельном поле
  `BusinessProfileDocument.google_review_url` (как `privacy`, правило
  expand/contract), API показывает её среди ссылок как `google_review`;
- отказ от рассылок: сообщение целиком «STOP», «СТОП», «სტოპ» или их
  переводы (`app/utilities/channels/opt_out_keywords.py`) добавляет канал в
  `ContactDocument.opted_out_channels`, «START» снимает отказ; обе записи —

  каждого клиента общий дневной лимит таких сообщений (3 в сутки,
  `proactive_message_counter` в `rate_limit_buckets`).

## Аналитика роста для основателя

Свои события продукта, без внешних трекеров (`app/use_cases/admin/metrics/`,
`app/use_cases/telemetry/`, маршруты `analytics_routes.py`, миграция 1074):

- `product_events` — шаги владельца от регистрации до оплаты
  (`ProductEventName`): регистрация и вход, бизнес создан, экраны туннеля
  (открыт, пройден, пропущен), итог запуска, принятие DPA, подключение
  канала, вехи (запуск, первый настоящий разговор, бронь, передача), пробный
  период, подписка, смена тарифа, отмена, неуспешный платёж. Каждый
  перечисленный сценарий пишет шаг одной строкой через
  `RecordProductEventFacilitator`, который никогда не роняет действие
  владельца. Однократные шаги получают id из субъекта (UUID v5), поэтому
  хранятся один раз; шаги оплаты несут, сколько подписка приносит в месяц
  (годовая цена / 12) и в какой валюте;
- ежедневная задача `reconcile_product_events` восстанавливает пропущенные
  шаги из записей (регистрации, бизнесы, вехи, запуск по первой
  опубликованной версии, каналы, пробный период) и выравнивает шаги оплаты с
  подпиской (ACTIVE или PAST_DUE в льготный срок после оплаченного периода —
  платит; иначе нет);
- `GET /v1/admin/metrics` строит всё на лету: воронка владельцев
  (приглашённые сотрудники и админы платформы не считаются; шаг засчитан,
  только если пройдены все предыдущие), медианное время до запуска,
  активация бизнеса (запуск, канал и настоящий разговор за 7 дней от
  создания; моложе недели — «ещё в пути»), пробный → оплата, туннель,
  когорты по месяцу регистрации, источники (`signup_attribution` на
  пользователе: utm_source → `src` → `referral` → `hosted_chat` → сайт →
  `direct`; без атрибуции — `unknown`), MRR: воспроизведение шагов оплаты
  по бизнесу даёт MRR на начало и конец периода и движения new,
  reactivation, expansion, contraction, churn (начало + движения = конец);
  суммы в евро по официальным курсам `ExchangeRateRegistry` (прямой или
  опубликованный обратный курс; валюта без курса не считается и
  называется), ARPA, валовая маржа из `ComputeClientCostUseCase`;
- `POST /v1/telemetry/events` принимает от кабинета пакеты Web Vitals (LCP,
  INP, CLS по шаблону маршрута и классу устройства) и шагов туннеля; 30
  пакетов в минуту на человека (`rate_limit_buckets`); замеры удаляет
  ежедневная `purge_web_vitals` через 90 дней (запись в аудите); p75
  считается по корзинам значений в базе (`count_by`);
- атрибуция: прокси кабинета на первой странице визита (лендинг, страница
  чата) кладёт в httpOnly-cookie `aw_attr` utm-метки, `ref`, `src`, хост
  ссылающегося сайта и путь; BFF входа отправляет её как
  `signup_attribution`, API хранит её только у нового аккаунта.

## LLM

- Провайдер-нейтральный контракт `LlmAdapterContract`. По умолчанию — OpenAI
  `gpt-5-mini` через `https://eu.api.openai.com/v1` (проект с хранением в ЕС,
  как в ТЗ); запасной — Anthropic; для тестов — `ScriptedLlmAdapter`.
- Транскрипт хранится «как есть» и только дописывается: пользовательские ходы —
  в каноническом формате, ходы модели — в формате провайдера. Изменчивое
  (текущее местное время) — в пользовательском ходе, не в инструкции.
- Инструкция собирается кодом из шаблона ниши без модели и не меняется внутри
  версии, поэтому кэш промпта работает.

## HTTP-слой

- Роутер каждого раздела — функция `build_<раздел>_router(...)`, операторы
  приходят аргументами.
- Ошибки приложения переводятся в HTTP-коды в одном месте
  (`app/gateways/http/error_responses.py`). Любая ошибка — `ErrorBody`
  (`{"error", "message", "reasons"?}`), и отказы самого фреймворка тоже
  (нет параметра — 422 с причинами `missing`/`invalid`, нет маршрута — 404);
  каждый роутер описывает их через `standard_error_responses()`
  (`openapi_error_contract.py`), и сгенерированный клиент кабинета знает тип
  ошибок. DELETE отвечает 204.
- Авторизация: `Authorization: Bearer`, асинхронная зависимость
  `build_current_user_dependency`: проверив токен (в пуле потоков), она
  кладёт сессию запроса (`SessionAssurance`: пользователь, сессия,
  `auth_level`, `authenticated_at`) в `SessionAssuranceContext` —
  контекстную переменную задачи запроса, которую видят потоки маршрута, но
  не другие запросы и не фон. Доступ к бизнесу — `AuthorizeBusinessAccessUseCase`
  (owner, staff; при `require_mfa_for_members` участник с одним фактором
  получает 403 `mfa_required`; вход платформенного админа пишется в журнал
  аудита). Админ платформы — тот, кто есть в `PLATFORM_ADMIN_*` сейчас
  (`is_listed_platform_admin`, при каждой проверке; флаг в `UserDocument`
  только для отображения), и админка требует сессию с двумя факторами
  (`AuthorizePlatformAdminUseCase`). Фон (сессии нет) действует от имени
  уже проверенного запроса.
- Двухфакторный вход (`app/use_cases/users/mfa/`): `VerifyOtpLoginUseCase`
  открывает сессию только тем, у кого нет приложения и кто не админ;
  остальным — `MfaRequiredView` и `MfaChallengeDocument`, а сессию с
  `TWO_FACTOR` открывает `VerifyMfaLoginUseCase` (код TOTP ±30 с, каждый
  шаг один раз — compare-and-swap по `last_used_step`; код восстановления
  гасится тоже через compare-and-swap). Каждое изменение фактора — запись
  `MFA_CHANGED` в журнале аудита.
- Подтверждение важных действий (step-up): use case после авторизации
  вызывает одну строку `step_up.require_recent_authentication()`
  (`RequireRecentAuthentication`, окно `STEP_UP_MAX_AGE_SECONDS`). Отказ —
  `StepUpRequiredError`: 401 `authentication_required` с причиной
  `step_up_required` и `WWW-Authenticate: Bearer
  error="insufficient_user_authentication"` (RFC 9470), по которому прокси
  кабинета не стирает сессию; кабинет показывает окно подтверждения
  (`/v1/auth/step-up`) и повторяет запрос. Неверный код — 422 с причиной
  `wrong_code`, а не 401.
- Живой кабинет (`events_routes.py`): use case после сохранения объявляет
  одной строкой, что изменилось (`EventPublisherFacilitatorContract.publish`:
  бизнес, вид события, id; никогда текст клиента; песочница не объявляется).
  Шина — `LiveEventBusAdapterContract`: в Postgres `NOTIFY` на канале
  `workshop_live_events` и одно слушающее соединение `LISTEN` на процесс (его
  поток раздаёт события подписчикам процесса; воркер только публикует), без
  Postgres — в памяти процесса. `GET …/events` — асинхронный маршрут
  Server-Sent Events: доступ проверяется коротко в пуле потоков, дальше поток
  не держит ни потока, ни соединения с базой; пульс каждые 20 с, через
  15 минут поток закрывается, `Last-Event-ID` досылает пропущенное из буфера
  процесса или просит кабинет перечитать всё (`stream.resync`); не больше 5
  потоков у человека на процесс. Кабинет перечитывает изменённое обычными
  маршрутами, которые проверяют доступ и пишут аудит.

## Сборка и точки входа

- Корень композиции — `app/containers/app.py::AppContainer`. Контейнеры по ролям
  зависят только «вниз»: операторы → пайплайны → оркестраторы → use case →
  репозитории, реестры, фасилитаторы, трансформеры, утилиты → адаптеры → клиенты.
  Use case типизированы своим контрактом (`UseCaseContract[вход, выход]`), а
  цепочки `PipelineOperator(OrchestratorPipeline(UseCaseOrchestrator(...)))`
  строятся типизированными помощниками `app/containers/provider_chains.py`, поэтому
  вызов каждого `build_<раздел>_router` проверяется mypy и pyright.
- Большие контейнеры ролей собраны из дочерних контейнеров по ограниченным
  контекстам: `app/containers/<роль>/<роль>_container.py` компонует
  `<контекст>_<роль>.py` (use case — по пакетам `app/use_cases/`, оркестраторы,
  пайплайны и операторы — по разделам API: accounts, compliance, knowledge,
  operations, conversations, assistants, channels, billing, platform, а также
  demo — демо-данные разработки, `SEED_DEMO_DATA`). Провайдер
  читается по пути контекста: `use_cases.bookings.create_booking_use_case`,
  `operators.billing.end_trials_operator`. Дочерний контейнер получает рёбрами
  только нужные ему контексты; контейнер уровнем выше видит вложенные контексты
  через `composed_container_edge` (`app/containers/container_edges.py`).
- Где модуль нарушает направление ролей, провайдер стоит в контейнере уровнем выше:
  прогон сценария автотеста (use case, которому нужен оркестратор разговора) — в
  `AssistantOrchestratorsContainer`, оркестраторы вебхуков каналов и виджета (им
  нужен пайплайн сообщения клиента) — в `ChannelPipelinesContainer`.
- Синглтоны: клиенты, адаптеры (в том числе все коллекции документов на одном пуле
  Postgres и одном `StorageScopeContext`, дочерний `DocumentCollectionsContainer`
  контейнера адаптеров), репозитории, реестры (замки и лимиты запросов —
  общие для всех процессов: advisory-блокировки и таблица `rate_limit_buckets`
  в Postgres, см. «Несколько процессов» ниже), фасилитаторы, пайплайн
  сообщения клиента. Use case, оркестраторы и операторы — фабрики.
- Журнал вызовов модели (`llm_trace_facilitator`) живёт в `AdaptersContainer`:
  `TracingLlmAdapter` оборачивает им маршрутизирующий адаптер модели, а
  фасилитаторы сами зависят от адаптеров.
- HTTP: `app/main.py` (фабрика uvicorn) и `app/gateways/http/router_assembly.py`.
  Миграции: `python -m app.gateways.cli.migrate` — шлюз командной строки, он
  запускает use case применения миграций (`app/gateways/cli/`).
  Фоновый воркер: `app/worker_main.py`, задачи перечислены в
  `app/containers/gateways.py`. Входящие (`process_inbound_message`,
  `process_platform_bot_update`, `process_post_call`) идут в полосе `inbound`,
  доставка исходящих (`deliver_outbound`) — в полосе `outbound`. В разработке
  без Postgres тот же воркер идёт потоком внутри API (`EMBEDDED_WORKER`,
  жизненный цикл в `app/main.py`): данные в памяти видны только своему
  процессу, а поставленная задача будит его сразу, поэтому ответ в
  разработке приходит без ожидания опроса очереди.

## Несколько процессов

API работает в нескольких экземплярах (`numInstances: 2` в `render.yaml`) рядом
с воркерами, поэтому ничто, от чего зависит правильность, не живёт в памяти
одного процесса:

- **Пул соединений и закрепление.** `PostgresConnectionPoolClient.pinned_connection()`
  закрепляет одно соединение за потоком на время блока: все операции хранилища
  этого потока внутри блока идут через него, вложенная транзакция становится
  точкой сохранения. Поток никогда не держит больше одного соединения, а
  запрос держит его мгновение, поэтому пул меньше числа потоков (по
  умолчанию `DB_POOL_SIZE` — половина `THREADPOOL_SIZE`); простаивающие
  соединения закрываются (`DB_POOL_MAX_IDLE_SECONDS`, до
  `DB_POOL_MIN_SIZE`). Сумма соединений всех процессов во время деплоя
  проверяется тестом `tests/platform/test_connection_budget.py`.
- **Единица работы.** `PostgresUnitOfWorkAdapter.unit_of_work()` (контракт
  `StorageUnitOfWorkContract`): одна транзакция на закреплённом соединении,
  область RLS задаётся в начале; каждая операция коллекции внутри — точка
  сохранения со своей областью, поэтому запись уровня платформы не оставляет
  обход RLS следующей записи бизнеса.
- **Блокировки** (`AdvisoryLockAdapterContract`, `app/adapters/locks/`):
  `hold_with_transaction` — `pg_advisory_xact_lock(hashtextextended(key, 0))`
  внутри единицы работы: запись брони и снятие блокировки бизнеса фиксируются
  вместе (`BusinessLockRegistry`), так же резерв отправки кода входа
  (`LoginCodeSendLockRegistry`). `hold_with_session` — `pg_advisory_lock` на
  закреплённом соединении на весь ход клиента (`CustomerMessageLockRegistry`,
  ключ business|channel|channel_user_id): ход вызывает модель, поэтому
  транзакция не держится открытой, а каждая запись хода фиксируется сразу.
  Ожидание ограничено (`lock_timeout`), ожидающие одного ключа в процессе
  стоят в очереди на локальной блокировке и не занимают соединения. Без базы
  те же реестры работают на блокировках процесса (`InMemoryAdvisoryLockAdapter`).
- **Лимиты запросов** (`RequestRateLimitRegistry` над
  `RateLimitBucketAdapterContract`): счётчики окон в таблице
  `rate_limit_buckets` (миграция 1041, `UNLOGGED`), запрос — один оператор
  `insert … on conflict do update … returning` по всем ключам в порядке
  ключей; запрос сверх лимита откатывается и нигде не засчитывается. Оценка —
  текущее окно плюс предыдущее с весом его части внутри скользящего окна
  (`app/utilities/limits/sliding_window_limits.py`); устаревшие счётчики
  удаляет задача `sweep_rate_limit_buckets` раз в 10 минут.
- **Потоки и модель.** Обработчики запросов — не больше `THREADPOOL_SIZE`
  потоков (ограничитель AnyIO задаётся при старте), вызовы модели — не больше
  `LLM_MAX_CONCURRENCY` в процессе (`ConcurrencyLimitedLlmAdapter`, вокруг
  трассирующего адаптера: ожидание места не попадает в трассу). Ход клиента
  сначала берёт место хода (`TurnSlotRegistry`, столько же мест), и только
  потом блокировку клиента, которая закрепляет соединение: ожидающий место
  ход соединения не держит.
- **Готовность.** `GET /readyz` отказывает (503), только если база не
  отвечает или не применена миграция сборки; занятый пул — `degraded` (200),
  отказ — лишь после 30 с подряд без свободного соединения.
- **Записи звонков** (`RecordingStorageAdapterContract`): с
  `RECORDINGS_STORAGE=s3` — `EncryptedObjectRecordingStorageAdapter` над
  S3-совместимым хранилищем в ЕС (`S3ObjectStorageClient`: запросы по ссылкам
  с подписью SigV4 на 60 с, чтение диапазонами байт). Запись шифруется до
  отправки (`app/utilities/security/recording_encryption.py`: ключ бизнеса —
  HKDF от `ENCRYPTION_KEY` и id бизнеса, ключ записи — HKDF от ключа бизнеса,
  соли и пути; AES-256-GCM блоками по 64 КиБ с номером блока и меткой
  последнего в AAD), поэтому диапазон плеера читает и открывает только свои
  блоки. После звонка задача `archive_call_recording` переносит запись из
  ElevenLabs в бакет (CAS по пути записи звонка: очистка по сроку или
  удаление контакта в это время побеждают) и удаляет разговор у ElevenLabs.
  Локальные файлы (`LocalRecordingStorageAdapter`) — только разработка.
- **Проверка.** `tests/storage/test_two_processes.py` запускает два процесса API
  (uvicorn) и воркеры на одной тестовой базе: последнюю бронь получает ровно
  один, лимит виджета общий, ответы одному клиенту идут по очереди.
  `tests/storage/test_worker_pickup.py`: сообщение, принятое API, отдельный
  воркер берёт за 500 мс; `tests/storage/test_widget_burst.py`: 64 медленных
  хода виджета разом, а `/readyz` остаётся 200 и кабинет отвечает быстро.
