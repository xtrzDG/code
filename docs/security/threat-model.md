# Threat model

Assistant Workshop answers the customers of small businesses on their
behalf and keeps their conversations, contacts, bookings and call
recordings. This document names what we protect, where data crosses a trust
boundary, and, threat by threat (STRIDE), the mitigation with the code that
implements it and the test that proves it. Every path below is checked to
exist by `tests/legal/test_security_documents.py`, so a moved file breaks
the build instead of silently breaking the model.

Reviewed: 2026-11-03. Review it with every new external integration, every
new kind of personal data and at least once a quarter, together with the
access review (`docs/security/access-review.md`).

## Assets

| Asset | Why it matters |
| --- | --- |
| Customers' conversations, contacts, bookings and call recordings | Personal data of people who never signed up with us (DPA section 3) |
| Owner and staff accounts, sessions and authenticators | They open every tenant's data and settings |
| Channel credentials (WhatsApp, Telegram, Instagram, Messenger, calendar tokens) | They let an attacker speak as the business |
| Platform admin and support access | Read access across tenants |
| The language model's instructions and tools | They decide what the assistant says and books |
| Billing records and invoices | Money and tax obligations |
| Backups and the encryption keys | A copy of everything |

## Trust boundaries

```
 Customers ──(messengers, widget, phone)──▶ [B1 webhooks & widget API] ──┐
                                                                          ▼
 Owners/staff ─▶ [B2 cabinet: Next.js BFF] ─▶ [B3 API] ─▶ [B5 Postgres, RLS per business]
                                                │   │
 Platform admins ─▶ [B8 admin & support access]─┘   ├─▶ [B6 sub-processors: LLM, voice, e-mail, SMS, S3]
                                                    └─▶ [B7 model output ▶ tools]
 Source code ─▶ [B9 CI/CD and dependencies] ─▶ images on Render
```

| Boundary | What crosses it | Who is on the other side |
| --- | --- | --- |
| B1 Webhooks and the widget API | Customer messages, call events, payment results | Anyone on the internet, messaging platforms, Flitt, ElevenLabs, Zadarma |
| B2 Cabinet (BFF) | Owners' and staff's clicks, the session cookie | Browsers, including hostile pages in other tabs |
| B3 API | Bearer tokens, JSON bodies | The BFF, the widget, scripts |
| B5 Database | Every tenant's rows | The API and the worker, scoped per business |
| B6 Sub-processors | Messages to the model, audio, e-mail and SMS, recordings | The providers listed in DPA section 8 |
| B7 Model output | Replies and tool calls written by a language model | Prompt-injected customer text |
| B8 Platform administration | Cross-tenant reads, support sessions, the platform's pause | The platform team (each admin role's permissions: `docs/security/permission-matrix.md`) |
| B9 Supply chain | Dependencies, actions, images | Package registries, GitHub Actions |

Every entry point and its access class (HTTP routes, webhooks, cabinet
route handlers, worker jobs and commands) is listed in
`docs/security/entry-points.json`, generated by
`scripts/entry_point_inventory.py`; `tests/platform/test_entry_point_inventory.py`
fails when it is stale or a new route has no class. What the running
service refuses and limits at each boundary, with its code and tests:
`docs/security/runtime-protections.md` and
`docs/security/product-protections.md`.

## Accepted risks and follow-ups

- Single region: the service, its database and the language model run in the
  EU only; a regional outage stops the service (docs/operations/slo.md).
- Sub-processors outside the EEA rely on the transfer mechanisms the DPA's
  list now publishes per sub-processor (DPF, SCCs, BCRs), with the
  transfer register's dates and the evidence still to file (TIAs, DPF
  screenshots: `docs/operations/vendor-register.md`); Zadarma's location
  is to be confirmed in its contract. Telegram receives customers'
  messages outside the EEA without SCCs, only when a business turns that
  channel on
  (`docs/security/data-classification.md`, `docs/operations/vendor-register.md`).
- No external penetration test yet: commission one before the first paying
  clients outside the pilot, and after every major change of the trust
  boundaries above.
- Separate origins and envelope encryption are roadmap items
  (`docs/security/roadmap.md`): the cabinet, the marketing site and the
  customers' chat and booking pages share one origin, customers' media is
  served from the API's origin under a sandbox CSP, the admin console has
  no host of its own, and channel credentials are sealed with keys from
  the hosting provider's secret store (no KMS; the API holds the key ring
  as well as the workers). One maintainer: no independent review of
  security changes until a second one joins (SDLC-05).
- The audit log is tamper-evident, not tamper-proof against the tables'
  owner: the migration role (DATABASE_URL) owns the audit tables and
  `workshop.purge_audit_chain`, so a leaked migration-role password can call
  the purge (only for entries older than 365 days: the function refuses a
  younger cutoff), grant itself DELETE again, drop the trigger, or rewrite
  a chain from some entry on with fresh hashes. The application's two
  roles (migration 1200) own nothing, may not call the purge and may only
  read and insert entries, so a compromised application can do none of
  this. The daily check logs each chain's newest verified entry (chain and
  hash only) to the log aggregator, outside the database, and finds an end
  that was cut off or rewritten after a check (`head_lost`, also when a
  checkpoint covers it with a cutoff younger than 365 days); shipping the
  chain heads to a store the owner cannot write (row 7) remains open.
  Follow-up: the release after 1200 revokes the owner's UPDATE on the three
  audit columns the previous release's upsert needs
  (docs/operations/deploys.md).
- The tenant role keys row-level security on `app.business_id`, which
  the session sets for itself (migration 1200): a SQL injection on a
  tenant connection could run `set app.business_id = '<other id>'` and
  then read or change that business's rows, and business ids are not
  secret (the website widget publishes its own). What the role closes is
  the bypass switch and every table whose rows name no business (people,
  sessions, factors); every statement is parameterized, so no injection is
  known. Follow-up: set the scope through a signed or SECURITY DEFINER
  function the tenant role cannot imitate.
- The website chat's allowed sites are opt-in: a business without a list
  still serves its chat on any site, and the check reads `Origin` (else
  `Referer`), which only browsers set honestly. A script without either
  header passes; the widget's limits per visitor, network and business and
  the business's daily spend limit bound it (row 13).
- Spend limits are checked before each model turn and call against the
  business's day: a turn or call already under way finishes past the
  limit, and a cost a provider reports late is counted at the planned
  price until it arrives. The platform's daily budget warns at 80% and
  stops every assistant at `PLATFORM_DAILY_SPEND_STOP_PERCENT` (row 25), but
  the reading is cached a minute per process, so up to a minute of spend
  per process passes the stop, and calls already under way run to their
  end. `render.yaml`'s budget of 50 dollars is therefore a hard daily stop
  until the operator sizes it (docs/operations/runbooks/platform-brakes.md).
  Conversations handed to the team during a pause or a stop stay with the
  team after the resume. A call that ends while a brake holds keeps no
  summary and no memory (skipped, not queued again), and an autotest run
  the brake skipped reads as ERRORED; an "Apply changes" whose checks it
  skipped waits for the owner as "checks stopped" and nothing goes live
  (tests/setup/test_apply_under_brake.py); the owner applies again once
  the brake lifts.
- No account deletion in the cabinet: a person cannot delete their account,
  nor an owner the business with all its data; it is done by the platform
  team on request (DPA section 13). Closed by R15-ACCOUNT-DELETION.
- Configuration: a Render service whose `APP_ENV` was overridden to
  `development` or `test` starts with development's leniency (the preview
  stand needs it); the address check refuses localhost and loopback, not
  private-network addresses, which are operator settings, not attacker
  input.
- Logs mask e-mails and `+` phone numbers in messages, not bare digit runs
  (ids, amounts, WhatsApp ids without `+`), exception tracebacks or
  structured fields.
- Webhook flood budgets and the widget's config budget count per process
  (times `WEB_CONCURRENCY`) and per client network, so carrier-grade NAT
  may share one; `authorization_denied` lines are bounded only by the
  per-address limit. A route given up with a 504 that fails afterwards is
  only logged. The Zadarma `call_start` format and ElevenLabs' tolerance
  come from samples, not their documentation (not reachable from the
  build environment): confirm both.
- The AI agent's caps per contact (5 leads, 3 staff alerts) can be dodged
  by a website visitor who rotates the visitor key; an emergency always
  alerts. The link check is heuristic (obfuscated or scheme-less non-Latin
  domains pass) and the team-note check catches only verbatim runs of five
  or more words, not paraphrases or translations.
- The voice platform's behaviour with authentication on phone calls and
  the transfer to the `transfer_number` variable are taken from its SDK
  schema, not yet confirmed on staging. The Twilio fallback dial rings
  the staff mobile also outside opening hours (a plain carrier dial, no
  recording or AI). The greeting's privacy sentence says only that the
  notice is on the business's web page, not its address. Switching
  recording off reaches the agent's own `record_voice` setting at the
  next hourly `resync_voice_agents` run: until then ElevenLabs may record
  a call's audio, which the platform discards after the call (the greeting
  changes at once).
- Cabinet: `Clear-Site-Data` at sign-out clears every
  cookie of the registrable domain, also those of sibling services. A
  self-hosted proxy that rewrites `Host` to localhost, sets no forwarded
  headers and runs with `COOKIE_SECURE=false` still gets cookies without
  `Secure` (the Render Blueprints set `COOKIE_SECURE=true` and ask for
  `SITE_URL`).
- Guest links: manage links of the older 96-bit version open until their
  own expiry, with no hard cut-off. The booking page's 30-minute
  credential has one way back to the long-lived link: its calendar file
  (`…/calendar.ics`) embeds a freshly signed manage link on purpose, so
  the guest's calendar entry keeps working; whoever holds a credential can
  therefore get the link for the rest of its life. During a deploy an
  older release cannot read the credentials, and reopening the link fixes
  the page. A booking page shows a ticked
  marketing box even while the guest's STOP blocks messages (the card in
  the cabinet says "stopped"). A rollback to the release before the
  consent record (ContactDocument v4) drops the record on that release's
  saves: no marketing, but the proof is lost. Consent scope is an open
  owner and legal decision: the consent is the contact's, so a consent
  ticked on booking A's page also covers a campaign anchored on a later
  booking B made in another messenger (B's chat), every later booking's
  page shows the box ticked, and the box is offered on phone and
  website-chat bookings, whose chats never carry a campaign.
- Sessions: a sweep (factor removal, owner promotion or enrollment) that
  runs between a rotation's wind-down of the old session and the save of
  the new one does not see the new session, so that token can keep two
  factors past a concurrent factor removal; only the client that made the
  proof holds it, as with a sign-in during a sweep (closing it needs an
  atomic user-wide sweep or a session generation counter). The old token
  answers 30 seconds more as one factor. A cabinet older than the API
  sends no ticket, so a raising proof leaves its session one factor until
  the new cabinet loads. A platform admin's view of a member's sessions
  still lists the winding-down token for those 30 seconds, and owner
  rights given at brand level end no sessions. When the second sweep of
  an owner promotion or invitation fails, the change is already stored and
  a session opened between the two sweeps stays (a retry changes nothing).
- Calls and text-backs: refusals by number fail closed across every
  contact holding it, typed phones included: a website-chat visitor who
  typed someone else's number and then said STOP or was blocked
  suppresses that number's text-backs and refuses its calls. Data written
  by earlier releases is not cleaned: call-only contacts whose verified
  phone came from a caller ID (a messenger customer who proves that number
  can still be joined to one), and messenger contacts a text-back gave a
  PHONE identity (their numbers get a new per-call contact on every
  call). A customer who proved the number on another channel gets a
  separate WhatsApp contact from a text-back, so the card can split; the
  text-back still moves the number's WhatsApp customer up the customer
  list (ordering only). Assistant versions published before this release
  keep their stored phone instruction, which still names the booking-change
  tools and the recording sentence, until they are published again (the
  agents lack those tools and the webhook refuses them). Links and
  confirmations are texted after a call only when the call's own contact
  has a messenger, which call-only contacts never have: texting
  messenger-only callers again is an owner decision. The anonymous
  booking cap (10 a day per client network, platform-wide) can catch
  visitors behind one carrier-grade NAT together; a per-business key is
  an owner decision.
- Platform operations: the reconciliation compares only a Flitt order's
  first payment (later automatic charges are Flitt's own orders) and runs
  serially on the default lane; the pause and its audit entry are two
  writes, not one transaction; the tenant check of queued jobs reads only
  the payload's top-level `business_id`. Switching off a Meta channel
  unsubscribes the page and erases the token, but Meta has no call to
  revoke the token itself.
- CI/CD: repository admins can edit the `release` ruleset and the
  environments; the daily check sees reviewers and branch rules, not a
  ruleset's bypass actors or a reviewer team's members (the quarterly
  access review does). The rollback force push needs a temporary admin
  bypass (docs/operations/deploys.md, "Rollback"; the services roll back
  in one command, `scripts/rollback.py`, whose Render API calls are to be
  confirmed in the first rollback drill). Images pinned in
  workflow `services:` move only by hand. The Lighthouse CI tool's tree
  carries high npm advisories with no compatible fix; it runs only on CI
  runners (`SECURITY.md`, accepted findings).
- `SUPPRESSION_LIST_KEY` has no re-keying: rotating it orphans the stored
  digests of opted-out numbers.
- Payments and cards: a payment webhook answers 200 `queued` once the
  job is stored, so the provider never sends it again; a job that still
  fails after its 5 attempts (about 7.5 minutes of backoff, for example an
  approval Flitt's status API does not confirm yet) is dead: only the
  `dead_jobs` alert and the daily `payment_mismatch` reconciliation catch
  it, and nothing re-queues it by itself (accepted; an admin re-queue is
  open). The job runs on the default lane, beside exports and integration
  webhooks, so a busy lane can delay a payment by minutes. Stripe (behind
  the closed `stripe_payments` gate) still reads the card from Stripe
  inside the request for two events, and its refund and dispute events are
  not mapped yet. The card-testing watch counts on an exact 5th and 10th
  decline, so two concurrent declines can step over the alert (the brake,
  at 10 or more, still holds), a retried job can count a decline twice,
  the counts live in the UNLOGGED `rate_limit_buckets` table, deposit
  pages (the businesses' own merchant links) are not watched, and the
  cabinet shows its generic error on the 429. A billing page reached by
  in-app navigation keeps the policy of the page it was opened from, which
  still names Turnstile's host in `connect-src` and `frame-src`; Next.js's
  SRI attributes are not on (the weekly SHA-384 check stands in), the
  Sentry alert on CSP violations is an owner step, and whether CI's build
  gives the inventory's hashes is unconfirmed (the pull request step would
  warn on every run). Card masking works on text: a card photo still reaches the
  model and storage, a card typed over several chat messages is masked
  message by message, the live voice model hears the digits, and messages
  and transcripts stored before masking are not rewritten.
- Supply chain: the registry check does not measure a change of the
  package index itself (`[[tool.uv.index]]`, `index-url`, `registry=` in
  `web/.npmrc`); those rest on the review of `.github/` and the dependency
  review. The new e2e checks of the middleware header and the billing
  page's policy run only in CI's shards.
- Tenant isolation: the generated matrix covers the public API's 14
  operations; the AGENCY role still has a few hand-written tests rather
  than a per-route matrix, and the customer-token routes
  (`/v1/public/bookings/{token}`, `/v1/widget/{business_id}/…`) are not
  tried with another business's ids.
- Audit purge: the platform role may now execute
  `workshop.purge_expired_audit_chain`, so a compromised platform role can
  remove audit entries older than 1,095 days, which the retention removes
  anyway; it cannot touch newer entries or call `workshop.purge_audit_chain`,
  and each removal leaves a checkpoint and a `retention_purge` entry.
  Inactivity-based retention for contacts and their marketing consents is
  not implemented (a product decision).
- Customers' data rights: items a brand shares are searched only as each
  location's copy, and a later brand sync can drop a copy's flag while the
  brand's text still names the customer. The exported texts can hold other
  people's data: the owner redacts them before handing the copy over
  (art. 15(4)).
- Health notes: the detector is keyword-based (a missed word leaves the
  note as before; a false match only hides it), dietary needs that reveal
  a religion are not detected, the notes are not encrypted at rest, and
  explicit-consent wording or structured allergy fields in the assistant's
  booking flow are an open product decision.
- Sign-in throttle: it can be used to grief sign-ups. Some dozen unused
  new-phone codes into a country (each behind a Turnstile pass) hold that
  country's new-phone sign-ups at 10 an hour for six hours; verified
  owners and e-mail sign-in are not affected and the platform team is
  alerted (`country_conversion`). Exempting the home market is an owner
  decision. The first burst before any code expires is bounded only by the
  static caps and Turnstile, and the six-hour lookback is read under the
  send lock for every code to a new phone.
- Calls: changing or cancelling a booking by voice stays refused on
  purpose (a caller ID proves nobody), a caller no messenger reaches gets
  no transcript (no SMS fallback), and there is no live voice evaluation
  of repeat, slower speech or transcript requests.
- Campaigns: bounce and complaint feedback loops are not measured (only
  STOP and consent withdrawals), owners see no "held" banner in the
  cabinet (only the notice), and the owner's settings save is a
  read-modify-write, so a hold that lands between its read and write is
  dropped until the next hourly run puts it back. Know-your-business
  checks before number rental and a trial cap on messenger messages are
  open, as are a platform network blocklist, a Turnstile challenge on the
  widget and the hosted chat (ABUSE-03) and a verification step for large
  public bookings (ABUSE-04).
- Evaluations and releases: the merge gate replays recorded answers, so a
  real model's drift shows only in the nightly run after the merge, and
  the hallucination rate has been measured only on the scripted model (0 %
  by construction) until the real-model baselines are recorded with the
  provider keys; invented values are matched as substrings. No code path
  reads a feature flag yet, a flag's inclusion and exclusion lists have no
  length cap (SUPER and a recent sign-in only), the customer turn slots
  and `LLM_MAX_CONCURRENCY` are per process, not per business, and the
  product error budgets leave booking success unmeasured (no Prometheus
  series) and count calls answered from webhook requests, a proxy.
- The assistant: the booking-claim guard and the memory filter read
  English patterns (summaries are written in English); switched-off tools
  are still offered to the model and refused when called; outbound actions
  outside the assistant's tools (waitlist offers, campaigns, text-backs,
  transfers) have no switch of their own.
- Sign-in: owners may skip the second-factor prompt and the team-wide
  requirement stays the owner's choice; an admin holding a passkey can
  still answer with a single-use recovery code; equal response timing of
  the sign-in code request is not measured.
