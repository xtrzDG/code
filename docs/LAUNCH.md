# Запуск Assistant Workshop

Пошаговая инструкция для владельца проекта: попробовать продукт на своём
компьютере, поднять рабочую версию на Render в Европе (Франкфурт), завести
внешние аккаунты и вписать их ключи. Названия переменных, адреса вебхуков и то,
что происходит без ключа, взяты из репозитория: `.env.example`, `render.yaml`,
`docker-compose.yml`, `README.md`, `web/README.md`, настроек приложения
(`app/utilities/config_helpers/app_settings/`) и `docs/legal`. Полный
список переменных с поведением по умолчанию — таблица «Окружение» в
[`README.md`](../README.md#окружение); тест
`tests/platform/test_environment_variables.py` не даёт ей разойтись с кодом.

Два адреса встречаются в тексте постоянно:

- **адрес API** — публичный https-адрес бэкенда, значение `APP_BASE_URL`
  (на Render, например, `https://workshop-api.onrender.com`);
- **адрес кабинета** — публичный адрес кабинета владельца, значение
  `CABINET_BASE_URL` (например, `https://workshop-cabinet.onrender.com`).

Адреса вебхуков ниже записаны как «адрес API + путь»: для примера выше вебхук
Meta — `https://workshop-api.onrender.com/v1/channels/meta/webhook`.

## 1. Что вы получаете

| Часть | Что делает | Как запускается |
| --- | --- | --- |
| Бэкенд (API) | Мозг продукта: кабинетные данные, анкета, сборка помощника, ответы клиентам, вебхуки мессенджеров, голоса и оплаты, виджет сайта, вход по коду | образ из `Dockerfile`, команда `workshop api` |
| Фоновый воркер | Ответы клиентам в мессенджерах и после звонков (вебхуки только сохраняют сообщения во входящие), доставка ответов и уведомлений персоналу с повторами, автотесты версий помощника, импорт знаний с сайта бизнеса, напоминания клиентам о бронях, окончание пробных и льготных периодов, предупреждения о расходе пакета, перенос записей звонков в хранилище ЕС (при `RECORDINGS_STORAGE=s3`) и удаление старых, очистка истёкших сессий, кодов входа и квитанций вебхуков, отправка журнала модели в Langfuse | тот же образ, команда `workshop worker` |
| Кабинет владельца | Сайт для владельцев и сотрудников: вход по номеру телефона любой страны или по почте, анкета из шести шагов, сводка, разговоры, брони, заявки, передачи, знания, помощник (тестовый чат, версии, публикация), каналы, оплата, настройки и админка платформы. Языки интерфейса — грузинский, русский, английский | образ из `web/Dockerfile` |
| Виджет сайта | Кнопка чата на сайте бизнеса; код для вставки выдаёт кабинет («Каналы» → «Чат на сайте» → «Включить», затем «Код чата для сайта»): `<script src="<адрес API>/widget.js" data-tenant="<id бизнеса>" async></script>` | его отдаёт API |
| База данных | Postgres 16 с изоляцией данных каждого бизнеса; миграции применяются сами перед каждым деплоем API | на Render — управляемая база во Франкфурте |

Браузер владельца не ходит в API напрямую: сервер кабинета обращается к API по
адресу `BACKEND_URL` и хранит токен входа в защищённой cookie.

## 2. Проба на своём компьютере

Нужны [Docker](https://www.docker.com/) (Docker Desktop, в нём уже есть Docker
Compose) и копия репозитория. В папке репозитория:

```bash
cp .env.example .env            # необязательно: в этот файл пишутся ключи
docker compose up --build       # первый раз собирает образы, это несколько минут
```

Поднимаются Postgres 16, миграции, API (<http://localhost:8000>), воркер и
кабинет (<http://localhost:3000>). Остановить — `Ctrl+C` или
`docker compose down`; удалить всё вместе с данными — `docker compose down -v`.
Если порты заняты, задайте в `.env` другие: `API_PORT`, `WEB_PORT` (адреса API и
кабинета в настройках Compose следуют за ними).

### Вход без SMS

Локально работает режим разработки (`APP_ENV=development` задан в
`docker-compose.yml`): пока провайдер кодов не настроен, код входа пишется в лог
API.

1. Откройте <http://localhost:3000>, выберите страну и введите свой номер (или
   переключитесь на вход по почте).
2. В другом окне терминала, в той же папке: `docker compose logs -f api`.
3. Найдите строку `Login code 123456 via … Code logging is for development only.`
   — шесть цифр после `Login code` и есть код. Введите его в кабинете.

В рабочей версии (`APP_ENV=production`) коды никогда не пишутся в лог: там нужен
хотя бы один провайдер кодов (раздел 4.3).

### Что работает без ключей

Без единого ключа работают вход, создание бизнеса, анкета, знания (кроме
импорта меню и импорта с сайта), брони вручную, команда, настройки и предпросмотр виджета
(«Каналы» → «Чат на сайте» → «Включить», затем «Код чата для сайта» → «Открыть
живой предпросмотр»). Всему, что читает или пишет текст,
нужна модель: тестовый чат, автотесты, импорт меню и ответы клиентам без ключа
заканчиваются ошибкой 502 (импорт с сайта — сообщением «Сервис чтения сейчас
недоступен»). Чтобы их попробовать, впишите в `.env` ключи OpenAI
(раздел 4.2):

```bash
OPENAI_API_KEY=sk-...
OPENAI_PROJECT_ID=proj_...
```

и выполните `docker compose up -d` — Compose пересоздаст контейнеры с новыми
значениями.

Чтобы увидеть «Админку», впишите в `.env` свой номер в международном формате,
например `PLATFORM_ADMIN_PHONE_NUMBERS=+995555123456`, выполните
`docker compose up -d`, выйдите из кабинета и войдите снова.

### Демо-данные: как выглядит живой бизнес

Чтобы сразу посмотреть кабинет с данными, а не пустым, впишите в `.env`

```bash
SEED_DEMO_DATA=true
PLATFORM_ADMIN_PHONE_NUMBERS=+995555000001
```

и выполните `docker compose up -d`. При запуске API один раз создаст
демо-владельца и два бизнеса: ресторан «Mtsvane Ezo» в Тбилиси (около 40
переписок за месяц на пяти языках, брони, заявки, передачи сотрудникам,
звонок с расшифровкой, пробный период) и салон красоты «Studio Lindenblatt» в
Берлине. Войдите с номером `+995 555 00 00 01` или почтой `demo@example.com` —
код, как обычно, в `docker compose logs -f api`. Сотрудник ресторана входит с
номером `+995 555 00 00 02`. Повторный запуск ничего не дублирует. В рабочей
версии (`APP_ENV=production`) эта переменная запрещена: API не запустится, пока
её не уберёте.

### Ограничения пробы

- Внешние сервисы (Telegram, Meta, ElevenLabs, Flitt, Google) не достучатся до
  `http://localhost:8000`: мессенджеры, звонки, оплату и календарь проверяйте в
  рабочей версии.
- `docker-compose.yml` задаёт общий для API и воркера ключ шифрования
  `ENCRYPTION_KEY`. Его значение по умолчанию общеизвестно и годится только для
  пробы на этом компьютере (с `APP_ENV=production` API его не принимает). Перед
  подключением настоящих каналов впишите в `.env` свой ключ (раздел 4.1) и больше
  его не меняйте.
- Все входы через кабинет приходят в API с одного адреса контейнера кабинета,
  поэтому Compose разрешает 100 кодов входа в час с адреса (в рабочей версии —
  `OTP_SENDS_PER_IP_PER_HOUR`, по умолчанию 10).

## 3. Рабочая версия на Render (Франкфурт, ЕС)

[Render](https://render.com) — хостинг, на котором файл `render.yaml` (Blueprint)
создаёт всё сразу и только в регионе Frankfurt, как требует концепция для
персональных данных:

| Ресурс | Что это |
| --- | --- |
| `workshop-db` | управляемый Postgres 16, доступен только изнутри Render |
| `workshop-api` | API; перед каждым деплоем применяет миграции (`workshop migrate`), трафик получает, только когда `/readyz` отвечает 200 (база отвечает, миграции применены; занятый пул — «degraded», но трафик идёт) |
| `workshop-worker` | фоновый воркер из того же образа |
| `workshop-cabinet` | кабинет владельца |

### Шаги

1. Зарегистрируйтесь на Render и подключите GitHub-аккаунт, где лежит
   репозиторий.
2. Заранее заведите аккаунты, обязательные для запуска (раздел 4: модель, хотя бы
   один провайдер кодов входа, уведомления сотрудникам) — Render спросит их ключи
   при создании.
3. Создайте ветку `release` (`git push origin main:release`, см. «Деплой только
   после проверок» ниже), затем в Render нажмите **New → Blueprint** и выберите
   репозиторий. Render прочитает
   `render.yaml` и попросит значения секретов (в файле они помечены
   `sync: false`). Впишите те, что уже есть; ненужные и пока неизвестные
   (адреса API и кабинета) оставьте пустыми — их можно добавить позже в
   настройках переменных сервиса. `ENCRYPTION_KEY` Render сгенерирует сам: не
   меняйте его никогда, иначе сохранённые токены каналов станут нечитаемыми.
4. Дождитесь первого деплоя всех четырёх ресурсов.
5. Посмотрите публичные адреса сервисов `workshop-api` и `workshop-cabinet` и
   задайте:
   - у `workshop-api`: `APP_BASE_URL` — адрес API; `CABINET_BASE_URL` — адрес
     кабинета; `CORS_ALLOWED_ORIGINS` — тот же адрес кабинета;
   - у `workshop-cabinet`: `BACKEND_URL` — внутренний адрес API из панели Render
     (`workshop-api` → Connect → Internal) с `http://` и портом 8000, например
     `http://workshop-api:8000`. Публичный адрес API сюда не подходит: запросы
     кабинета пойдут через интернет, API увидит вместо адресов владельцев один
     исходящий адрес Render, и все входы упрутся в лимит
     `OTP_SENDS_PER_IP_PER_HOUR` (10 кодов в час с адреса), а журнал аудита
     запишет адрес кабинета.

   Воркер копирует у API только ключи, перечисленные в `render.yaml`
   (`fromService` копирует по одному ключу): те, что Blueprint спросил при
   создании. Все остальные переменные (тонкая настройка модели,
   `OPENAI_BASE_URL`, `LANGFUSE_HOST`, `RECORDING_RETENTION_DAYS`,
   `WORKER_POLL_SECONDS` и т. п.) задавайте в группе окружения
   `workshop-backend` (Render → Environment Groups): её читают и API, и
   воркер. Заданные только у `workshop-api`, они до воркера не дойдут —
   например, автотесты пойдут на модели по умолчанию. После изменения
   переменных заново задеплойте API, воркер и кабинет, чтобы они прочитали
   новые значения.
6. Зарегистрируйте адреса вебхуков во внешних сервисах (раздел 4) — теперь адрес
   API известен.
7. Сделайте себя админом платформы (раздел 4.1) и пройдите проверку из раздела 7.

Свой домен: если подключите к сервисам Render свои домены, впишите их во все
переменные выше и в адреса вебхуков.

### Деплой только после проверок

Сервисы из `render.yaml` берут код из ветки `release` и разворачивают коммит,
только когда все проверки GitHub (CI) по нему прошли. Поэтому **до** шага 3
создайте эту ветку: `git push origin main:release`. Дальше новая версия
попадает в рабочую так:

1. Изменения сливаются в `main`, CI проверяет их.
2. Окружение staging (`render.staging.yaml`, создаётся так же: New → Blueprint,
   путь к Blueprint — `render.staging.yaml`) разворачивает `main`. Там своя база
   и `LLM_PROVIDER=scripted`: вместо модели — репетиция (помощник отвечает на
   языке клиента, что он тестовый, бронирует первое свободное время и зовёт
   человека, когда просят; проверки «Применить изменения» проходят),
   без модели и без оплаты за сообщения (`SCRIPTED_LLM_LATENCY_MS` задаёт ему
   задержку настоящего провайдера только для нагрузочных тестов, см.
   `docs/operations/capacity.md`; на staging оставьте 0).
3. После деплоя GitHub Actions запускает `scripts/smoke.sh`: здоровье API,
   скрипт виджета, варианты входа, кабинет и тестовый чат через виджет.
4. Если на staging всё зелёное, тот же коммит переносится в `release`, и его
   разворачивает рабочая версия; после неё проверка запускается ещё раз.

Без staging переносите проверенный коммит сами:
`git push origin <коммит>:release`. Настройка окружений GitHub, правила
изменения данных между версиями, `workshop migrate-documents` и откат на
прошлую версию — в `docs/operations/deploys.md`.

Полезно знать:

- API работает в двух экземплярах (`numInstances: 2` в `render.yaml`): деплой
  или упавший экземпляр не останавливает ни кабинет, ни виджет. Всё общее у
  экземпляров живёт в базе — подробности в разделе «Несколько экземпляров API»
  ниже.
- Фоновый воркер — отдельный сервис `workshop-worker`. Экземпляров может быть
  несколько, и при деплое старый и новый воркеры спокойно работают рядом: задачу
  из очереди берёт только один воркер (с арендой), задачу упавшего воркера
  подхватывает другой, а ежедневные задачи (напоминания, сводки) выполняются один
  раз в день, даже если воркер перезапустился. Сколько задач каждой полосы один
  воркер выполняет одновременно, задаёт `WORKER_LANE_CONCURRENCY` (по умолчанию
  `inbound=8,outbound=4,default=2,autotests=2`). `EMBEDDED_WORKER` не задавайте:
  по умолчанию (`auto`) воркер работает внутри API только при разработке без
  базы, а значение `true` в рабочей версии (`APP_ENV=production`) API отклоняет
  при запуске.
- Без работающего воркера сообщения из Telegram, WhatsApp, Instagram и
  Messenger принимаются и хранятся, но ответ уходит, только когда воркер
  запущен. Ответ, который провайдер не принял (отказ `4xx`, отозванный токен)
  или не принял за 8 попыток, отмечается у канала ошибкой в кабинете, а
  разговор передаётся человеку.
- Задачи, которые так и не удались после пяти попыток, видит платформенный
  админ: `GET /v1/admin/jobs?status=dead`; перезапуск —
  `POST /v1/admin/jobs/{job_id}/retry`, отказ — `POST /v1/admin/jobs/{job_id}/discard`
  (оба пишутся в журнал аудита). Завершённые задачи удаляются через 30 дней.
- Изменения только в `docs/` Render не собирает: тексты договора попадают в образ
  только при новой сборке. Новую версию договора включайте так: закоммитьте
  файлы, затем задайте `DPA_DOCUMENT_VERSION` у `workshop-api` через «Save,
  rebuild, and deploy» (не «Save and deploy»: тот берёт старую сборку без новых
  файлов) или сделайте Manual Deploy → «Deploy latest commit» (раздел 5).
- `render.yaml` сам задаёт API порт (`PORT=8000`) и адреса доверенных прокси
  (`FORWARDED_ALLOW_IPS`), а кабинету — `COOKIE_SECURE=true` и
  `TRUSTED_PROXY_HOPS=1`; менять их не нужно.

### Несколько экземпляров API

Два экземпляра API (и любое число воркеров) работают с одной базой, и всё,
что раньше держалось в памяти одного процесса, теперь общее:

- **Брони.** Проверка свободного места и запись брони идут под блокировкой
  бизнеса в Postgres (`pg_advisory_xact_lock`) в одной транзакции: двое
  клиентов в разных экземплярах не займут последний столик.
- **Сообщения одного клиента** отвечаются по одному, где бы ни пришли
  (виджет в любом экземпляре, Telegram или WhatsApp через воркер): ход
  держит блокировку клиента в Postgres (`pg_advisory_lock`) от первого
  вызова модели до сохранённого ответа.
- **Коды входа.** Проверка часовых лимитов и резерв отправки кода идут под
  одной блокировкой на всю платформу.
- **Лимиты запросов** (сообщения и опрос виджета, отчёты об ошибках
  виджета, проверки кода входа) считаются в таблице `rate_limit_buckets`
  (миграция 1041), а не в памяти экземпляра: два экземпляра не удваивают
  то, что может отправить скрипт. Устаревшие счётчики раз в 10 минут
  удаляет задача воркера `sweep_rate_limit_buckets`.
- **Записи звонков**, которые платформа хранит сама, лежат в объектном
  хранилище ЕС (`RECORDINGS_STORAGE=s3`, раздел 4.6), а не на диске
  экземпляра; без него записи остаются у ElevenLabs.

Блокировка, которую не удалось получить за отведённое время (бронь — 10 с,
ход клиента — 150 с), заканчивается ошибкой запроса, а не зависанием; если
процесс упал, Postgres сам снимает его блокировки.

## 4. Аккаунты и ключи

Сначала сводка, затем каждый сервис: зачем он, где его завести, какие переменные
вписать (на Render — ключи, которые спросил Blueprint, у `workshop-api`, воркер
скопирует их сам; остальные — в группе окружения `workshop-backend`; локально — в
`.env`), какие адреса зарегистрировать у сервиса и нужен ли он для запуска.

| Сервис | Зачем | Для запуска |
| --- | --- | --- |
| Render | хостинг | обязательно |
| Ключ шифрования, адреса, админ (4.1) | основа работы | обязательно |
| OpenAI или Anthropic (4.2) | модель, которая отвечает клиентам | обязательно одно из двух |
| Twilio SMS, WhatsApp, Telegram Gateway, почта (4.3) | коды входа в кабинет | обязательно хотя бы один |
| Бот платформы в Telegram или шаблон WhatsApp (4.4) | уведомления сотрудникам о передачах, бронях и заявках | обязательно хотя бы один |
| Meta (4.5) | WhatsApp, Instagram и Messenger бизнесов | по желанию: без него работают Telegram и чат на сайте |
| ElevenLabs и Zadarma (4.6) | звонки | для тарифов «Голос + чат» и «Плюс» |
| Flitt (4.7) | оплата подписок | до конца первых пробных периодов (14 дней) |
| Google Calendar (4.8) | брони в календаре бизнеса | по желанию |
| Langfuse (4.9) | журнал каждого ответа модели | по желанию, рекомендуется |
| Sentry (4.9) | неожиданные ошибки | по желанию, рекомендуется |

### 4.1. Основа: ключ шифрования, адреса, админ платформы

**Ключ шифрования `ENCRYPTION_KEY`** — обязателен. Им шифруются токены каналов
(ботов Telegram, страниц Facebook). На Render генерируется сам. Для своего
сервера или локального `.env` — ключ Fernet или любая случайная строка от 32
символов, например:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

API и воркер должны работать с одним и тем же ключом. Заменить его на месте
нельзя (сохранённые токены перестанут открываться), но ключ можно сменить
плавно — через `ENCRYPTION_KEYS` и перешифровку (раздел 4.11). В рабочей версии
без ключа API не запускается, как и с общеизвестным значением по умолчанию из
`docker-compose.yml`.

Той же командой удобно придумать и `META_VERIFY_TOKEN` (раздел 4.5) — секрет,
который вы задаёте сами.

**Адреса** — обязательны:

| Переменная | Где | Значение |
| --- | --- | --- |
| `APP_BASE_URL` | API | адрес API: на нём работают вебхуки, виджет и оплата. Без него нельзя подключить Telegram, опубликовать голосовую версию и принять оплату; страница чата `/c/…` грузит виджет и обращается к API по этому адресу (без него — по `BACKEND_URL` кабинета, который браузер клиента обычно не видит) |
| `CABINET_BASE_URL` | API | адрес кабинета: туда Google Calendar и страница оплаты возвращают владельца; на нём живут страница чата `/c/{адрес}` и политика конфиденциальности по умолчанию `/c/{адрес}/privacy`. Без него Google Calendar не подключается, а «Каналы → Поделиться» не даёт ссылку на страницу чата |
| `CORS_ALLOWED_ORIGINS` | API | адрес кабинета (несколько — через запятую) |
| `BACKEND_URL` | кабинет | адрес, по которому сервер кабинета находит API (на Render — только внутренний, не публичный; см. раздел 3) |
| `DATABASE_URL` | API | строка подключения к Postgres в ЕС; на Render и в Compose задаётся сама. Без неё данные хранятся в памяти и пропадают при перезапуске |

**Админ платформы** — `PLATFORM_ADMIN_PHONE_NUMBERS` (номера в международном
формате E.164, например `+995555123456`, через запятую) и/или
`PLATFORM_ADMIN_EMAILS` (почты через запятую). Права админа проверяются при каждом
входе: впишите свой номер или почту, заново задеплойте API и воркер, выйдите из
кабинета и войдите снова — в меню появится «Админка» (`/admin`): все клиенты,
их состояние, вход в кабинет клиента (такие входы пишутся в журнал аудита).

### 4.2. Модель: OpenAI или Anthropic

Обязательно одно из двух. Без модели помощник не отвечает (ошибка 502), не
проходят автотесты и тестовый чат.

**OpenAI** (выбор концепции: `gpt-5-mini`, данные хранятся в ЕС).

- Где: платформа OpenAI для разработчиков (platform.openai.com). Создайте проект
  с хранением данных в ЕС (EU data residency) и API-ключ в этом проекте.
- Переменные: `OPENAI_API_KEY` (ключ), `OPENAI_PROJECT_ID` (id проекта).
  `OPENAI_BASE_URL` уже указывает на европейский адрес
  `https://eu.api.openai.com/v1`, `LLM_PROVIDER=openai` и модель `gpt-5-mini`
  стоят по умолчанию.
- Вебхуков нет.

**Anthropic** (запасной вариант).

- Где: консоль Anthropic (Claude Console, console.anthropic.com) — API-ключ.
- Переменные: `LLM_PROVIDER=anthropic`, `ANTHROPIC_API_KEY`. Модель по умолчанию
  — `claude-opus-5-5`.
- Вебхуков нет.

Тонкая настройка (необязательно; на Render — в группе `workshop-backend`, чтобы её
получил и воркер, который играет автотесты): `LLM_MODEL_ID` — другая модель;
`LLM_JUDGE_MODEL_ID` — модель клиента и судьи автотестов; `LLM_SUMMARY_MODEL_ID` —
модель итогов звонков для персонала (по умолчанию — `LLM_MODEL_ID`; подойдёт
более дешёвая, например `gpt-5-nano`); `LLM_CHAT_EFFORT`,
`LLM_JUDGE_EFFORT`, `LLM_MAX_OUTPUT_TOKENS`, `LLM_TOOL_ROUND_LIMIT`,
`AUTOTEST_TURN_LIMIT` — значения по умолчанию в таблице «Окружение» `README.md`.
Другой `OPENAI_BASE_URL` — тоже в группе `workshop-backend`.

**Голосовые сообщения и фото клиентов.** Голосовые из WhatsApp, Telegram,
Messenger и Instagram распознаёт модель OpenAI `LLM_TRANSCRIBE_MODEL`
(`gpt-4o-transcribe`) в том же проекте с хранением в ЕС — нужен
`OPENAI_API_KEY`, даже при `LLM_PROVIDER=anthropic`. Фото помощник видит сам
(обе модели принимают изображения), место — как координаты и ссылку на карту.
Без ключа или при `LLM_PROVIDER=scripted` голосовое не распознаётся, и клиент
получает вежливую просьбу написать текстом на своём языке — так же, как на
видео, документы, стикеры и контакты. Пределы: `MEDIA_MAX_VOICE_BYTES` (16 МиБ),
`MEDIA_MAX_IMAGE_BYTES` (5 МиБ), `MEDIA_MAX_VOICE_SECONDS` (300). Файлы
хранятся зашифрованными там же, где записи звонков (`RECORDINGS_STORAGE`), и
удаляются через `RECORDING_RETENTION_DAYS` или вместе с данными клиента.
Секунды распознавания учитываются в расходах («Распознанные голосовые сообщения» в карточке клиента у админа).

### 4.3. Коды входа в кабинет

Для запуска нужен **хотя бы один** провайдер. Код приходит первым каналом из
списка страны номера, для которого настроен провайдер: в большинстве стран
сначала SMS, потом WhatsApp; WhatsApp первым — в AR, BR, CO, ID, IL, IN, KZ, MX,
NG, ZA; Telegram добавляется в AM, AZ, BY, KG, KZ, RU, TJ, UA, UZ. Если провайдер
отказал, тот же код уходит следующим каналом. Вход по почте работает только с
SMTP. Провайдер настраивается целиком или никак: неполные настройки
останавливают запуск API с понятной ошибкой. Каждый код — платное сообщение,
поэтому отправки ограничены (`OTP_SENDS_PER_DESTINATION_PER_HOUR`,
`OTP_SENDS_PER_IP_PER_HOUR`, `OTP_SENDS_PER_HOUR`).

**SMS — Twilio** (twilio.com).

- Где: консоль Twilio (Twilio Console): Account SID и Auth Token в разделе
  Account info; номер-отправитель или Messaging Service.
- Переменные: `TWILIO_ACCOUNT_SID` (начинается с `AC`), `TWILIO_AUTH_TOKEN` и
  отправитель — `TWILIO_FROM_NUMBER` (номер E.164 или буквенное имя
  отправителя, где страна это разрешает) или `TWILIO_MESSAGING_SERVICE_SID`
  (начинается с `MG`, сам выбирает отправителя для страны).
- Вебхуков нет.

**WhatsApp — шаблон категории «authentication»** (через Meta, раздел 4.5).

- Где: номер платформы в WhatsApp Business и шаблон категории «authentication» с
  кнопкой «скопировать код», утверждённый Meta.
- Переменные: `WHATSAPP_OTP_PHONE_NUMBER_ID` (ID номера платформы, с которого
  уходят коды), `WHATSAPP_OTP_TEMPLATE` (название шаблона, например `login_code`),
  `WHATSAPP_OTP_TEMPLATE_LANGUAGES` (утверждённые языки через запятую, например
  `en,ru,ka`; первый — запасной), `WHATSAPP_OTP_ACCESS_TOKEN` (по умолчанию —
  `WHATSAPP_SYSTEM_USER_TOKEN`).
- Вебхуков нет.

**Telegram — Telegram Gateway** (gateway.telegram.org; платно за каждый
доставленный код).

- Переменная: `TELEGRAM_GATEWAY_API_TOKEN`.
- Работает только в странах, где в списке есть Telegram (см. выше).
- Вебхуков нет.

**Почта — любой SMTP** (например, Mailgun EU, Postmark, Amazon SES или обычный
почтовый ящик).

- Переменные: `SMTP_HOST`, `SMTP_PORT` (по умолчанию 587), `SMTP_SECURITY`
  (`starttls` по умолчанию, `ssl` или `none` — последнее только для локального
  тестового сервера), `SMTP_USERNAME` вместе с `SMTP_PASSWORD`, если сервер
  требует вход, `SMTP_FROM` (например,
  `Assistant Workshop <no-reply@example.com>`).
- Вебхуков нет.

Проверить, какие способы входа работают прямо сейчас, можно по адресу API +
`/v1/auth/login-options?country_code=GE` (код нужной страны): в ответе каналы
страны с провайдером и доступен ли вход по почте. Если провайдера нет совсем,
API при запуске пишет в лог ошибку `No login code provider is configured, so
nobody can sign in.`, а вход отвечает ошибкой 502.

**Защита входа от ботов и SMS pumping — Cloudflare Turnstile** (бесплатно,
dash.cloudflare.com → Turnstile).

- Зачем: боты заказывают коды на дорогие номера (SMS pumping) и подбирают коды.
  Перебор и дорогие номера (premium-rate, спутниковые) закрыты всегда; проверка
  «не робот» добавляется к рискованным запросам кода: новый номер или почта,
  адрес, уже запросивший 3 кода за час, израсходована половина часового лимита,
  страна из `OTP_HIGH_RISK_COUNTRIES`. Вернувшийся владелец её обычно не видит.
- Где: Cloudflare → Turnstile → Add widget; домен — адрес кабинета, режим
  Managed. Скопируйте Site Key и Secret Key.
- Переменные: `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET_KEY` (обе или ни одной).
  Без них проверка выключена, остальная защита работает. Для пробы на staging
  подойдут тестовые ключи Cloudflare (`1x00000000000000000000AA` и
  `1x0000000000000000000000000000000AA` — проверка всегда проходит).
- Лимиты (по умолчанию разумные): `OTP_SENDS_PER_COUNTRY_PER_HOUR` (100 кодов в
  час на новые номера одной страны), `OTP_SENDS_TO_VERIFIED_USERS_PER_HOUR` (300 —
  отдельный бюджет для вернувшихся пользователей), `OTP_VERIFIES_PER_IP_PER_10_MINUTES`
  (20 проверок кода с адреса), `OTP_DENIED_PHONE_PREFIXES` (диапазоны, на которые
  код не уходит, например `+4470`). Когда срабатывает общий лимит, админы из
  `PLATFORM_ADMIN_EMAILS` получают письмо (нужен SMTP), а Sentry — событие: проверьте
  в журнале провайдера SMS, куда уходили коды, и добавьте страну в
  `OTP_HIGH_RISK_COUNTRIES` или диапазон в `OTP_DENIED_PHONE_PREFIXES`.

### 4.4. Уведомления сотрудникам

Сотрудники бизнеса получают передачи разговоров, брони и заявки — в Telegram,
WhatsApp, на почту, по SMS и на свои устройства (Web Push). Без контакта
сотрудника помощника нельзя опубликовать. Каждое уведомление уходит через
исходящие с повторами, а в кабинете («Настройки» → «Уведомления») у каждого
контакта видно, дошло ли последнее (или почему нет), у чата Telegram,
подключённого через бота, — его @username, а владелец может «Отправить
проверку» (не больше 5 в час на контакт). Сотрудники с ролью «сотрудник»
видят в настройках только эту страницу: свои устройства, события и тихие
часы. Каждое уведомление заканчивается подписанной ссылкой
`CABINET_BASE_URL/n/…` на разговор, заявку или бронь: она действует 7 дней и
открывается только после входа (без `CABINET_BASE_URL` ссылки в уведомлениях
нет). В почте, SMS и на экране устройства нет имени, телефона и текста
клиента — только что случилось и ссылка. Сотрудник выбирает события и тихие
часы (в часовом поясе бизнеса; срочные передачи приходят и ночью); одному
получателю уходит не больше 10 SMS, 20 WhatsApp и 30 остальных уведомлений в
час.

Нужен **хотя бы один** способ из списка ниже.

**Почта и SMS** — те же провайдеры, что и для кодов входа (раздел 4.3):
`SMTP_*` для почты, `TWILIO_*` для SMS. Отдельных переменных нет. Без
провайдера в рабочей версии такое уведомление отмечается недоставленным с
причиной, вне `production` пишется в лог.

**Уведомления на устройствах (Web Push)** — бесплатно, на телефоне и
компьютере, в установленном приложении кабинета и в браузере.

- Ключи: один раз `npx web-push generate-vapid-keys` — публичный и закрытый
  ключ (base64url).
- Переменные: `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`,
  `WEB_PUSH_VAPID_SUBJECT` (`mailto:` адрес команды или `https://` страница) —
  все три или ни одной. Пару ключей API проверяет при запуске. Сменить ключи
  можно, но тогда устройства надо включить заново.
- Включает каждый сотрудник сам: «Настройки» → «Уведомления» → «Включить на
  этом устройстве». На iPhone и iPad сначала добавьте кабинет на экран
  «Домой» (Safari → «Поделиться» → «На экран Домой»), иначе iOS не даёт
  уведомлений. Проверка — кнопка «Отправить проверку».
- Проверить вживую можно только на настоящем телефоне: тесты используют
  поддельный push-сервис (шифрование сверено с примером RFC 8291).

**Бот платформы в Telegram** (бесплатно, проще всего).

- Где: в Telegram у @BotFather — команда `/newbot`, имя и username,
  оканчивающийся на `bot`; BotFather пришлёт токен.
- Переменная: `TELEGRAM_PLATFORM_BOT_TOKEN`.
- Вебхук регистрируется сам при запуске API (`адрес API` +
  `/v1/channels/telegram-platform/webhook`), если заданы токен, `ENCRYPTION_KEY`
  и `APP_BASE_URL`. Поменяли адрес API или токен — перезапустите API.
- Сотрудник подключается по личной ссылке из кабинета: «Каналы» → «Уведомления
  сотрудникам в Telegram» → «Создать ссылку».

**Шаблон WhatsApp** (с номера платформы, платно по тарифам Meta).

- Где: номер платформы в WhatsApp Business и утверждённый Meta шаблон с одной
  переменной в тексте (например, `staff_notification`), раздел 4.5.
- Переменные: `WHATSAPP_NOTIFICATION_PHONE_NUMBER_ID`,
  `WHATSAPP_NOTIFICATION_TEMPLATE`.
- Шаблон уходит на языке сотрудника, а если перевода нет — на английском, так
  что английский перевод нужен обязательно.

### 4.5. Meta: WhatsApp Cloud API, Instagram, Messenger

По желанию: без Meta работают Telegram и чат на сайте. Для WhatsApp, Instagram и
Messenger бизнесов, а также для кодов входа и уведомлений через WhatsApp нужен
аккаунт Meta.

- Где: Meta for Developers (developers.facebook.com) — приложение с продуктами
  WhatsApp, Messenger и Instagram; бизнес-аккаунт Meta (Meta Business Suite) с
  системным пользователем и номером платформы в WhatsApp Business; шаблоны — в
  WhatsApp Manager.
- Переменные:
  - `META_APP_SECRET` — секрет приложения: им проверяется подпись каждого
    вебхука Meta;
  - `META_VERIFY_TOKEN` — любая случайная строка, которую вы придумали сами
    (раздел 4.1); её же вписываете в настройки вебхука у Meta;
  - `WHATSAPP_SYSTEM_USER_TOKEN` — токен системного пользователя: открывает
    номера WhatsApp бизнесов и платформы и отправляет сообщения;
  - `META_APP_ID` — пока не используется кодом, можно оставить пустым.
- Вебхук: в настройках приложения укажите адрес обратного вызова `адрес API` +
  `/v1/channels/meta/webhook` и токен проверки `META_VERIFY_TOKEN`; подпишите
  приложение на сообщения (поле `messages`) для WhatsApp Business Account,
  страниц (Page) и Instagram. Конкретную страницу бизнеса (и его аккаунт WhatsApp
  Business, если владелец указал его ID) платформа подписывает на обновления
  сама, когда владелец подключает канал.
- Проверка приложения (App Review) нужна для Instagram, Messenger и для доступа
  к WhatsApp-аккаунтам бизнесов (расширенный доступ к
  `whatsapp_business_management` и `whatsapp_business_messaging`, вместе с
  верификацией бизнеса платформы) — по концепции на неё стоит заложить время до
  первых клиентов.

Как бизнес подключает каналы («Каналы» в кабинете):

- **WhatsApp**: встроенной регистрации (Embedded Signup) в кабинете пока нет,
  номер подключается вручную. Платформа API ходит к номеру бизнеса с токеном
  `WHATSAPP_SYSTEM_USER_TOKEN`, поэтому её системный пользователь должен
  получить доступ к аккаунту WhatsApp Business (WABA) бизнеса.
  - Один раз для платформы: в Meta Business Suite → «Настройки компании» →
    «Пользователи» → «Системные пользователи» создайте системного пользователя
    с правами администратора, добавьте ему приложение и выпустите токен с
    разрешениями `whatsapp_business_management`, `whatsapp_business_messaging`
    (и `business_management`) — это и есть `WHATSAPP_SYSTEM_USER_TOKEN`. Чтобы
    работать с аккаунтами других компаний, приложению нужен расширенный доступ
    к этим разрешениям (App Review), а бизнес-портфолио платформы — пройденная
    верификация бизнеса (статус Tech Provider в Meta).
  - Для каждого бизнеса: (а) бизнес регистрирует свой номер в Cloud API в своём
    аккаунте WhatsApp Business (статус «Подключён» в WhatsApp Manager) и в своих
    «Настройках компании» → «Аккаунты» → «Аккаунты WhatsApp» → аккаунт →
    «Партнёры» добавляет бизнес-портфолио платформы партнёром с полным доступом
    (ID портфолио — в ваших «Настройках компании» → «Информация о компании»);
    (б) вы в своих «Настройках компании» → «Системные пользователи» →
    пользователь → «Назначить активы» даёте ему полный доступ к этому аккаунту
    WhatsApp; (в) владелец вводит в кабинете («Каналы» → WhatsApp) ID номера
    телефона и ID аккаунта WhatsApp Business из WhatsApp Manager.
  - Другой путь — зарегистрировать номер бизнеса в собственном аккаунте WhatsApp
    Business платформы; тогда шаблоны и оплата Meta идут через платформу.
- **Instagram и Messenger**: ID страницы Facebook и токен доступа страницы
  (Instagram — профессиональный аккаунт, связанный со страницей).

**Шаблоны WhatsApp, которые должна утвердить Meta.** Свободный текст в WhatsApp
можно отправлять только в течение 24 часов после последнего сообщения клиента;
всё остальное — утверждённые шаблоны:

| Шаблон | В каком аккаунте | Переменные шаблона | Куда вписать | Без него |
| --- | --- | --- | --- | --- |
| Коды входа (категория «authentication», кнопка «скопировать код») | номер платформы | код | `WHATSAPP_OTP_TEMPLATE`, языки — `WHATSAPP_OTP_TEMPLATE_LANGUAGES` | коды не приходят в WhatsApp |
| Уведомления сотрудникам | номер платформы | одна: текст уведомления | `WHATSAPP_NOTIFICATION_TEMPLATE` | уведомления только в Telegram |
| Напоминания о бронях | аккаунт WhatsApp каждого бизнеса | четыре: бизнес, дата, время, имя | `WHATSAPP_REMINDER_TEMPLATE` (одно название для всех бизнесов) | напоминание в WhatsApp уходит, только если клиент писал туда за последние 24 часа |
| Ответы сотрудников позже 24 часов | аккаунт WhatsApp бизнеса | одна: текст сотрудника | владелец вписывает название и язык шаблона в кабинете («Каналы» → WhatsApp) | ответить клиенту в WhatsApp через сутки после его последнего сообщения нельзя |
| Запрос отзыва после визита | аккаунт WhatsApp бизнеса | одна: название бизнеса | владелец вписывает название шаблона в кабинете («Настройки» → «Отзывы»); текст для Meta на каждом языке показан там же | клиентов WhatsApp, молчавших больше суток, о визите не спрашивают |

Шаблоны напоминаний и уведомлений уходят на языке получателя, а если перевода
нет — на английском: английский перевод нужен у каждого.

**Отзыв после визита и ссылка Google.** Через заданное время после конца
брони (по умолчанию 2 часа) платформа спрашивает клиента в его мессенджере
и на его языке, как прошёл визит (1–5). Ответ принимает сама платформа:
благодарит и присылает ссылку на страницу отзывов Google — всем, при любой
оценке (просить отзыв только у довольных запрещено правилами Google);
оценка 3 и ниже ещё и попадает в «Нужен человек». Владелец включает это в
кабинете: «Настройки» → «Отзывы» (там же ссылка Google, шаблон WhatsApp и
цифры за 30 дней). Ключей не нужно; переходы по ссылке считаются, когда
задан `APP_BASE_URL` (ссылка идёт через `{APP_BASE_URL}/v1/public/reviews/…`),
без него клиент получает адрес Google напрямую. Клиент, ответивший «STOP»
(«СТОП», «სტოპ» и переводы), больше не получает ни запросов отзыва, ни
напоминаний, ни сообщений после пропущенного звонка; «START» возвращает их.

### 4.6. Звонки: ElevenLabs и Zadarma

Нужны, если вы продаёте тарифы со звонками («Голос + чат» и «Плюс»): в рабочей
версии без ElevenLabs опубликовать версию помощника с голосом нельзя (причина
`voice_configuration` в чек-листе запуска). Для тарифа «Чат» не нужны.

**ElevenLabs** (elevenlabs.io) — голосовой агент; данные голоса — в ЕС.

- Где: аккаунт ElevenLabs с хранением данных в ЕС (EU data residency) и API-ключ.
- Переменные: `ELEVENLABS_API_KEY`, `ELEVENLABS_WEBHOOK_SECRET`.
  `ELEVENLABS_API_BASE_URL` уже указывает на европейский адрес
  `https://api.eu.residency.elevenlabs.io`; другой адрес рабочая версия
  отклоняет, пока не задан `ELEVENLABS_ALLOW_NON_EU_REGION=true`. Обе
  переменные на Render задавайте в группе `workshop-backend`: воркер удаляет
  старые записи звонков по тому же адресу.
- Вебхук после звонка (post-call): в настройках вебхуков ElevenLabs укажите
  `адрес API` + `/v1/voice/webhooks/post-call`; секрет подписи (HMAC) этого
  вебхука впишите в `ELEVENLABS_WEBHOOK_SECRET`. Через него приходят
  расшифровка, запись и стоимость звонка.
- Вебхуки инструментов (`адрес API` + `/v1/voice/tools/{инструмент}`) и начала
  звонка (`адрес API` + `/v1/voice/webhooks/conversation-initiation`)
  регистрировать не нужно: платформа сама создаёт агента ElevenLabs для каждого
  бизнеса при публикации версии с голосом и прописывает ему эти адреса и секрет,
  выведенный из `ELEVENLABS_WEBHOOK_SECRET`. Если поменяли `APP_BASE_URL` или
  `ELEVENLABS_WEBHOOK_SECRET`, соберите и опубликуйте новую версию каждого
  бизнеса со звонками: при публикации платформа обновляет его агента.
- Агент говорит по своей, телефонной инструкции версии (цены, часы и даты —
  так, как их произносят, без ссылок) и в начале каждого звонка получает
  местные дату и время, ближайшие дни и, если звонящий известен по
  подтверждённому номеру, его имя и ближайшую бронь. Версии, собранные до
  обновления, звонят со старой (чатовой) инструкцией: после выката соберите и
  опубликуйте новую версию бизнесов со звонками. Ссылки агент не зачитывает:
  платформа присылает их сообщением после звонка, если звонящий известен в
  подключённом мессенджере. После каждого звонка сказанные агентом цены,
  время и даты сверяются с данными бизнеса; если в звонке с бронью или
  заявкой нашлось значение не из данных, сотрудник получает передачу с
  низкой срочностью, а карточка разговора показывает найденное.

**Записи звонков в объектном хранилище ЕС.** Без настройки запись каждого
звонка остаётся у ElevenLabs (кабинет проигрывает её оттуда, воркер удаляет
её там по сроку хранения). С `RECORDINGS_STORAGE=s3` платформа хранит записи
сама, в S3-совместимом хранилище в ЕС, и оба экземпляра API видят одни и те
же файлы (локальная папка `RECORDINGS_DIRECTORY` — только для разработки на
одном компьютере):

- Где: AWS S3 в `eu-central-1`, Cloudflare R2 с юрисдикцией ЕС, Hetzner Object
  Storage или Scaleway. Создайте закрытый бакет без версий (иначе удалённая
  запись остаётся старой версией) и ключ доступа, которому разрешены только
  чтение, запись и удаление объектов этого бакета.
- Переменные (в `render.yaml` у API, воркер копирует их):
  `RECORDINGS_STORAGE=s3`, `RECORDINGS_S3_ENDPOINT_URL` (например
  `https://s3.eu-central-1.amazonaws.com` или адрес бакета R2 вида
  `https://<account>.eu.r2.cloudflarestorage.com`), `RECORDINGS_S3_REGION`
  (`eu-central-1`; у R2 — `auto`), `RECORDINGS_S3_BUCKET`,
  `RECORDINGS_S3_ACCESS_KEY_ID`, `RECORDINGS_S3_SECRET_ACCESS_KEY`. Без любой
  из них или без `ENCRYPTION_KEY` процесс не запустится и назовёт, чего не
  хватает.
- После каждого звонка воркер (задача `archive_call_recording`) копирует
  запись из ElevenLabs в бакет и удаляет разговор у ElevenLabs: вторая копия
  у подрядчика не остаётся, а срок хранения и удаление данных контакта
  работают с копией в бакете.
- В бакет запись попадает уже зашифрованной: ключ каждого бизнеса выводится
  из `ENCRYPTION_KEY` (HKDF), запись шифруется AES-256-GCM блоками по 64 КиБ.
  Хранилище видит только шифротекст, а запись одного бизнеса не открывается
  ключом другого. При смене ключа (раздел 4.11) записи, зашифрованные
  прежним ключом, открываются, пока он остаётся в `ENCRYPTION_KEYS`: держите
  его там до конца срока хранения записей (`RECORDING_RETENTION_DAYS`).
- Кабинет перематывает запись: API читает из бакета только нужные блоки
  (запросы с диапазоном байт по ссылкам с подписью, действующим минуту).

**Zadarma** (zadarma.com) — номера помощников.

- Номер для каждого бизнеса покупается в Zadarma вручную (концепция: в Грузии —
  номер +995) и направляется по SIP на агента ElevenLabs этого бизнеса (агент
  называется «название бизнеса (id бизнеса)»). Код этого не автоматизирует.
- Номер вписывается в кабинете бизнеса: «Каналы» → Телефон; после этого кабинет
  показывает владельцу коды переадресации неотвеченных и занятых звонков с его
  номера на номер помощника.
- Концепция советует проверить правило в АТС Zadarma «если SIP недоступен — на
  мобильный дежурного».
- `ZADARMA_API_KEY` пока не используется кодом, его можно оставить пустым.
- Пропущенные звонки на линии (занято, никто не ответил, клиент сбросил до
  помощника, линия не соединила): в личном кабинете Zadarma → «Настройки» →
  «Интеграции и API» → «Уведомления о звонках в АТС» укажите адрес
  `https://<API>/v1/telephony/zadarma/notifications` и включите уведомление
  о конце входящего звонка («NOTIFY END»). Zadarma сначала проверит адрес
  запросом с `zd_echo` — API отвечает на него сам. Впишите в окружение API
  `ZADARMA_API_SECRET` (секрет из «Интеграции и API» → «Ключи и API»): им
  подписано каждое уведомление, без него уведомления отклоняются (401).
- Звонки, которые помощник принял, но клиент молча положил трубку, звонки,
  которые ElevenLabs не смог начать (событие `call_initiation_failure` того же
  post-call-вебхука), и переводы на сотрудника, на которые никто не ответил,
  находятся сами — настраивать ничего не нужно.

**Сообщение после пропущенного звонка (text-back).** Клиенту, который не
дозвонился, в течение минуты-двух уходит сообщение в WhatsApp с номера
бизнеса, а если WhatsApp недоступен — SMS с отправителя платформы (Twilio,
те же `TWILIO_*`, что для кодов входа). Владелец включает это в кабинете:
«Настройки» → «Звонки».

- WhatsApp требует одобренный Meta шаблон категории UTILITY в WABA номера
  бизнеса. Текст шаблона на каждом языке бизнеса кабинет показывает там же
  («Настройки» → «Звонки» → «Текст шаблона»), с одним параметром `{{1}}` — названием
  бизнеса. Создайте шаблон с этим текстом в WhatsApp Manager на нужных языках
  и впишите его имя в кабинете. Сообщение уходит на языке звонившего (язык
  звонка, иначе язык страны его номера, если бизнес на нём говорит), при
  отказе Meta — на английском.
- Ответ клиента приходит в обычный разговор WhatsApp, который сообщение и
  открыло: помощник видит, что клиенту написали после пропущенного звонка.
- Не чаще одного сообщения одному номеру в сутки и не больше 200 сообщений
  бизнеса в сутки; клиенту, который отказался от сообщений или уже
  переписывается с бизнесом, сообщение не уходит. Каждое решение (отправлено,
  пропущено и почему) видно в списке последних сообщений там же.
- SMS не тарифицируется в использовании бизнеса (стоимость несёт аккаунт
  Twilio платформы); отключается переключателем «Отправлять SMS, если
  WhatsApp недоступен».

**Итоги звонков для персонала.** После каждого звонка сотрудникам в Telegram
и WhatsApp (и на устройства с push) приходит итог: кто звонил, что хотел
(короткий текст от модели `LLM_SUMMARY_MODEL_ID` на языке получателя), чем
закончилось, бронь, значения, которых нет в данных бизнеса, и ссылка на
разговор с записью. О пропущенном звонке приходит заметка — во все каналы,
включая e-mail и SMS, чтобы кто-то перезвонил. Отключается в «Настройки» →
«Звонки». Итог виден и на карточке звонка в кабинете.

### 4.7. Оплата: Flitt

- Зачем: подписки с автоматическим списанием. Без Flitt работает бесплатный
  пробный период (14 дней), а оплата отвечает ошибкой 502 — поэтому Flitt нужен
  до конца первых пробных периодов.
- Где: кабинет мерчанта Flitt (flitt.com). По концепции для Грузии нужен счёт в
  TBC.
- Переменные: `FLITT_MERCHANT_ID`, `FLITT_SECRET_KEY`.
- Адрес уведомлений об оплате (callback): `адрес API` +
  `/v1/payments/flitt/webhook`. API передаёт его в каждом платеже сам, поэтому
  без `APP_BASE_URL` оплата не работает.
- Валюта: бизнес платит в своей валюте, если для неё есть цены тарифа (сейчас —
  лари в Грузии), иначе в евро.

### 4.8. Google Calendar

- Зачем: брони попадают в календарь бизнеса. По желанию.
- Где: Google Cloud Console — проект с включённым Google Calendar API, экран
  согласия OAuth и OAuth-клиент типа «веб-приложение». Доступ запрашивается
  только к событиям календаря (`calendar.events`).
- Переменные: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`; также
  нужны `APP_BASE_URL` и `CABINET_BASE_URL`.
- Адрес перенаправления (Authorized redirect URI): `адрес API` +
  `/v1/integrations/google-calendar/callback`.
- Владелец подключает календарь в кабинете: «Каналы» → «Подключить Google
  Календарь».

### 4.9. Наблюдение: Langfuse и Sentry

**Langfuse** — журнал каждого ответа модели (качество, разбор разговоров).

- Где: Langfuse Cloud в регионе ЕС (cloud.langfuse.com) — проект и его API-ключи.
- Переменные: `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`; `LANGFUSE_HOST` уже
  `https://cloud.langfuse.com`. `LANGFUSE_CAPTURE_CONTENT=true` пишет в журнал и
  тексты сообщений — это персональные данные клиентов, включайте осознанно (по
  умолчанию `false`). `LANGFUSE_HOST` и `LANGFUSE_CAPTURE_CONTENT` на Render
  задавайте в группе `workshop-backend`: журнал отправляет и воркер.

**Sentry** — неожиданные ошибки API, воркера, виджета на сайтах и кабинета.

- Где: sentry.io (регион ЕС) — проект и его DSN; для кабинета удобнее
  отдельный проект.
- Переменные: `SENTRY_DSN` у `workshop-api` (воркер копирует его) и
  `SENTRY_DSN` у `workshop-cabinet`. Без них ошибки только в логе.
- Каждая ошибка помечена версией сборки (Render сам задаёт
  `RENDER_GIT_COMMIT`; на других платформах — `APP_RELEASE`) и тегами
  `request_id`, `business_id`, `conversation_id`, `channel`, `job_name` —
  по ним ошибку находят в логах. Тела запросов, пользователи и тексты
  сообщений в Sentry не уходят.
- `SENTRY_TRACES_SAMPLE_RATE` (группа `workshop-backend`) — доля запросов
  API с трассировкой, по умолчанию `0.05`.
- Периодические задачи (напоминания, пробные периоды, очистка) сами
  создают мониторы в разделе Crons: пропущенный или упавший запуск придёт
  уведомлением Sentry.

### 4.10. Остальные настройки

У остальных переменных разумные значения по умолчанию (таблица «Окружение» в
`README.md`). На Render их задавайте в группе `workshop-backend`, которую читают и
API, и воркер. Чаще всего могут понадобиться:

- `RESTRICTED_COUNTRY_CODES` — страны, из которых нельзя войти по номеру и
  создать бизнес; по умолчанию `CU,IR,KP,SY`. Список нужно сверить с юристом.
- `RECORDING_RETENTION_DAYS` — срок хранения записей и расшифровок звонков по
  умолчанию (90 дней; бизнес может поменять свой). Голосовые сообщения и фото
  клиентов хранятся столько же.
- `DPA_DOCUMENT_VERSION` — действующая версия договора обработки данных
  (раздел 5; новую версию включайте вместе с пересборкой образа).
- `WORKER_LANE_CONCURRENCY` — потоки воркера по полосам: ответы клиентам
  (`inbound`), отправки (`outbound`), прочие задачи (`default`) и прогоны
  автотестов (`autotests`).
- `THREADPOOL_SIZE` и `DB_POOL_SIZE` — сколько запросов API обрабатывается
  одновременно (64) и сколько соединений с базой держит один процесс
  (половина потоков). `render.yaml` уже задаёт их: у двух экземпляров API —
  40 потоков и 12 соединений, у воркера — 16 соединений. Во время деплоя
  старые и новые экземпляры работают вместе, и вместе с резервной копией,
  миграцией и запасом выходит 94 из 100 соединений тарифа `basic-256mb`
  (это проверяет `tests/platform/test_connection_budget.py`). Третий
  экземпляр API — только с тарифом базы, у которого больше соединений, с
  PgBouncer перед базой или с меньшими пулами
  (`docs/operations/capacity.md`, «Connection budget»).
- `DB_POOL_MIN_SIZE` и `DB_POOL_MAX_IDLE_SECONDS` — после пика нагрузки
  соединение, простоявшее 300 с, закрывается, пока открыто больше двух.
- `TEST_CHAT_MAX_CONCURRENCY` — сколько тестовых чатов владельцев один
  экземпляр API ведёт одновременно (4); следующий владелец видит «попробуйте
  через несколько секунд».
- `WORKER_INBOUND_POLL_SECONDS` — сообщение клиента воркер берёт сразу:
  очередь будит его через Postgres (`NOTIFY`). Если пробуждение потерялось
  (переподключение к базе), воркер всё равно найдёт сообщение не позже чем
  через столько секунд (2).
- `LLM_CALL_TIMEOUT_SECONDS` — сколько ждать один ответ модели в чате (25 с,
  затем одна повторная попытка и передача сотруднику).
- `LLM_MAX_CONCURRENCY` — сколько вызовов модели один процесс делает
  одновременно (по умолчанию 32; в `render.yaml` — 8 у API и 12 у
  воркера: ответы клиентам готовит воркер). Следующий вызов ждёт свободного места не дольше
  `LLM_CALL_TIMEOUT_SECONDS`, и медленная модель не занимает все потоки
  запросов: кабинет отвечает и под нагрузкой.
- `LOG_FORMAT` — `json` в `production` (строки для поиска в логах Render с
  `request_id`, `business_id`, `job_name`), `text` при отладке.
- `LIVE_EVENTS_DATABASE_URL` — кабинет обновляется сам (новые передачи,
  заявки, брони и сообщения появляются за секунду): API слушает события базы
  (`LISTEN`) по одному соединению на процесс. На Render база подключена
  напрямую, и переменная не нужна. Если `DATABASE_URL` идёт через пулер
  транзакций (PgBouncer, Supavisor на порту 6543), укажите здесь прямое
  подключение к той же базе (у Supabase — «Session pooler» или «Direct
  connection»).

### 4.11. Резервные копии вне Render и смена ключа

Render сам делает снимки базы и восстанавливает её на любой момент в пределах
окна своего тарифа (вкладка Recovery базы). Этого не хватит, если пропадёт сам
аккаунт или регион, поэтому `render.yaml` создаёт cron-сервис
`workshop-backup`: каждую ночь он снимает базу одним согласованным снимком,
шифрует копию форматом age и кладёт её в бакет другого провайдера в ЕС.
Подробности, RPO и RTO, восстановление по шагам — в
`docs/operations/backup-restore.md`.

**Настройка (один раз).**

1. Бакет в ЕС у другого провайдера (AWS `eu-central-1`, Hetzner, Scaleway,
   Cloudflare R2 с юрисдикцией ЕС): закрытый, с версиями; правило жизненного
   цикла удаляет прежние версии через 14 дней и незавершённые загрузки через
   2 дня. Два ключа доступа: для копий (запись, список, удаление в папке
   `workshop/`) и для учений (только чтение и список).
2. Два ключа age (`age-keygen` на своём компьютере, не на сервере): ключ
   учений и ключ на хранении (распечатать и убрать в сейф, копия — в хранилище
   паролей; держат двое). Сервисам нужны только открытые ключи `age1…`.
3. В `workshop-backup` на Render: `BACKUP_S3_ENDPOINT_URL`,
   `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID`,
   `BACKUP_S3_SECRET_ACCESS_KEY` (ключ для копий) и `BACKUP_AGE_PUBLIC_KEY` —
   оба открытых ключа через запятую. Хранение — 30 ежедневных и 12 ежемесячных
   копий (`BACKUP_KEEP_DAILY`, `BACKUP_KEEP_MONTHLY`).
4. Учения восстановления идут в GitHub Actions
   (`.github/workflows/restore-drill.yml`): каждую ночь — круг «копия →
   восстановление» текущего кода, по понедельникам — свежая копия production
   во временную базу. Для еженедельных учений задайте в репозитории
   переменные (Settings → Variables) `BACKUP_S3_ENDPOINT_URL`,
   `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET` и создайте окружение `backup-drill`
   с секретами `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` (ключ
   учений), `BACKUP_AGE_IDENTITY` (закрытый ключ учений) и `SENTRY_DSN`. Пока
   `BACKUP_S3_BUCKET` не задан, еженедельные учения пропускаются.
5. В Sentry появятся мониторы `database-backup` (раз в сутки) и
   `restore-drill` (раз в неделю): пропуск или ошибка — оповещение.

**Смена ключа шифрования** (ключ мог утечь, сотрудник с доступом ушёл или
просто пришёл срок):

1. Новый ключ:
   `python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
2. В группе `workshop-backend` задайте `ENCRYPTION_KEYS` = новый ключ.
   `ENCRYPTION_KEY` пока не трогайте: он идёт следом как прежний. После деплоя
   всё новое шифруется новым ключом, старое открывается прежним, вебхуки
   Telegram принимают оба секрета.
3. Кабинет админа → «Ключи шифрования» → «Перешифровать токены» (или
   `POST /v1/admin/security/encryption-keys/rotate`). Дождитесь итога: все
   секреты на новом ключе, «не открываются» — 0, вебхуки Telegram заново
   зарегистрированы без ошибок.
4. Через 7 дней (срок ссылок из уведомлений) и после срока хранения записей
   звонков в бакете задайте `ENCRYPTION_KEY` = новый ключ и удалите
   `ENCRYPTION_KEYS`. Прежний ключ храните вместе с ключами age год: им
   открываются токены в старых резервных копиях.

## 5. Договор обработки данных (DPA)

Владелец каждого бизнеса принимает договор обработки данных в кабинете
(«Настройки» → «Данные и приватность» → «Принять договор»); без принятого
договора помощника нельзя опубликовать. Тексты лежат в `docs/legal/` на
английском, русском и грузинском (`dpa-2026-10-01.<язык>.md`).

**Это шаблон.** До запуска его должен проверить юрист вашей юрисдикции и стран
ваших клиентов. Заполните все поля в квадратных скобках: реквизиты оператора,
места обработки у субобработчиков, сроки уведомлений, резервные копии,
применимое право — и держите три языка одинаковыми. Изменённый текст — это новая
версия: новые файлы с новой датой в `docs/legal/` и новое значение
`DPA_DOCUMENT_VERSION`; тогда владельцы примут договор заново. Версию без текста
принять нельзя, поэтому новое значение включайте только вместе со сборкой из
коммита с новыми файлами: на Render — «Save, rebuild, and deploy» (не «Save and
deploy»: тот перезапускает старую сборку без новых файлов) или Manual Deploy →
«Deploy latest commit». Рабочая версия, в сборке которой нет текста настроенной
версии, не запускается и пишет, какого файла не хватает; предыдущий деплой при
этом продолжает работать.

У юриста стоит сверить и другое, что в коде помечено как «подтвердить с
юристом»: список `RESTRICTED_COUNTRY_CODES` и правила записи звонков по странам
(раздел 6).

## 6. Новая страна

Продукт работает в любой стране без доработки кода: владелец входит по номеру
своей страны, а профиль страны собирается автоматически:

- номера телефонов разбираются для 245 регионов и хранятся в международном
  формате;
- языки, валюта и часовые пояса берутся из общих справочников (CLDR);
- брони считаются в часовом поясе бизнеса, цены хранятся в его валюте;
- коды переадресации звонков (GSM) работают почти в любой мобильной сети;
- тексты SMS и писем с кодом — на английском, русском, грузинском, украинском,
  турецком, иврите, арабском, немецком, французском, испанском, иначе на
  английском.

Поверх этого для страны можно уточнить данные. Это правка кода в
`app/registries/` (её делает разработчик):

| Что уточняется | Где |
| --- | --- |
| Языки, на которых помощник отвечает с первого дня, языки «по запросу» (туристы, общины) и язык кабинета владельца | `localization/curated_country_languages.py` |
| Экстренный номер (по умолчанию 112), порядок каналов кода входа, можно ли купить местный номер без документов (сейчас GE, US, CA, GB), нужно ли согласие всех сторон на запись звонка (сейчас AU, CH, DE, FR, US; в остальных — предупреждение в начале звонка), пилотные страны (сейчас GE) | `localization/curated_country_telephony.py` |
| Часовой пояс и валюта по умолчанию, где справочник неоднозначен | `localization/curated_country_time_and_money.py` |
| Операторы связи и их инструкции по переадресации (сейчас для Грузии: Magti, Silknet, Cellfie) | `localization/call_forwarding_texts.py` |
| Цены тарифов в местной валюте (сейчас лари; без них — евро) и запасные курсы на случай, когда ежедневное обновление ещё не сохранило курсы НБГ и ЕЦБ (задача `refresh_exchange_rates` раз в 6 часов читает nbg.gov.ge и ecb.europa.eu; при закрытом исходящем доступе их нужно разрешить) | `billing/plan_catalog.py`, `billing/exchange_rate_catalog.py` |

Вне кода для новой страны:

- юрист: договор обработки данных, правило записи звонков,
  `RESTRICTED_COUNTRY_CODES`;
- коды входа: доступен ли там отправитель Twilio (буквенное имя или номер), есть
  ли нужный язык у шаблона кода WhatsApp (`WHATSAPP_OTP_TEMPLATE_LANGUAGES`);
- переводы шаблонов WhatsApp (напоминания, уведомления) на языки страны;
- номера помощников для звонков в этой стране;
- приём оплаты: в какой валюте и через какой счёт.

## 7. Проверка после первого деплоя

1. **Здоровье.** Откройте `адрес API` + `/healthz` — ответ `{"status": "ok"}`,
   затем `адрес API` + `/readyz` — `"status": "ready"`; у `worker` через
   минуту после старта воркера `heartbeat_age_seconds` — несколько секунд.
   `адрес API` + `/v1/auth/login-options?country_code=GE` (код своей страны)
   показывает, какими каналами сейчас уходят коды входа.
2. **Вход.** Откройте адрес кабинета, войдите номером из
   `PLATFORM_ADMIN_PHONE_NUMBERS` (или почтой): код должен прийти настоящим
   сообщением. В меню есть «Админка».
3. **Бизнес.** Создайте бизнес (название, ниша, страна, языки) и пройдите
   «Анкету» — шесть шагов: ниша и языки, контакты и часы, предложение, правила
   брони, вопросы и передача человеку, каналы. Блок «Что дописать» покажет, чего не хватает.
4. **Подготовка к публикации.** Пробный период начнётся сам при первой
   публикации (кнопка «Оплата» → «Начать бесплатно» запускает его раньше);
   «Настройки» → «Данные и приватность» → «Принять договор»; «Настройки» →
   «Уведомления» → «Кто получает уведомления» — добавьте сотрудника (Telegram или
   WhatsApp); сотрудника в Telegram подключите по ссылке из «Каналы» →
   «Уведомления сотрудникам в Telegram».
5. **Сборка и автотесты.** «Помощник» → «Версии» → «Собрать новую версию».
   Автотесты играет фоновый воркер; ход виден на странице версии.
6. **Тестовый чат.** «Помощник» → «Тестовый чат»: задайте пару вопросов о
   бизнесе и попробуйте забронировать.
7. **Публикация.** На странице версии чек-лист запуска (пробный период,
   подписка или пробный период, который начнётся при запуске, договор, анкета
   без блокирующих пробелов, контакт сотрудника, автотесты, для тарифов со
   звонками — голос) должен быть зелёным → «Опубликовать». То же одним
   вызовом — `POST /v1/businesses/{business_id}/assistant/apply` («Применить
   изменения»: сборка, автотесты воркером и публикация); ход — в
   `GET /v1/businesses/{business_id}/setup`. После публикации на «Оплате» идёт
   пробный период на 14 дней.
8. **Виджет.** «Каналы» → карточка «Чат на сайте» → «Включить». Ниже появится
   раздел «Код чата для сайта» → «Открыть живой предпросмотр» (страница
   `адрес API` + `/widget/demo?business_id=…`): напишите сообщение и дождитесь
   ответа; разговор появится в «Разговорах». Затем вставьте код на сайт
   бизнеса.
9. **Страница чата и QR-код.** «Каналы» → «Поделиться»: откройте ссылку
   страницы чата (`адрес кабинета` + `/c/{адрес}`) на телефоне — чат на весь
   экран, на языке телефона, внизу «AI-ассистент · может ошибаться ·
   Конфиденциальность». При желании смените адрес («Изменить адрес»; старый
   продолжит работать), выберите, где разместите ссылку (метка `?src=`),
   скачайте QR-код (PNG или SVG) или распечатайте карточку A6 на столик и
   отсканируйте её телефоном. Ссылки WhatsApp, Instagram и Messenger
   появляются после подключения канала (подключённым раньше этого выпуска —
   после переподключения: API узнаёт публичный номер и имена аккаунтов при
   подключении). Свою политику конфиденциальности укажите в «Анкете» →
   ссылки → «Политика конфиденциальности», иначе виджет ведёт на политику
   платформы по умолчанию.
10. **Остальное по мере подключения:** бот Telegram бизнеса, WhatsApp, Instagram,
   Messenger (сообщение доходит и получает ответ), звонок на номер помощника
   (после звонка в разговоре есть расшифровка), Google Calendar, тестовая оплата
   через Flitt, появление событий в Langfuse и Sentry.
